# DB 構成（v3）に、決済と返金・手数料・店舗の閉鎖・組織のロール・招待キー・警告の履歴を足す（issue #126）

## Context

2026-11-11 に、店舗側アカウントの作り直し（#103）で使う DB の構成（v3）を決めた（[2026-11-11-shop-organization-db-v3.md](2026-11-11-shop-organization-db-v3.md)）。その後、2026-11-12 までに、DB の形が変わる決定が次の issue で出た。

- #105：組織のロール（`ORG_ADMIN`）を足す。招待キーを、1回限りと、期限内なら何回でも使えるものから選べるようにする
- #125：料金プランは作らない。手数料は、注文1回ごとの金額から引く
- #130：手数料は全店舗一律8%で、注文したときの率と額を注文に保存する。表示するだけで、請求・精算はしない
- #79：店舗の閉鎖（閉鎖中 → 閉鎖済み）。誰がキャンセルしたかを注文に記録する。閉鎖済みから90日後に店舗の連絡先を消す
- #109：組織の停止を「通常 → 受付停止中 → 停止」の3段階にする
- #16：運営による警告・警告解除・停止・再開を、履歴として残す
- #131〜#133：Stripe のテストモードで、カード決済と返金を扱う

v3 のテーブル定義と ER 図は、これらを反映していなかった。マイグレーション（#107）はテーブル定義から作るので、先に1つの構成にまとめ直す。

## Decision

ER 図・制約・今のテーブルとの対応は [../database-er.md](../database-er.md)、テーブル定義は [../database-v3-check/schema.sql](../database-v3-check/schema.sql) のとおりとする。テーブルは21個から27個になる。

### 1. Stripe のテストモードで、決済と返金を範囲に入れる

- 実際のお金は動かさない。Stripe のテストモードだけを使い、加盟店の審査は申し込まない（2026-11-12、ユーザー判断）
- 理由：決済サービスを入れると、返金などの決済まわりの処理を1か所にまとめられるため。今は支払方法を注文に記録するだけで、キャンセルしても返金の処理がなく、返金のルールも決められなかった
- 細かいルール（請求を確定する時点、在庫を確保する時点、返金する場面など）は、#131 の「決めること」がまだ決まっていない。テーブルは、#131 の採用候補（カードだけ、注文時に請求を確定、お会計1回で決済1つ、注文時に在庫を確保）に合わせた仮の形にする
- `payments`：お会計1回につき1行。`(cart_id, request_id)` を一意にして、二重の請求を DB が拒否する
- `stripe_events`：処理済みの通知を、通知の ID を主キーにして記録する。同じ通知の2回目は主キーの重複で止まり、在庫・通知・返金を二重に処理しない
- `refunds`：注文1件につき1行。`order_id` を一意にして、二重の返金を DB が拒否する。金額はその注文の合計で、1つの決済に対する一部返金になる
- 注文は、同じお会計の決済だけを指せる。返金は、その注文が支払われた決済だけを指せる（どちらも複合外部キー）
- 注文の状態に、支払い待ちの `PENDING_PAYMENT`（仮）を足す

### 2. 手数料の率と額を、注文に保存する（#130、#125）

- `orders.commission_rate_bp`（1万分率。800 = 8%）と `orders.commission_yen`（名前は仮）
- 理由：あとで率を変えても、過去の注文の手数料が変わらないようにするため
- 料金プランは作らないので、出店申請の `plan` の列をなくす

### 3. 店舗の閉鎖を、3つの列で表す（#79）

- `stores.closing_started_at`（閉鎖を始めた日時）、`closing_started_by`（`OWNER` か `ADMIN`）、`closed_at`（閉鎖済みになった日時）
- 営業中・閉鎖中・閉鎖済みは、この3つの列から決まる。閉鎖中を経ない閉鎖済みと、誰が始めたか分からない閉鎖は、DB が拒否する
- 閉鎖済みになってから90日後に、店舗の連絡先（担当者名・連絡用メール）を MySQL のイベントで消す。店舗・商品・在庫の行は消さない

### 4. 組織の停止を、3段階にする（#109）

- `organizations.suspension_started_at`（受付停止を始めた日時）を足す。通常・受付停止中・停止は、この列と `suspended` から決まる
- 理由：組織の行を1つ書き換えるだけで、配下のすべての店舗の新規注文の受付が止まるため
- 受付停止を経ない停止は、DB が拒否する
- 列の名前と形は #104 で決めることになっている。それまでは、店舗の閉鎖と同じ「始めた日時の列」の形にしておく

### 5. 誰がキャンセルしたかを、注文に記録する（#79）

- `orders.cancelled_by_member_id`。運営か店舗かは、その会員の種別で分かる
- 購入者のキャンセル申請の状態（`cancellation_status`）は、申請の状態だけを表す。運営がまとめてキャンセルしても、申請の状態は変わらない

### 6. 組織のロールを、組織への所属に持つ（#105）

- `organization_members.role`。値は `ORG_ADMIN`（仮名）か空
- 店舗の操作のロール（`store_members.role`）とは受け持つ操作が重ならないので、どちらが効くか決まらない、ということは起きない

### 7. 招待キーに上限回数を持ち、使った人を別のテーブルに記録する（#105）

- `store_invitations.max_uses`（1 = 1回限り、空 = 期限内なら何回でも）。使用日時と使用者の2列はなくす
- `store_invitation_uses`：キーを使った人を1人1行で残す。キーが使えるのは新規登録のときだけなので、1人につき1行までにする
- 上限回数を超えないことは、DB の制約では守れない。キーの行をロックしてから使用記録の件数を確かめる処理を、アプリケーションが行う

### 8. 警告・停止の履歴を、商品と店舗で別のテーブルに持つ（#16）

- `product_moderation_events` と `store_moderation_events`。列の形は同じにそろえる
- 「今、警告中か」は列で持たず、最新の履歴から求める
- 理由のない警告・停止は、DB が拒否する

## Alternatives

- 返金を、注文の列（返金の ID・金額・状態）として持つ：二重の返金を一意キーで止められず、Stripe の管理画面からの返金や、失敗した返金のやり直しを記録しにくい
- 注文に「返金済み」「一部返金済み」の状態の列を足す：返金の行と同じ事実を2か所に持つことになり、食い違う原因になる。注文ごとの返金の行から求める
- 決済の ID だけを注文に持ち、複合外部キーにしない：注文が別のお会計の決済を指す誤りを、DB が拒否できない
- 支払いが成功してから注文を作る（支払い待ちの注文を作らない）：支払い中にほかの人が同じ在庫を買えてしまう。#131 の採用候補は、注文時に在庫を確保する形
- 店舗の閉鎖を、状態の列1つ（営業中 / 閉鎖中 / 閉鎖済み）で持つ：閉鎖を始めた日時と閉鎖済みになった日時が別に要る（90日の判定に使う）ので、日時の列から状態を求める形にした（#79 の決定）
- 組織の受付停止を、店舗ごとの列で持つ：取り消しや再開のときに、店舗の状態を元に戻す手間が要る。受付停止中に作った店舗が止まらない（#109 の決定）
- 招待キーのテーブルに、使用回数の列だけを足す：何回でも使えるキーで誰が入ったかが残らず、キーが漏れたときに入った人を特定しにくい（#105 の決定）
- 店舗の担当のロールに `AREA_MANAGER` などの値を足す：店舗ごとの行に組織全体の権限を持たせることになり、行ごとに食い違うとどれが効くか決まらない（#105 の決定）
- 警告の履歴を1つのテーブルにして、対象の種別と ID の列で表す：対象の ID に外部キーを張れず、存在しない対象を DB が拒否できない（#16 の決定）
- 90日後の連絡先の削除を、アプリケーション側の定期処理で行う：定期処理を動かす仕組みを別に用意する必要がある（#79 の決定）

## Consequences

### ほかの決定・文書への影響

- #79 は「支払いはデモのままにし、返金の処理は作らない」と決めていた。決済を範囲に入れたので、運営がまとめてキャンセルするときも、キャンセルの承認と同じ返金の処理（#133）を呼ぶ
- AGENTS.md と `docs/functional-requirements.md` は「実決済は対象外」と書いている。#131 で、テストモードの決済を範囲に入れる書き方に直す（この記録では直していない）
- 閉鎖した店舗の連絡先を消すイベントは、MySQL の `event_scheduler` が `ON` のときだけ動く。イベントはマイグレーション（#107、#79）で作り、手作業で DB に入れない。イベントが失敗しても MySQL のエラーログにしか出ないので、確かめ方を #79 で決める
- Stripe の秘密鍵と、通知の署名の検証に使う秘密の値は、環境変数で渡す。DB、Git、ログ、テストの成果物には入れない（#132）
- 進める順番は [../database-v3-implementation-plan.md](../database-v3-implementation-plan.md) のとおり

### 確かめたこと（2026-11-12）

使い捨ての MySQL 8.0.46 を、開発用（3306）とは別のポート（33999）に一時的なデータフォルダーで立てて確かめた。開発用・E2E 用の DB には接続していない。試験の後、この MySQL は停止した。

- `schema.sql` で27テーブルとイベント1つを作成できた
- 160件を試し、すべて期待どおりだった（拒否されるべき操作83件がすべて拒否され、通るべき操作77件がすべて通った）。拒否は、どの制約で拒否されたかを結果に残して、別の理由で失敗していないことを確かめた
- 足した試験：招待キーの使用記録（1回限り・何回でも・取り消し）、組織のロール、組織の受付停止と再開、店舗の閉鎖と取り消し、お会計1回で決済1つ、支払い成功の通知と2回目の拒否、注文ごとの手数料、キャンセルの承認と返金、運営のまとめてのキャンセル、二重の返金の拒否、警告と停止の履歴、90日たった店舗の連絡先だけがイベントで消えること
- ER 図の列と、テーブル定義の列が一致することを照合した（27テーブル、209列）

### 確かめていないこと

- Stripe の API と通知そのもの。確かめたのは、通知を受けたときに DB で行う操作の SQL だけ
- アプリケーション（Spring Boot）からの動作、Flyway のマイグレーションとしての適用
- 同時実行（同じ在庫の同時購入、同じ招待キーの同時使用で上限回数を超えないこと、同じ注文への同時の返金の要求）
- 本番の MySQL（RDS）で `event_scheduler` を `ON` にしたときの動き
- Canvas の DB の変更

### まだ決まっていないこと

決まるまでは仮の形で進め、決まったら `schema.sql`・ER 図・マイグレーションを直す。
