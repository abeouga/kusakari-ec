# 運営の警告と、商品・店舗の停止の履歴（issue #16）

## Context

運営が商品・店舗に対してできる操作は、停止と再開だけだった。軽い問題でもすぐに停止するしかなく、出店者は前もって知ることも直すこともできなかった。特に店舗の停止は、購入者の画面から全商品が消え、出店者は商品・在庫・注文の操作ができなくなるのに、出店者へ通知していなかった。停止の理由と日時も DB に残っていなかった。

2026-11-12 に警告の流れと規則を決め、2026-11-13 に実装した。この記録は、その2つの決定を今の実装に合わせて1つにまとめたものである。

## Decision

### 警告と停止の関係

- 運営は、商品と店舗のどちらにも、理由を付けて「警告」できる。警告しても、商品の公開状態・店舗の利用状態は変わらない。購入者への表示も注文の受付も続く。
- 警告は停止の前に行ってもよい段階で、必須ではない。停止は警告をしていなくても実行できる。
- 期限は設けず、自動で停止する仕組みも作らない。停止するかどうかは運営が判断して手で行う。
- 警告を解除できるのは運営だけである。出店者が「対応済み」と報告する機能はない。商品を編集しても警告は解除されない。停止・再開しても警告は自動では解除されない。
- 警告中の対象にも、停止中の対象にも、もう一度警告できる。

### データ

- 履歴は、商品と店舗で別のテーブルに持つ（`product_moderation_events`・`store_moderation_events`、V1）。列の形は同じで、対象の ID（外部キー）、操作の種別（`WARN`・`CLEAR_WARNING`・`SUSPEND`・`RESUME`）、理由、操作した運営の会員 ID（外部キー）、日時を持つ。行は書き換えず、削除もしない。
- 「今、警告中か」は、警告と警告解除のうち最新の行が `WARN` かどうかで求める。`products`・`stores` に警告用の列は持たない。
- 停止の状態は対象の列（`products.suspended`・`stores.suspended`）に持つ。停止・再開では、その列の更新と履歴の行の追加を1つのトランザクションで行う。
- Java では操作の種別を共通の enum（`ModerationAction`）にし、2つのテーブルの Entity を同じ形にする。
- 理由は画面と API で500文字まで。警告と停止は必須（400 `REASON_REQUIRED`）、警告解除と再開は任意。
- 組織の停止は、この決定の対象に入れない（[店舗の閉鎖と組織の停止](2026-11-13-store-closure-organization-suspension.md)）。

### API

- 停止・再開：商品は `PUT /api/operator/products/{id}/moderation`（`suspended`・`reason`）、店舗は `PUT /api/operator/stores/{id}/enabled`（`enabled`・`reason`）。
- 警告・警告解除：`PUT /api/operator/{products|stores}/{id}/warning`（`warned`・`reason`）。
- 履歴：`GET /api/operator/{products|stores}/{id}/moderation-events`（新しい順、操作した運営の表示名つき）。
- どの操作も、応答は操作の後の状態（`{ "suspended", "warning" }`）。
- 運営の商品一覧（`GET /api/operator/products`）と店舗の応答（`StoreService.Profile`）に `warning` を入れる。店舗の応答は購入者にも返すので、`warning` は出店者と運営にだけ入れ、購入者・未ログインには null にする。
- 出店者の商品一覧のための `GET /api/seller/products/moderation?storeId=`（警告中か運営が停止している商品と、警告の理由）。商品の応答（`ProductView`）は購入者の画面・Canvas と共通なので、警告の項目を足さない。

### 操作の規則

- どの操作も、対象の行をロックしてから履歴に1行足し、出店者（組織のオーナーと、ロールが割り振られた担当者。`NotificationService.toStore`）に通知する。
- 停止中の停止・停止していない対象の再開・警告していない対象の警告解除は、何もしない（履歴も通知も足さない）。二重送信で履歴と通知が重ならないようにするため。警告は、警告中でも毎回1行足す。
- 閉鎖済みの店舗には、警告・停止・再開のどれもできない（409 `STORE_CLOSED`）。閉鎖中の店舗にはできる。

### 通知（EC-S11）

- 警告・警告解除・停止・再開のすべてを出店者へ通知する。`notifications` に種別の列は足さず、タイトルで区別する。本文は「対象の名前 / 理由」（理由がなければ名前だけ）。
  - 商品：「商品に運営から警告がありました」「商品への運営の警告が解除されました」「商品の公開を停止しました」「商品の公開停止を解除しました」
  - 店舗：「店舗に運営から警告がありました」「店舗への運営の警告が解除されました」「店舗の利用が停止されました」「店舗の利用停止が解除されました」
- 店舗が停止されても、出店者は通知（`/api/notifications`）を見られる。

### 画面

- 運営の商品管理（`/operator/products`）と店舗管理（`/operator/sellers`）に、共通の部品（`Moderation.jsx`）を置く。警告中のバッジと理由、「警告する」「警告を解除」、停止中なら通常の位置に「再開」、履歴（開いたときに読む）、停止していなければ「デンジャーエリア」に「停止」を出す。
- 停止・再開・警告・警告解除は、確認ダイアログで理由を入れてから確定する。理由が必須の操作で空のまま確定すると「理由を入力してください。」を出す。
- 出店者の店舗一覧（`/seller/stores`）と店舗情報の編集（`/seller/profile`）に、警告中のバッジと理由を出す。商品管理（`/seller/products`）には、一覧の上に「運営からの警告・停止」の欄（商品名・理由）を、各行に「警告中」「運営により公開停止中」のバッジを出す。一覧は25件ごとに分かれるので、ほかのページの商品の警告も上の欄で分かるようにする。
- 購入者の画面には何も出さない。

### 停止中の商品のお会計

- お会計は、店舗の行と組織の行の後、在庫の行の前に、商品の行を ID の順に共有ロック（`FOR SHARE`）で読み、運営が停止した商品があれば 409 `OUT_OF_STOCK` を返す。ロックしない読み取りだけでは、停止のコミットがお会計の最初の読み取りより後のとき、停止した商品の注文が通ることがあるため。
- ロックの順は「店舗 → 組織 → 商品 → 在庫」になる。商品の編集は「商品 → 在庫」、商品の停止は「商品」だけなので、輪にならない。

### ユースケース

- 警告は別のユースケースに切り出さず、EC-A10・EC-A11 の中の流れとして扱う（停止と同じ画面・同じ対象で、操作の前後の関係が強いため）。

## Alternatives

- 警告を経ないと通常の停止ができないようにし、すぐ止めるのはデンジャーエリアからだけにする：止める入口が2つになり、運営の判断が増える。重大な問題ではすぐ止めたいので、警告は任意の前段階にした。
- 期限を設け、期限切れで自動停止する：定期的に動く処理が新しく要り、運営が見ていないところで店舗の全商品が消えることになる。
- 出店者が「対応済み」と報告し、運営が確かめて解除する：出店者の画面と状態が1つ増える。通知を見て直してもらい、運営が確かめて解除する形で足りる。
- 商品を編集したら警告を自動で解除する：編集が問題の是正とは限らず、店舗の警告にも当てはまらない。
- 停止したら警告を自動で解除する：解除は運営だけ、という規則と合わない。
- 最新の警告だけを対象の列に持ち、再警告で上書きする：何回、何の理由で警告したかが残らず、停止の判断の材料にならない。
- 商品と店舗の履歴を1つのテーブルにし、`target_type` と `target_id` で対象を表す：`target_id` に外部キーを張れず、`products.id`（文字列）と `stores.id`（数値）で型も違う。
- 1つのテーブルに `product_id` と `store_id` の両方を持ち、CHECK でどちらか一方だけにする：片方の列が常に空になり、対象が増えるたびに列と CHECK を足す必要がある。
- `products`・`stores` に「警告中」の列を足す：履歴と同じことを2か所に持つことになり、食い違う原因になる。
- `notifications` に種別の列を足す：通知の画面は種別で絞り込んでおらず、今ある通知を作る処理もすべて直すことになる。
- 操作の種別を受ける1つの API（`POST .../moderation-events` に `action`）にする：停止の API を使っている画面・試験・手順をすべて変えることになる。停止・再開の意味は変わらないので、停止の API を残し、警告だけを足した。
- 同じ操作を2回送ったら 409 にする：画面は操作の後に最新の状態を読み直すので、何もしない扱いで足りる。
- 商品の応答（`ProductView`）に警告を足す：購入者の画面と Canvas の照会も同じ応答を使うので、購入者に出さない決定と合わない。
- お会計で商品の行を排他ロックする：お会計どうしが同じ商品で待ち合うことになる。停止との関係だけを見ればよいので、共有ロックにした。
- 在庫の行のロックの後に商品の行を読む：商品の編集（商品 → 在庫）と逆の順になり、デッドロックする。

## Consequences

- 停止の理由と日時が、商品・店舗とも履歴に残る。
- 店舗の停止（`PUT /api/operator/stores/{id}/enabled` の `enabled:false`）は理由が必須である。`reason` の項目自体は、ほかの API と同じく、欠けると 400 `INVALID_INPUT`。
- ユースケースの記述（EC-A10・A11・S11）は、このリポジトリではなく kusakari-document にある。
- 確かめていないこと：本番の MySQL（RDS）での動き。お会計と停止の同時実行は、E2E で停止と同じロックを持つトランザクションを DB に直接作って確かめている（運営の API そのものとの同時実行ではない）。
