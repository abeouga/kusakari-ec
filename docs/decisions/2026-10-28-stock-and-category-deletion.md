# 在庫数の期待値照合とカテゴリの削除済み表示

## Context

- EC-S05 5b では、在庫数を表示した後に注文の引き当てやキャンセルの戻しで在庫が変わった場合、更新せずに最新の在庫数を表示して再確認を求める。従来の在庫画面は商品全体を `PUT /api/products/{id}` で送り、在庫を絶対値で確認なしに上書きしていた。表示後に変わった商品名・価格も古い内容で上書きされうる。商品編集フォームの「選択店舗の在庫」も同じ方法で上書きしていた。
- EC-A09 では商品が紐づくカテゴリの削除を拒否する。従来は削除済み商品も数えたため、削除済み商品だけが残ったカテゴリは永久に削除できなかった。`products.category` は `categories(name)` への外部キー（V10）で NOT NULL のため、参照が残る行は物理削除できない。
- 出店者の店舗選択は初期値が店舗1固定で、全店舗が選択肢に出ていた。サーバーは `AuthService.requireSeller` で所属店舗以外を403にするが、画面は所属店舗を開けなかった。

## Decision

- 在庫だけを更新する `PUT /api/seller/products/{id}/stock` `{storeId, expectedStock, stock}` を追加する。店舗の在庫行を注文・キャンセルと同じ悲観ロックで取得し、`expectedStock` と現在の数量が異なれば 409 `STOCK_CHANGED`（現在の在庫数をメッセージに含む）で保存しない。権限は販売状態の変更と同じく店舗単位（`requireSeller(storeId)`）とする。
- `PUT /api/products/{id}` は任意の `expectedStock` を受け付ける。省略時は `stock` を期待値とみなすため、古い商品全体を再送しても在庫は上書きされない。照合は商品情報を変更する前に行う。
- 画面は失敗時に一覧を再取得し、変更前の在庫数を最新値に更新したうえで入力値を残して再確認を求める。
- カテゴリは `categories.deleted_at`（V13、NULL 許容の列追加のみ）を追加する。「使用中」は、無効化されておらず、少なくとも1店舗で `DELETED` 以外の在庫行を持つ（または在庫行がない）商品とする。削除済み商品だけが参照する場合は `deleted_at` を設定して一覧・商品登録の選択肢から外し、参照がなければ従来どおり行を削除する。同名を追加すると行を復元する。カテゴリ削除は行を排他ロック、商品保存は共有ロックで取得し、削除と商品登録が並行しても使用中の判定を誤らない。
- 出店者の店舗選択肢はセッションの `storeIds`（`AuthMember.storeId`）だけとし、初期値もそれにする。運営者は全店舗を選べる。

## Alternatives

- 商品全体の PUT に `revision` を持たせる楽観ロック：商品表に版番号がなく、在庫は店舗別の行のため、在庫だけの照合には過剰でスキーマ変更も増える。
- 在庫の差分（増減量）を送る：「表示後に変わっていたら再確認」というUCに合わず、意図しない合計値になりうる。
- 削除済み商品のカテゴリを NULL や別カテゴリへ移す：NOT NULL 制約の変更や既存データの書き換えになり、注文・庭から参照される商品の記録を変えるため採用しない。
- 外部キーを外す：アクティブな商品のカテゴリ整合性を失うため採用しない。

## Consequences

- 在庫を変えたい API 利用者は現在値を `expectedStock` で送る必要がある。古い在庫を含む商品全体の再送は 409 になる。
- 削除済みのカテゴリ名は行として残る。復元時は削除済み商品も同じカテゴリ名を指す。
- V13 は列追加だけで既存行を変更しない。
