# 店舗側アカウントの作り直しで使う DB の構成（v3）を決める（issue #126、#104）

## Context

店舗側アカウントの作り直し（#103）では、購入用のアカウントと店舗側のアカウントを分け、店舗側を「組織 → 店舗 → 店舗ごとの担当者」にする。既存のデータは移行せず、DB を初期化して作り直す（#102 決定事項2）。

テーブル構成の決定は #104 のコメントに改定が重なっていた（対応策1〜9、対応策4の改定、在庫の持ち方の改定、2026-11-11 の訂正）。2026-11-10 に書いた記録と ER 図の下書きは、その途中の内容のままで、次の決定が入っていなかった。

- 商品の持ち主を、組織ではなく店舗にする（#104 対応策4の改定）
- 在庫を商品と1対1にする（#122）
- カートの店舗と、発送用の列をなくす（#104 対応策9、#119）
- 申請中の法人用アカウントの種別を足す（#109）

このままマイグレーション（#107）を作ると、古い図と新しい決定のどちらに合わせるかで食い違う。そこで、決定を1つの設計案（v3）にまとめ直し、採用するかを #126 で決めた。

## Decision

ER 図・制約・今のテーブルとの対応は [../database-er.md](../database-er.md)、テーブル定義は [../database-v3-check/schema.sql](../database-v3-check/schema.sql) のとおりとする。

### これまでの issue の決定から引き継ぐ方針

- 種別は会員の列1つ（`members.account_type`）で決める。購入者・申請中の法人用アカウント・オーナー・子アカウント・運営の5種類
- 店舗側は「組織 → 店舗 → 店舗ごとの担当者」。ロール（`MANAGER` / `STAFF`）は店舗の担当（`store_members`）にだけ持つ。ロール未割り当ては、ロールが空の担当で表す
- オーナーは組織に1人で、所属（`organization_members`）や担当（`store_members`）には入れない
- してはいけない組み合わせは、DB の制約で拒否する。トリガーは使わない
- 商品は1つの店舗に属し、在庫は商品と1対1。受取店舗は商品で決まり、購入者は店舗を選ばない
- 発送用の列は作らない（将来は #120 で設計し直す）
- 既存のデータは移行しない。互換性は考えない

### これまでの決定から変えた9点（2026-11-11 にすべて採用）

| 番号 | 決定 | それまでの決定 | 理由 |
| --- | --- | --- | --- |
| 1 | 会員のテーブル名を `members` にする | `auth_members` を残す（#104 対応策1） | 残す理由が「書き換えが増える」だけで、互換性が不要になったため |
| 2 | 出店申請のテーブル名を `organization_applications` にする | `store_applications` に列を足す | 申請の対象が店舗ではなく組織になったため（#109） |
| 3 | 店舗の公開を、オーナーの公開（`published`）と運営の停止（`suspended`）の2つの列に分ける | `enabled` 1つで、初期値を非公開にする | 列が1つだと、運営が停止を解除したときに、オーナーがまだ公開していない店舗まで公開されるため |
| 4 | 組織の停止を `suspended` にする | `enabled` | 店舗・商品と名前の向きをそろえるため |
| 5 | 受取連絡先と支払方法を `orders` に入れ、`order_details` を作らない。金額は `total_yen` だけにする | `order_details` を4列にして残す（#104 対応策9） | 注文と必ず1対1で、残る列が4つだけのため。送料もないため |
| 6 | 店舗の緯度経度を空（NULL）にできるようにする。片方だけの入力は DB が拒否する | 未決定（緯度0・経度0を「位置なし」の印にする案が残っていた） | 位置なしを緯度0・経度0で表すと、店舗の案内で距離が約14,000 km と計算されるため |
| 7 | 商品番号の一意を、店舗の中だけにする（`(store_id, sku)`） | 全体で一意 | 同じ品種を、店舗ごとに別の商品として登録するため |
| 8 | 会員に、メール確認の日時（`email_verified_at`）と作成日時（`created_at`）の列を足す | 列の指定なし | メール確認まで進まなかった法人用アカウントを判定できるようにするため |
| 9 | 招待キーのテーブルに組織の列を持たせない | 2026-11-10 の図にあった | 店舗からたどれるため |

8番について：列は足すが、アカウントを自動で削除する処理は実装しない。削除の扱いは #109 で決める。

### 今の定義をそのまま引き継ぐもの

設計案の試験用の DDL では省いていたが、変える決定がないので、今の定義のまま持つ。

- `products` の説明・サイズ・育て方などの列（`latin_name`、`description`、`size_label`、`care`、`unit`、`image_url`、`badge`、`source` 系、`nursery_*`、`sunlight`、`use_case`、`care_level`、`min_temperature_c`、`heat_tolerant`、`drought_tolerant`、`age_years`、`height_cm`、`pot_diameter_cm`、`family_name`、`flowering_description`、`seasonal_care`、`style_description`、`published_at`）と、価格が1円以上・育てやすさが1〜3の CHECK
- `product_media`（画像の本体）、`material_products`（素材コードと商品の対応）
- `orders.request_revision`、`orders.cart_id` から `carts` への外部キー、キャンセルの列の初期値（`cancellation_status = 'NONE'`）
- `cart_items.quantity` が1〜99の CHECK

## Alternatives

- #104 のコメントの決定を、名前も列も変えずにマイグレーションにする：改定が重なっていて、どれが最新かをコメントの順に追わないと分からない。1つの設計案にまとめ直した
- カートのテーブルをなくし、会員に直接明細を持たせる：注文と庭の買い物リストがカートの ID を使っていて、得るものが少ない
- 商品を組織のものにし、店舗ごとの在庫を持つ（2026-11-10 の図）：受取店舗を購入者が選ぶ必要が出て、#70 の「商品の店舗で受け取る」と食い違う。#104 対応策4の改定で採用しなかった
- 店舗の公開を `enabled` 1つで持つ：上の3番の理由で採用しなかった
- 緯度0・経度0を「位置なし」の印にする：上の6番の理由で採用しなかった
- `organizations.owner_account_type` の値を、組織寄りの名前にする：この列は有効・無効の列ではなく、複合外部キーのための固定値で、`members.account_type` の値と同じでなければ外部キーが成り立たない。変えるなら会員の種別の名前ごと変えることになり、`SHOP_OWNER`・`SHOP_STAFF`・`SHOP_OWNER_APPLICANT` の揃いが崩れるため、変えない

## Consequences

### 失われるもの・元に戻せないこと

- DB を初期化するので、EC の今の会員・店舗・商品・注文が失われる。Canvas の庭・写真・画像生成の履歴も、Canvas 側の初期化（abeouga/kusakari-canvas#63）で失われる
- EC と Canvas の片方だけを初期化すると、庭の持ち主（EC の会員 ID）と、買い物リストが持つ庭 ID が食い違う。2つの初期化は続けて行う（#113）
- 初期化の対象を間違えると、別のプロジェクトや開発者のデータが消える。対象を特定できないときは何も消さずに止める（#106）

### 実装への影響

- マイグレーションはまだない。#107 で、Flyway の V1〜V15 を、`schema.sql` から作ったテーブル定義とサンプルデータにまとめ直す
- #107 の後、会員と認可（#108）・出店申請（#109）・商品と在庫（#110、#122）・招待キー（#111）・カートと注文（#119）が終わるまで、統合ブランチで一部の画面が動かない。作業は統合ブランチ `feature/shop-organization` の中だけで進め、main には入れない
- テーブル名と列名が変わる（[../database-er.md](../database-er.md) の5章）。#104・#107・#109・#119・#122 の本文は古い名前で書かれているので、読むときはこの対応表で読み替える
- 進める順番は [../database-v3-implementation-plan.md](../database-v3-implementation-plan.md) のとおり

### 確かめたこと（2026-11-11）

使い捨ての MySQL 8.0.46 を、開発用（3306）とは別のポート（33999）に一時的なデータフォルダーで立てて確かめた。開発用・E2E 用の DB には接続していない。試験の後、この MySQL は停止した。

- `schema.sql` で21テーブルを作成できた
- 90件を試し、すべて期待どおりだった（拒否されるべき操作50件がすべて拒否され、通るべき操作40件がすべて通った）。拒否は、どの制約で拒否されたかを結果に残して、別の理由で失敗していないことを確かめた
- 一覧は [../database-v3-check/cases.txt](../database-v3-check/cases.txt)、結果は [../database-v3-check/result.txt](../database-v3-check/result.txt)

### 確かめていないこと

- アプリケーション（Spring Boot）からの動作。確かめたのは SQL だけ
- Flyway のマイグレーションとしての適用
- 同時実行（同じ在庫の同時購入、同じ招待キーの同時使用）。在庫と招待キーの行をロックしてから更新し、#110・#111 の E2E で確かめる
- Canvas の DB の変更

### まだ決まっていないこと

決まるまでは仮の形で進め、決まったら `schema.sql`・ER 図・マイグレーションを直す（main に入れる前なので直せる）。

| 項目 | 仮の形 | 決める場所 |
| --- | --- | --- |
| 招待キーは1回限りか、期限内なら何人でも使えるか | 1回限り | #105 |
| 料金プランを組織と店舗のどちらに持つか | 申請の行に残す | #125 |
| 同じ品種の商品をジャンルでまとめて表示するか | 入れない | issue はまだない |
| 素材コードと商品の対応のテーブルを残すか | 残す | #119 |
| 初期化のときに、認証基盤に残ったユーザーも消すか | 消さず、初回ログインで会員を作る | #108 |
| 店舗の閉鎖の状態 | 入れない | #79 |
| 運営の警告の記録 | 入れない | #16 |
| メール確認まで進まなかった法人用アカウントの削除 | 自動では削除しない（列だけ持つ） | #109 |
