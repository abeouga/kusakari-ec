# 販売手数料の表示と、閉鎖した店舗の注文実績（#130）

## Context

#130 の決定（2026-11-12）で、販売手数料は全店舗一律8%、注文ごとに `floor(合計 × 率)`、注文したときの率と額を注文に保存し、表示だけにする（請求・精算・Stripe での差し引きはしない。[残りの決定](2026-11-12-remaining-decisions.md) 1-13）と決めた。率と額は DB 構成 v3 の `orders.commission_rate_bp`・`orders.commission_yen` に入り、お会計（`CheckoutService`）で保存していたが、どの画面にも出していなかった。

閉鎖した店舗（`stores.closed_at` あり）は、店長・スタッフが担当から外れる（#79）。閉鎖後も、オーナー・ORG_ADMIN・運営が注文実績を読み取り専用で、期限なく見られるようにすると決めていた。#130 には、次の5つが未決定で残っていた。

1. 運営が店舗ごとの注文実績を開く画面の場所
2. 2つの列と「できること」の正式な名前
3. 率を変える手段
4. 営業中の店舗の注文実績を、オーナー・ORG_ADMIN が見られるか
5. 注文が後からキャンセルされたとき、保存した手数料の額を0に書き換えるか、残して表示で0にするか

閉鎖の操作（#79）はまだない。閉鎖した店舗は `closed_at` を読むだけで扱う。

## Decision

### 未決定だった5項目

| # | 決定 | 理由 |
| --- | --- | --- |
| 1 | 運営の「店舗管理」（`/operator/sellers`）の各店舗の「注文実績を見る」から、`/operator/stores/{id}/sales` を開く | 運営が店舗を探す画面が店舗管理なので、店舗ごとの実績もそこから開く。全注文管理（`/operator/orders`）にも注文ごとの手数料と合計を出す |
| 2 | 列は `commission_rate_bp`・`commission_yen` のまま。「できること」は `VIEW_STORE_SALES`（営業中・閉鎖中の店舗）と `VIEW_CLOSED_STORE_SALES`（閉鎖済みの店舗） | 列は V1 に入っていて、名前を変える利点がない |
| 3 | 設定ファイルだけ（`kusakari.ec.commission-rate-bp`、既定 800） | 料金プランを作らない（#125）ので、運営の画面で変える必要がない |
| 4 | 営業中の店舗は、オーナー・MANAGER・STAFF・運営が見られる。ORG_ADMIN は、その店舗のロールがあるときだけ（ロールのない店舗では人事の画面だけ。残りの決定 2-5） | 今の注文の画面（`requireSeller`）と同じ範囲にし、2-5 と食い違わないようにする |
| 5 | 保存した額は残し、表示のときにキャンセルの注文を「手数料なし」（0円）として扱う | 注文した時点の記録を書き換えない。キャンセルの理由や時点にかかわらず、表示の規則1つで済む |

### 誰が見られるか（対応表）

判定は `StoreCapabilityPolicy`（`backend/src/main/java/jp/kusakari/ec/auth/StoreCapabilityPolicy.java`）の表1か所で行う。ロールを足すときは、立場と表を直すだけにする。

| できること | オーナー | ORG_ADMIN | MANAGER | STAFF | 運営 |
| --- | --- | --- | --- | --- | --- |
| `VIEW_STORE_SALES`（営業中・閉鎖中） | ○ | × | ○ | ○ | ○ |
| `VIEW_CLOSED_STORE_SALES`（閉鎖済み） | ○ | ○ | × | × | ○ |

- 運営が停止した営業中の店舗は、ほかの操作と同じく運営だけが見られる。閉鎖済みの店舗は、停止していても表のとおり。
- 閉鎖中（`closing_started_at` あり、`closed_at` なし）は営業中と同じ扱い。
- 見られない店舗は 403。どの画面も読み取りだけで、注文を変える操作はない。

### 手数料の表示

- 注文ごとに、注文したときの率・手数料・差引額（合計 − 手数料）を出す。率の設定を変えても、過去の注文は保存した値のまま出る。
- 合計（注文金額・販売手数料・差引額）は、キャンセルと支払い待ち（`PENDING_PAYMENT`）を除いた注文で求める。支払い待ちは、支払われるまで売上として数えない（30分以内に受付か取り消しになる）。
- 店舗・運営向けの注文の応答（`GET /api/seller/orders`、`GET /api/seller/orders/{id}`、`GET /api/operator/orders` など）に `sales`（`commissionRateBp`・`commissionYen`・`netYen`・`counted`）を足した。購入者向けの応答では null。

### API と画面

- `GET /api/seller/sales/stores`：注文実績を見られる店舗（閉鎖済みは `closedAt` つき）。運営には全店舗。
- `GET /api/seller/stores/{storeId}/sales`、`GET /api/operator/stores/{storeId}/sales`：`SalesReport`（店舗名、`closedAt`、注文1件を1行の `orders`、`totals`）。1つの処理（`SalesReportService`）から返し、エクスポートを作るときは同じ一覧を出す。
- `/seller/sales`：上の「管理する店舗」で選んだ店舗の実績を出す。閉鎖した店舗は「表示する店舗」で選ぶ。出店者画面の店舗の候補（`GET /api/seller/stores`）に閉鎖した店舗が出なくなっても（#79）、ここから選べる。閉鎖した店舗には「閉鎖済み」と、読み取り専用である旨を出す。

## Alternatives

- 運営の店舗ごとの実績を全注文管理の絞り込みにする：全注文管理は受け渡しの状態を見る画面で、店舗の合計を出す場所ではない。店舗管理から開く形にした。
- 表示のときに今の率で計算する：率を変えると過去の実績が書き換わって見える（#130 決定8で不採用）。
- キャンセルの承認で `commission_yen` を0に書き換える：注文時の記録が消え、返金や閉鎖のまとめてキャンセルなど、キャンセルする処理ごとに書き換えが要る。
- ORG_ADMIN に営業中の全店舗の実績を見せる：残りの決定 2-5（ロールのない店舗では人事の画面だけ）と食い違う。閉鎖済みの店舗は担当者がいなくなるので、組織全体を見る立場として ORG_ADMIN に見せる。
- 閉鎖した店舗を出店者画面の店舗の候補に残して選ばせる：閉鎖した店舗で商品管理などの画面を開けてしまう。閉鎖の扱いは #79 で決めるので、実績の画面だけで選べる形にした。
- 支払い待ちも合計に含める（今までの「キャンセル以外」）：まだ支払われていない注文を売上と手数料に数えることになる。
- 判定を `AuthService.requireSeller` に閉鎖の分岐として足す：ロール名を判定の処理に並べることになり、ロールを足すときに探して直す箇所が増える（#130 決定2）。

## Consequences

- 出店者の注文実績の応答が、注文の一覧（`GET /api/seller/orders`）から `SalesReport` に変わった。画面の件数の表示に「支払い待ち」を足した。
- 閉鎖した店舗の注文実績以外の操作（受け渡し・キャンセルへの回答・商品）を閉鎖後に止めるかは、#79 で扱う。今の `requireSeller` は `closed_at` を見ないので、オーナーは閉鎖した店舗の受け渡しの画面も開ける。
- 率の設定を変えて API を起動し直す試験は行っていない。E2E は、注文に保存した率と額を DB で別の値（10%）にして、画面が保存した値を出すことを確かめた。
- E2E（`e2e/business-commission.spec.js`）は、閉鎖を DB で `closed_at` を入れて作る。#79 の閉鎖の操作ができたら、操作で閉鎖する形に直す。
