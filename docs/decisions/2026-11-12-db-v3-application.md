# 新しい DB 構成（v3）へ、マイグレーションとアプリを同時に切り替える

## Context

2026-11-11・12 に、27テーブルの新しい DB 構成（v3）を決めました（[構成の記録](2026-11-11-shop-organization-db-v3.md)、[決済・閉鎖・ロールの追加](2026-11-12-db-v3-payments-closure-roles.md)、[ER 図](../database-er.md)）。この時点では、構成は文書と検証用の SQL（`docs/database-v3-check/`）だけにあり、アプリは旧構成（Flyway V1〜V15）で動いていました。

API は起動時に、エンティティとテーブルが合っているかを確かめます（`spring.jpa.hibernate.ddl-auto=validate`）。そのため、マイグレーションだけを先に置き換えると、API が起動しなくなります。#107（マイグレーション）と、#108・#109・#110・#119・#122 のうち起動と基本の流れに要る部分を、1つの変更にまとめました。

## Decision

### マイグレーション

- 旧 V1〜V15 を削除し、`V1__schema.sql`（27テーブル）と `V2__sample_data.sql`（サンプルの組織1つ・店舗3つ・カテゴリー5つ・商品14件・在庫・材料の対応16件）に置き換えます。既存のデータは移行しません（#102 決定事項2）。
- 旧構成の DB は、Flyway の履歴が合わないため、そのままでは起動しません。`DB-reset.bat`（[手順](../database-reset.md)）で初期化します。
- サンプルの組織にはオーナーがいません。開発では `scripts/set-member-role.ps1 -Role SHOP_OWNER -OrganizationId 1` でオーナーを付けます（[会員の種別とロールの値](../member-roles.md)）。
- サンプルの商品は、1商品1店舗に合わせて3つの店舗に割り当てました。店舗1：オリーブ・ラベンダー・ローズマリー・モンステラ。店舗2：Canvas モデル対応の4件。店舗3：庭のデモ用の6件。旧構成では同じ商品が複数の店舗に在庫を持てましたが、その形はなくなります。
- 閉鎖した店舗の連絡先を消すイベント（`ev_stores_clear_closed_contacts`）は、マイグレーションに入れません。`CREATE EVENT` には、アプリ用の DB ユーザーに EVENT 権限が要りますが、既存の PC ではセットアップが権限を付け直せないためです。定義は `docs/database-v3-check/store-closure-event.sql` に分け、閉鎖の実装（#79）でマイグレーションに入れます。

### 会員と認可

- 会員の権限は、`members.account_type`（5種）と、店舗ごとのロール（`store_members.role`）で決めます。オーナーは自分の組織の全店舗、担当者はロールの付いた店舗、運営は全店舗を操作できます。
- ログイン情報の API（`GET /api/auth/me`）は、`role` の代わりに `accountType`・`organizationId`・`storeIds` を返します。
- 新規登録に「企業様向け」の選択を足しました。選ぶと、出店を申請できる会員（`SHOP_OWNER_APPLICANT`）として作ります。
- 商品の登録・編集・削除、店舗情報の編集、キャンセル申請への回答は、オーナーか `MANAGER`。商品の公開・非公開、在庫、注文の受け渡しは `STAFF` 以上。商品の削除だけは、公開状態を変える API から行っても `MANAGER` 以上です（`STAFF` が別の API から削除できないようにするため）。

### 出店申請と店舗

- 申請できるのは `SHOP_OWNER_APPLICANT` だけです。承認すると、申請者が `SHOP_OWNER` になり、組織ができます。店舗は作りません。
- 申請は、1人につき「今の申請」と「前回の申請」の2行までです。再申請すると、前々回の行を消します。審査中の申請は取り下げられます。プランの項目はなくしました（#125）。
- オーナーは、審査なしで店舗を作ります（`POST /api/seller/stores`）。作った直後は非公開で、オーナーが公開します（`PUT /api/seller/stores/{id}/published`）。運営の停止（`suspended`）とは別の列なので、停止を解除しても、非公開の店舗は公開されません。

### 商品・カート・注文

- 商品は1つの店舗に属し、在庫と公開状態は商品ごとに1行です。`products.active` はなくなり、削除は在庫の公開状態 `DELETED` で表します。商品番号は店舗の中で一意です。
- 購入者に見える商品は、「店舗が公開・未停止・未閉鎖」「店舗の組織が受付停止でない」「商品が運営に停止されていない」「在庫の公開状態が `PUBLISHED`」をすべて満たすものです。`GET /api/products` は、`storeId` を省くと全店舗の見える商品を返します。
- カートは店舗を持ちません。受取店舗は商品の店舗です。`PUT /api/cart/store` と、カート・注文の送料・配送先の項目を削除しました。
- お会計は、今までどおり受取店舗ごとに注文を1件作ります。開いていない店舗の商品が1つでもあれば、どの注文も作りません。
- 注文に、手数料の率と額を保存します。率は設定値 `kusakari.ec.commission-rate-bp`（既定 800 ＝ 8%）、額は合計に率を掛けて切り捨てます（#130）。画面にはまだ出しません。
- 決済はまだつないでいません。注文は今までどおり受付済み（`ACCEPTED`）で作り、`payment_id` は空です（#131〜#133）。

### 開発用のスクリプトと試験

- `scripts/set-member-role.ps1` を、`ADMIN` / `SHOP_OWNER` / `SHOP_STAFF` を付ける形に作り直しました。
- `scripts/manage_accounts.py` は、運営のアカウントを準備するだけにしました。持ち主のいない商品を出店者に結び付ける処理は、商品が必ず店舗に属するようになったため不要です。
- 出店承認を取り消すスクリプト（`scripts/revert_store_approval.py`）とその試験は削除しました。承認で店舗を作らなくなり、前提が成り立たないためです。
- E2E の準備（`prepareMember`）の `'SELLER'` は、「サンプルの店舗1の `MANAGER` の担当者」を作ります。

## Alternatives

- **旧マイグレーションの後ろに V16 以降を足して移行する**：採用しません。既存のデータを移行しないと決めていて（#102）、15本の履歴を残す理由がないためです。
- **マイグレーションだけを先にマージする**：採用しません。統合ブランチの API が起動しなくなるためです。
- **`products.active` を残す**：採用しません。公開状態と二重になり、どちらが正しいかが分からなくなるためです（#122）。
- **カートの「閲覧中の店舗」を残して、商品一覧の絞り込みに使う**：採用しません。受取店舗と混同されるためです（#104 対応策9）。
- **イベントをマイグレーションに入れ、セットアップで EVENT 権限を付ける**：今回は採用しません。旧 DB を持つ PC では、セットアップが履歴の検証で止まり、権限を付け直す所まで進まないためです。

## Consequences

- 開発用・E2E 用の DB は、EC と Canvas の両方を初期化する必要があります。片方だけを初期化すると、庭の持ち主と、EC の買い物リストが持つ庭の ID が食い違います。
- Canvas は、商品一覧と AI の候補を全店舗の商品から取るように変えました（abeouga/kusakari-canvas#64・#65 の一部）。
- 次のものは、この変更に含めていません。
  - 店舗の招待キーと、担当者のロールの割り振りの画面（#111）。担当者は、開発用のスクリプトでだけ作れます。
  - 店舗側のアカウントで買い物をさせない制限と、Canvas を購入者だけにする制限（#108、abeouga/kusakari-canvas#64）。
  - 運営による組織の停止の操作と、停止された組織の商品をカートから外す処理（#109、#119）。DB の列と「見える」の判定だけ入っています。
  - 店舗の閉鎖（#79）、停止の前の警告（#16）、手数料の表示と閉鎖した店舗の注文実績（#130）、Stripe（#131〜#133）。
  - 運営による商品の停止の履歴（`product_moderation_events`）への記録。今は `products.suspended` を変えるだけです。
  - Canvas で、買えなくなった商品の配置を庭から外す処理（abeouga/kusakari-canvas#65）。
- お会計は、商品の行をロックしません（店舗 → 在庫の順でロックします）。運営による商品の停止とお会計が同時に起きると、停止の直後の注文が1件通ることがあります。
- `GET /api/stores/{id}` は、未ログインでも非公開の店舗を返します。旧構成からの動きのままで、公開の判定を入れるかは未決定です。
