# 店舗側アカウントの作り直し（#103）の残りの未決定事項を決める（決済・権限・店舗と組織・Canvas）

## Context

店舗側アカウントの作り直し（#103）の第1段階として、DB 構成 v3 を main に入れた（[2026-11-12-db-v3-application.md](2026-11-12-db-v3-application.md)、[2026-11-12-db-v3-payments-closure-roles.md](2026-11-12-db-v3-payments-closure-roles.md)）。その時点で、残りの issue（#79・#105・#108・#109・#111・#112・#119・#131〜#133・canvas#64・canvas#65・canvas#69 など）に、決まっていない事項がまとまって残っていた。issue の記述と実装が食い違っているもの（STAFF の価格変更、ロール未割り当ての GET、14日の自動削除など）もあった。

2026-11-12 に、ユーザーが「#103 の残りを、既定の案（各 issue で有力とした案）で決めて記録して進める」を選んだ。この記録は、そのとき決めた全項目と、採らなかった案と理由をまとめる。項目ごとに Decision と Alternatives を並べ、最後に全体の Consequences を書く。

## Decision

### 0. 全体

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| DB の変更の仕方 | main に入った `V1__schema.sql`・`V2__sample_data.sql` を書き換えず、V3 以降のマイグレーションを足す | V1 を書き換えると、すべての PC で DB の作り直しが要るため |
| 進め方 | 区切りごとに、統合ブランチ（`feature/shop-organization`）から main へマージする | 2026-11-12 の #137 と同じ進め方。大きな差分を一度に入れない |

### 1. 決済（#131、#132、#133）

範囲：Stripe のテストモードの決済を範囲に入れる。実際のお金は動かさない（テスト用の鍵だけを使い、加盟店の審査は申し込まない）。

| # | 項目 | 決定 |
| --- | --- | --- |
| 1-1 | 支払方法 | カード（Stripe テストモード、Payment Element）と店頭払いの2つ。PayPay・楽天ペイは消す。店頭払いは決済を作らず、注文を作った時点で `ACCEPTED`（今と同じ） |
| 1-2 | 請求の確定 | 注文時に確定する（`capture_method=automatic`） |
| 1-3 | 単位 | お会計1回で PaymentIntent 1つ。店舗ごとの注文は複数のまま。店舗ごとのキャンセルは一部返金 |
| 1-4 | 在庫と支払われなかった注文 | カードの注文は `PENDING_PAYMENT` で作った時点で在庫を確保する。30分以内に支払いが成功しなければ取り消して在庫を戻す。取り消しは `payment_intent.payment_failed` の Webhook と、アプリ内の定期処理（1分ごとに、時間を過ぎた `PENDING_PAYMENT` を取り消す）の両方で行う。データは消さず状態を変えるだけ |
| 1-5 | 状態 | 注文：`PENDING_PAYMENT` → `ACCEPTED` → `READY` → `COMPLETED`、`CANCELLED`。決済：`PENDING`/`SUCCEEDED`/`FAILED`/`EXPIRED`。返金：`REQUESTED`/`SUCCEEDED`/`FAILED`。DB の今の値のまま名前は変えない。「返金済み」は返金の行から求める |
| 1-6 | 返金する場面 | キャンセル申請の承認と、店舗の閉鎖・組織の停止によるまとめてキャンセル。カードで支払い済みの注文だけを返金する（店頭払いは返金なし） |
| 1-7 | 受け取り後の返品 | 扱わない。必要なら Stripe の管理画面から返金し、Webhook で結果を反映する |
| 1-8 | 受け取りに来なかった注文 | 自動の処理は作らない。店舗がキャンセルする操作も作らない。運営の画面で状態を見られるだけ |
| 1-9 | 返金を実行できる人 | キャンセル申請を承認できる人（オーナーか MANAGER）と、まとめてキャンセルを行う運営。返金はキャンセルの承認に伴って自動で行い、単独の返金ボタンは作らない |
| 1-10 | 返金時の在庫 | 受け取り前のキャンセルは在庫を戻す（今と同じ） |
| 1-11 | 一部の商品だけの返金 | できない（注文1件に返金1行） |
| 1-12 | 戻らない決済手数料 | Kusakari（運営）が負担する扱い。アプリでは記録しない |
| 1-13 | 手数料8%の差し引き（Stripe Connect） | 入れない。#130 は表示だけ |
| 1-14 | チャージバック | `charge.dispute.created` を受けて記録するだけ（`stripe_events` に残す） |
| 1-15 | 鍵の確認 | `STRIPE_SECRET_KEY` が `sk_test_` か `rk_test_`（テストモードの制限付きキー。2026-11-13 に広げた。[決済の決定](2026-11-13-stripe-card-payment.md)）で、公開鍵が `pk_test_` で始まらないときは、決済の API を使えなくする。起動は止めない。カードの選択肢を出さず、店頭払いだけにする。鍵がないときも同じ |
| 1-16 | 環境変数 | `STRIPE_SECRET_KEY`、`STRIPE_WEBHOOK_SECRET`、`VITE_STRIPE_PUBLISHABLE_KEY`（画面用）。`.env` に入れ、Git・ログ・成果物に入れない |
| 1-17 | API | `POST /api/orders`（お会計。カードのときは PaymentIntent の `client_secret` も返す）、`POST /api/payments/stripe/webhook`（会員認証なし、Stripe の署名で検証、CSRF の対象外） |

### 5. この決定に合わせた API の形（#108・#119・#105 の実装で入れたもの）

- カート・注文・庭の買い物リストの API（`/api/cart/**`、`POST/GET /api/orders`、`/api/orders/{id}` 系、`/api/shopping-lists/**`、`/api/cart/shopping-lists/**`）は、店舗側・申請中のアカウントに 403 `BUYER_REQUIRED` を返す
- `GET /api/cart` の応答に `removedItems`（外した明細の商品 ID・商品名・店舗名・数量・理由）を足す。明細に `unavailableReason`（今は買えない理由。買えるなら null）を足す
- `POST /api/products/references` の応答に `unavailableReason` を足す。値は `DELETED`・`STORE_CLOSED`・`STORE_SUSPENDED`・`ORGANIZATION_SUSPENDED`（Canvas が配置を外す）、`STORE_CLOSING`・`STORE_UNPUBLISHED`・`ORGANIZATION_NOT_ACCEPTING`・`PRODUCT_SUSPENDED`・`HIDDEN`・`OUT_OF_STOCK`（配置を残す）。`purchasable` が true なら null。照会では在庫0も `purchasable:false`（理由 `OUT_OF_STOCK`）にする
- `GET /api/stores/{id}` の応答に `closingStartedAt` を足す

## Alternatives

### 全体

- V1 を書き換えて DB を作り直す：マイグレーションが1本で済むが、main を取り込んだ全 PC で `DB-reset.bat` のやり直しが要る。開発データも消えるので採らない

### 決済

- 1-1 カードだけにする（店頭払いをなくす）：支払方法の分岐が減るが、Stripe の鍵がない PC で購入の流れを試せなくなるので採らない。PayPay・楽天ペイを残す：テストモードで扱える決済の仕組みがなく、選べても実際には何も起きない選択肢になるので消す
- 1-2 与信だけ取り、受け取り時に確定する：店舗ごとに受け取り日がずれ、与信の期限（7日）も扱う必要がある。1回のお会計で複数店舗の注文を作る形と合わないので採らない
- 1-3 店舗ごとに PaymentIntent を作る：店舗ごとのキャンセルが全額返金になり分かりやすいが、1回のお会計でカードの入力・認証が店舗の数だけ要るので採らない
- 1-4 支払い成功の Webhook を受けてから在庫を減らす：支払ったのに在庫がない注文が起き、返金が要る。時間切れの分数は、10分（カード入力・3D セキュアの時間に足りない）や24時間（在庫を長く押さえすぎる）を採らず30分にした。取り消しを「注文を見たときに判定する」だけにする案は、誰も見ない注文の在庫が戻らないので、定期処理も併せて行う
- 1-5 状態の名前を変える：DB の CHECK 制約と ER 図をすべて直すことになるが、得るものがないので採らない
- 1-6 店頭払いも返金の対象にする：アプリの中でお金を受け取っていないので、返金の記録だけが残る形になる。採らない
- 1-7 受け取り後の返品をアプリで扱う：返品の受付・在庫の扱い・期限のルールが要る。今の範囲では採らない
- 1-8 受け取りの期限を決めて自動でキャンセルする、または店舗がキャンセルできるようにする：期限の長さ・通知・返金の手順が要る。今は運営が状態を見られれば足りるので採らない
- 1-9 単独の返金ボタンを作る：キャンセルせずに返金だけをする操作になり、注文の状態と返金が食い違う。採らない
- 1-11 商品ごとの一部返金：返金の行を明細ごとに持つ必要があり、DB の構成（注文1件に返金1行）を変えることになるので採らない
- 1-12 決済手数料を店舗の負担として記録する：精算を作らないので、記録しても使い道がない。採らない
- 1-13 Stripe Connect で手数料を差し引く：店舗ごとの Stripe アカウントの登録と審査が要り、テストモードの範囲を超えるので採らない
- 1-14 チャージバックに自動で応じる処理を作る：テストモードでは実際に起きないので、記録だけにする
- 1-15 本番の鍵や鍵の不足で起動を止める：Stripe の鍵がない PC で EC 全体が動かなくなるので採らない。決済だけを止める
- 1-17 決済の作成を別の API（`POST /api/checkout/{requestId}/payment`）に分ける：お会計と決済の作成の間に失敗が起きると、在庫を確保した注文だけが残る。1つの API で返す

### 権限

- 2-1 STAFF は在庫数だけ（今の実装）：#105 の決定（STAFF は価格と在庫数を変えられる）と食い違う。価格と在庫数だけを変える別の API を作る案は、商品の編集画面と API が2つになるので採らず、商品の編集を STAFF に開けた
- 2-2 ロール未割り当ては何も見られない（今の実装）：#105 の決定と食い違い、招待キーで登録した直後の人が所属店舗を確かめられないので採らない
- 2-3 MANAGER も組織の全員を見られる：ほかの店舗の担当者の一覧まで見えることになるので採らない
- 2-4 MANAGER も MANAGER を割り振れる：「自分より下のロールだけを付けられる」の考え方から外れるので採らない
- 2-5 ORG_ADMIN の候補を担当店舗だけにする：ORG_ADMIN は組織の全店舗のロールを割り振る役なので、ロールのない店舗も選べる必要がある。商品・在庫・注文は店舗のロールに従うので、ロールのない店舗では人事の画面だけにした
- 2-6 店舗側のアカウントでも購入できるようにする：店舗側のアカウントで自分の店舗の商品を買える形になり、注文と売上の区別がつかなくなる。運営（ADMIN）も止める案は、運営が購入者側の動きを確かめられなくなるので採らない
- 2-7 14日操作のない会員を消す：#109・#126 で「無期限に残す」と決めた後も完了条件に残っていただけなので、完了条件から外す

### 店舗・組織

- 3-1 MySQL の Event Scheduler で連絡先を消す（#79 の元の決定）：既存の PC ではアプリ用の DB ユーザーに EVENT 権限を付け直せず、本番（RDS）でも `event_scheduler` の設定が別に要るので採らない
- 3-2 未ログインでも非公開の店舗を返す（今の実装）：非公開・停止の店舗の情報が誰にでも見える。閉鎖予定の店舗も 404 にする案は、未完了の注文がある購入者が受け取り先を確かめられなくなるので採らない
- 3-3 受付停止を取り消せないようにする：店舗の閉鎖は閉鎖中なら取り消せるので、組織も揃える。理由を記録しない案は、運営の判断を後から確かめられないので採らない
- 3-4 `material_products` をなくす：旧アセットを置いた庭で商品候補が出なくなる。今はテスト・デモの庭でも使っているので残す
- 3-5 外した商品を「○○の商品は見つかりません」と出す（#79・canvas#65 の元の文言）：商品が消えたように読めるので、「購入できなくなったため外した」と理由が分かる文言にした。非公開・在庫0も外す案は、出店者が一時的に止めただけの商品までカートから消えるので採らない
- 3-6 #120 を「発送は行わない」で閉じる：ユーザーの承認がまだないので、決定案のまま開いておく

### Canvas

- 4-1 店舗側のアカウントでも Canvas を使えるようにする：Canvas の庭から買い物リスト・カートへ進む導線があり、2-6（店舗側は購入できない）と食い違うので採らない
- 4-2 在庫0や非公開でも配置を外す：一時的な状態で庭のデザインが壊れるので採らない。配置の店舗を後から切り替える案は、商品と店舗が1対1なので採らない
- 4-3 Canvas の試験の選び方を変える（`force` で選ぶなど）：画面の構造（label の中に別の操作部品がある）が残り、支援技術からも同じ問題が見えるので、EC の画面を直す

## Consequences

- 決済は #132・#133 で実装する。Stripe のテスト用の鍵（`sk_test_`・`pk_test_`）、Webhook の署名用の値、Stripe CLI の用意が先に要る（この PC にはまだない）。鍵がない PC でも、店頭払いで購入の流れを試せる
- AGENTS.md と `docs/functional-requirements.md` などの「実決済は対象外」を、「Stripe のテストモードの決済は範囲に入れる（実際のお金は動かさない）」に直した
- 店舗側・申請中のアカウントは、カート・注文・庭の買い物リストの API で 403 になる。画面ではヘッダーのカート、商品の「カートに追加」、カート画面を出さず、購入者のアカウントで使うよう案内する。共通ヘッダーの部品（`@kusakari/site-header`）にはカートを隠す引数がないので、EC 側の CSS で隠している
- 店舗の閉鎖（`closed_at`）を書く処理は #79 でまだ作っていない。カートから外す判定・照会の理由・店舗の公開ページは、`closed_at` と `closing_started_at` を読むだけで先に入れた。閉鎖中（`closing_started_at` あり、`closed_at` なし）は `STORE_CLOSING` として外さずに残している。#79 の元の決定（閉鎖中から外す）に合わせるかは、#79 の実装のときに決め直す
- ロール未割り当ての担当者は、`GET /api/seller/stores` の店舗一覧に所属店舗が出る。`/api/auth/me` の `storeIds` は、今までどおりロールのある店舗だけ
- 組織の受付停止の取り消し・理由の記録（3-3）、#79 の閉鎖、アカウント一覧（2-3・2-4）、ORG_ADMIN（2-5）、Canvas の制限（4-1・4-2）は、それぞれの issue で実装する
