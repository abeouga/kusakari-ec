# 購入者・アカウント機能をユースケース（00・EC-B*）に合わせる

## Context

ユースケース（`kusakari_document/ユースケース/kusakari-ec/` の 00 と EC-B*）と実装を照合したところ、次の差があった。

- EC-B21 退会：未完了の注文や出品中の商品を確認せず、`DELETE /api/account` が無条件に会員を無効化していた。退会画面には「戻る」がなく、完了メッセージは遷移前に消えていた。
- 共通 *a/*b：APIがJSON以外（プロキシの502 HTMLなど）を返すと、画面に生の例外文が出た。操作中にログインが切れても通常のエラー表示だけで、ログインの導線がなかった。
- EC-B19：確認用パスワードがなく、現在のパスワード誤りを401（ログイン時と同じ文言）で返していた。
- EC-B05：商品詳細の「販売店舗の紹介」が、商品の出店者ではなく選択中の受取店舗を指していた。
- EC-B12：停止中の店舗も受取店舗の候補に出ていた（注文時は拒否済み）。
- EC-B17/B18：確認画面がなく、状態表記が「審査待ち」、申請日・案内文・再申請の入力済み表示がなかった。
- EC-B24/B25：カートにない商品も「カートに0点」と表示し、在庫不足をカート内の点数を含めずに判定していた。通信失敗で選択が消え、全選択では追加できない商品を黙って除外していた。

## Decision

- **退会の判定はサーバーで、削除ボタン押下時に行う**（`MemberService.withdraw`、`WithdrawalGuard`）。会員行をロックしたうえで次の順に確認し、該当すれば409で拒否する。
  - 購入者として「注文受付」「受取準備完了」、または未処理のキャンセル申請がある注文：`WITHDRAWAL_OPEN_ORDERS`。応答に対象注文（ID・状態）を含め、画面は注文一覧と注文履歴へのリンクを出す。購入者が履歴から非表示にした注文も、店舗の引き渡しが残るため対象に含める。
  - 出店者として自店舗の在庫が `PUBLISHED` で、削除されていない商品がある：`WITHDRAWAL_LISTED_PRODUCTS`。商品一覧へのリンクを出す。
  - 自店舗の注文に「注文受付」「受取準備完了」、または未処理のキャンセル申請がある：`WITHDRAWAL_STORE_ORDERS`。受注一覧（キャンセル申請も同じ画面で処理する）へのリンクを出す。出店者の判定前に店舗行をロックし、注文確定（同じ店舗行をロックする）と直列化する。
  - 旧デモ注文（`DEMO_CONFIRMED`）は受け渡しの手続きがないため未完了として扱わない。
  - データ保持は従来どおり：会員は無効化（`enabled=false`、`withdrawn_at`）し、注文などの記録は残す。UCの「30日後に削除」は今回実装しない。
- **退会画面**：同意チェックまで削除ボタンを押せない。「戻る」で直前の画面へ戻る。完了時はセッションが終わるため、トップページを読み直して `?notice=withdrawn` の完了メッセージを表示する（URLからはすぐ外す）。401は「ログインの有効期限が切れました。もう一度ログインしてください」とログイン導線、通信失敗・5xxは「退会処理に失敗しました。時間をおいて再度お試しください」。
- **共通 *a/*b**（`frontend/src/api.js`）：応答がJSONでなければ、サーバー側の結果が不明な通信エラー（status 0）として扱う。ログイン済みだった画面で401を受けたら、画面を切り替えずに上部へ有効期限切れの案内と、既存の `returnTo` 付きログインを出す（`SessionNotice`）。未ログインの利用者（ゲストカートなど）の401では出さない。
- **EC-B19**：`PUT /api/account/password` に `confirmPassword` を必須で追加し、不一致は400 `PASSWORD_MISMATCH`。現在のパスワード誤りは400 `CURRENT_PASSWORD_INVALID`「現在のパスワードが正しくありません。」にする。401にしないのは、有効なセッションを期限切れと誤認させないため。ログインAPIの文言は変えない。完了後はログイン画面を読み直して完了メッセージを出す。
- **EC-B05**：商品の応答に `sellerStoreId` を追加する。出店者の商品は出店者の店舗、所有者のない共通商品は表示中の店舗（その店舗が在庫を持ち販売している）とする。出店者の商品は出店者の店舗にだけ在庫が作られるため、受取店舗の商品一覧に出る商品は常にその店舗で販売されている。
- **EC-B12**：`GET /api/stores` は停止中の店舗を返さない。注文時の拒否は従来どおり。
- **EC-B17/B18**：申請画面は「確認画面へ」→確認画面（「修正する」「申請する」）。申請状況画面 `/seller/application/status` を追加し、審査中は「審査中」・申請日・申請内容（閲覧のみ）・「審査結果は通知でお知らせします」を表示し、フォームを出さない。却下時は却下理由と「再申請する」を表示し、前回の内容を入力済みにした申請画面へ移る（書類ファイルはブラウザーの制約で再選択が必要）。メニューは申請前「出店申請」、申請後「出店申請状況」。URL直アクセスは、出店者なら商品一覧、未申請なら申請画面、審査中に申請画面を開いたら申請状況画面へ移す。
- **EC-B24/B25**：「カートにn点」はカートにある商品だけ表示する。在庫不足は「在庫 < カート内の点数＋数量」で判定する（サーバーと同じ）。通信失敗では選択を残し、再実行できるようにする。全選択では選べなかった商品と理由を表示する。部分成功（追加できる分だけ追加して理由付きで見送る）とカート画面への遷移は従来どおりとし、UC側を直す。

## Alternatives

- 退会の確認を画面表示時に行う案は、画面を開いた後に注文や商品の状態が変わるため採用しない（UC関連情報）。
- 退会時に会員と関連データを削除する案は、注文実績を残す必要があるため採用しない。
- 期限切れの401でログイン画面へ即時移動する案は、入力中の内容が消えるため採用しない。
- 現在のパスワード誤りを401のままにして画面側で区別する案は、APIの意味が「未認証」と「入力誤り」で混ざるため採用しない。
- 商品詳細の店舗リンクを画面側の受取店舗だけで決める案は、出店者の店舗という意味をAPIが持たなくなるため採用しない。

## Consequences

- 退会できない利用者は、注文の引き渡し・キャンセル処理、または商品の販売停止を済ませる必要がある。E2Eで共有アカウント（`test.user`）を退会させる手順は、未完了注文が残る他のテストと衝突するため、専用のCognitoテストアカウントで行う。
- `PUT /api/account/password` の呼び出しは `confirmPassword` が必要になる（互換性のない変更。利用箇所はECの画面とE2Eのみ）。
- 申請の「再申請」は新しい申請行を作る（従来どおり）。前回の書類は再利用しない。
- `sellerStoreId` は応答への追加のみで、Canvasなど既存の利用側には影響しない。
- スキーマ変更はない（Flywayマイグレーションの追加なし）。
