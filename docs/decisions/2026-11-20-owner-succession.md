# 組織のオーナーの譲渡（#181、#190、#200）

## Context

組織のオーナーは1つの組織に1人で（#102）、出店申請をした人が承認でオーナーになる（#109）。オーナーは組織から除名できない（#167）。オーナーが会社を辞める、担当を変えるといった場面でオーナーを替える方法がなく、替えるには組織を作り直すしかなかった。

基本の仕様は #181 で決め、譲渡先の指定のしかたと承認の形は #190 の子 issue で決めた。決めることの洗い出しは #191、承認までの流れは #194、交代した後のロールと担当は #195、操作の記録は #196、承認したときの DB の付け替え方は #197。実装の途中で出た決めること 1〜6 は #200 で決めた（2026-11-20）。実装は #201〜#205・#213。

この記録は、譲渡の仕様と、実装で決めた作り（ロックの順番、期限切れの見つけ方、通知の作り）をまとめる。

## Decision

### 誰が、誰に譲渡できるか

- 譲渡を申し出られるのは、その組織のオーナー（`SHOP_OWNER`）本人だけ。運営（`ADMIN`）は関与しない（#181 の 1）。
- 譲渡先は、同じ組織の担当者（`organization_members` の人）なら誰でもよく、ロールの制限はない（#181 の 2）。除名中・停止中・退会済みの人は譲渡先にできない（409 `OWNER_SUCCESSION_TARGET_UNAVAILABLE`）。
- 譲渡先は、店舗専用ページの今の「アカウント」の一覧から選ぶ。会員 ID は入力しない（#191 の 1、#195 の 3）。譲渡の列と操作はオーナーにだけ表示し、ORG_ADMIN・MANAGER には表示せず、API も 403 で断る（#195 の 7）。
- 組織が受付停止中・停止中でも、申し出も承認もできる（#200 の決めること 2）。停止は注文を止めるためのもので、組織の中の人の管理は止めておらず、オーナーが替わっても組織の停止はそのまま続くため。

### 申し出から、交代か無効になるまで

- 譲渡先が承認した時点で交代する。オーナーの操作だけでは交代しない（#181 の 4、#194 の 1）。
- 承認を待っている状態は `organizations.pending_owner_member_id`（譲渡先）と `pending_owner_expires_at`（申し出た時刻＋30 分）に持つ（#194 の 10・12）。申し出がなければ2つとも空で、片方だけに値がある状態は CHECK 制約が拒否する。
- 同時に申し出られるのは1人だけ（#194 の 4）。承認待ちが残っている間の新しい申し出は 409 `OWNER_SUCCESSION_PENDING`。
- オーナーは承認される前の申し出を取り消せる（#194 の 5）。譲渡先は断れる（#194 の 6）。
- 承認の期限は申し出から 30 分。期限が過ぎた申し出は、残っていないものとして扱う（#194 の 16）。期限切れの申し出への承認・断りは 409 `OWNER_SUCCESSION_EXPIRED`、取り消しは 409 `OWNER_SUCCESSION_NOT_PENDING`。
- 承認待ちの間に、譲渡先が除名・運営の停止・退会したとき（#194 の 7・13）、オーナーが譲渡先を除名したとき（#194 の 8・14）、申し出たオーナー本人が退会・運営の停止をされたとき（#200 の決めること 5）は、その処理と同じトランザクションで申し出を無効にする。
- 承認したら、1つのトランザクションで新旧のオーナーを入れ替える（#197 の 8）。外部キーと CHECK 制約にぶつからないよう、次の順に1段ずつ DB に書く。
  1. 新しいオーナーを `organization_members` から外す。店舗の担当（`store_members`）も一緒に消える（#195 の 1、#197 の 4）。
  2. 新しいオーナーの `members.account_type` を `SHOP_OWNER` にする（#195 の 2）。
  3. `organizations.owner_member_id` を新しいオーナーにする（#197 の 1）。
  4. 元のオーナーの `members.account_type` を `SHOP_STAFF` にする。
  5. 元のオーナーを `organization_members` に `role = 'ORG_ADMIN'` で入れる（#195 の 5、#197 の 5）。どの店舗の担当でもない。
  6. 承認待ちの2列を空にし、承認を記録する。
- 新しいオーナーのロールは、ほかのオーナーと同じ。譲渡されたことを表すロールは作らない（#195 の 4）。
- 元のオーナーは、交代した時点からほかの ORG_ADMIN と同じ扱いで、除名もできる（#195 の 8）。
- オーナーは常に1人で、交代までの移行期間はない（#190）。間違えて譲渡したときに元に戻す操作はなく、戻すには新しいオーナーからもう一度譲渡してもらう（#197）。

### 通知

- 知らせるのは店舗専用ページの本人あての通知だけで、メールなどの外部への配信はしない（#194 の 2・9）。
- 通知に種類の列（`notifications.category`）を足した（#194 の 17）。値は `ORDER`・`CANCEL_REQUEST`・`MODERATION`・`STORE_CLOSURE`・`OWNER_SUCCESSION_REQUEST`・`OWNER_SUCCESSION_RESULT`・`GENERAL` の7つ。重要かどうかは DB に持たず、種類から決める。重要の印を出すのは `OWNER_SUCCESSION_REQUEST` だけ。それまでの通知は `GENERAL`。
- 申し出たら、譲渡先に「オーナーの譲渡の申し出」（`OWNER_SUCCESSION_REQUEST`）を送り、承認の期限を書く。
- 申し出が終わったら、交代したとき（#194 の 9）も、断り・取り消し・自動で無効のとき（#200 の決めること 1）も、オーナーと譲渡先の両方に「譲渡の結果」（`OWNER_SUCCESSION_RESULT`）を送る。自動で無効のときは、本文の最初に理由（期限切れとその期限、譲渡先の除名・停止・退会、オーナーの停止・退会）を書く。除名中・停止中・退会済みの相手にも送る。組織のほかの人には送らない。
- 申し出の通知の「承認する」「断る」は、自分あての期限内の承認待ちがあるときの、いちばん新しい申し出の通知にだけ出す。それ以外の申し出の通知には、申し出が終わったことを出す（#200 の決めること 6）。押しても通らないボタンを残さないため。どの通知が今の申し出のものかはサーバーが決め、通知一覧の API の `answerable` で返す。

### 操作の記録

- 担当者の操作の記録（`organization_member_events.event_type`）に5つの種類を足した（#181 の 5、#196）。店舗は持たない（`store_id` は NULL）。

| 種類 | いつ | 操作した人 | 操作された人 |
| --- | --- | --- | --- |
| `OWNER_SUCCESSION_REQUEST` | 申し出 | オーナー | 譲渡先 |
| `OWNER_SUCCESSION_CANCELLATION` | 取り消し | オーナー | 譲渡先 |
| `OWNER_SUCCESSION_REFUSAL` | 断り | 譲渡先 | 譲渡先 |
| `OWNER_SUCCESSION_APPROVAL` | 承認（交代の記録を兼ねる） | 新しいオーナー | 新しいオーナー |
| `OWNER_SUCCESSION_AUTO_INVALIDATED` | 期限切れ、譲渡先の除名・停止・退会、オーナーの停止・退会 | 申し出たオーナー | 譲渡先 |

- 自動で無効は、期限切れと、除名・停止・退会のすべてを1つの種類で表す（#196 の 5）。オーナーが譲渡先を除名したときも、取り消しではなくこの種類にする（#200 の決めること 4）。除名の記録が別に残るので理由は分かり、ORG_ADMIN が除名したときと記録の形がそろうため。#194 の 14 の「取り消しと同じ扱い」は、承認待ちが消えるという効き目のことと読む。
- 自動で無効の「操作した人」は、誰が除名・停止したかにかかわらず、申し出たオーナーにする（#196 の 6）。列を空にできるようにはしない。
- 除名・停止・退会で当たった申し出の期限がもう過ぎていたら、その申し出は期限切れで終わったものとして、通知の理由も期限切れにする。記録は1回だけ残す。
- 譲渡の記録は、店舗専用ページの「履歴」に、除名・復帰と同じく組織全体の記録として、どの店舗を選んでいても出す（#200 の決めること 3、#213）。見られる人は今までどおりオーナーと ORG_ADMIN で、交代した後の新しいオーナーも前の記録を見られる。自動で無効は誰かの操作ではないので、画面では「操作した人」を「なし（自動）」とし、申し出たオーナーは「申し出たオーナー」として出す。

### 期限切れの見つけ方

- 期限切れを調べる定期処理は作らない。次に誰かが操作したときに見つけて「自動で無効」を記録し、通知を送る（#194 の 15）。
- 見つけるのは、申し出の API、アカウント一覧の読み込み、通知一覧の読み込み（自分がオーナーか譲渡先の組織）、承認・断りの前。
- 承認・断りが期限切れで 409 になるときも、記録と通知はコミットする（このエラーではトランザクションを巻き戻さない）。
- 通知一覧の読み込みで見つけたときは、同じトランザクションで通知を保存してから一覧を読むので、その一覧に新しい「譲渡の結果」の通知が含まれる。

### 同時に起きる操作とロックの順番

- 承認待ちを扱う処理は、どれも組織の行を `PESSIMISTIC_WRITE` でロックしてから、DB の今の値で読み直して確かめる（権限の確認で読み込み済みの値は古いことがあるため）。会員の行も、ロックした後に読み直す。
- ロックの順番は、すべての操作で「店舗 → 組織 → 所属 → 会員」の向きにそろえる。逆向きの組み合わせがあると、同時に起きたときに互いを待ってデッドロックし、MySQL がどれか1つを失敗させるため。

| 操作 | ロックの順番 |
| --- | --- |
| 申し出 | 組織 → 譲渡先の所属（共有）→ 譲渡先の会員 |
| 承認 | 組織 → 譲渡先の所属 → 譲渡先の会員 → 元オーナーの会員 |
| 断り・取り消し | 組織 |
| 除名 | 組織 → 所属 |
| 運営の停止（担当者・オーナー） | 組織 → 会員 |
| 担当者の退会 | 組織 → 会員 |
| オーナーの退会 | 組織のすべての店舗（ID の順）→ 組織 → 会員 |
| 注文の確定 | カート → 店舗（ID の順）→ 組織（共有）→ 商品 → 在庫 |

- オーナーの退会は、出品中の商品と未完了の注文がないことを確かめるために店舗の行をロックするので、組織の行より先にロックする（#200 の決めること 5）。前は「会員 → 店舗」で、承認・注文の確定と輪になっていた。
- どの行をロックするかはロックせずに読んだ会員の種類で決め、ロックの後に読み直す。ロックを待つ間に承認でオーナーから担当者になっていたら、担当者として退会を確かめる。担当者からオーナーになっていたら（同じ人が承認と退会を同時に送ったとき）、店舗をロックしていないので 409 `WITHDRAWAL_ACCOUNT_CHANGED` で断る。

### 通知の作り

- 譲渡の通知の宛て先と文面は1か所（`OwnerSuccessionNotices`）にまとめ、呼ぶ側のトランザクションの中で保存する。
- 通知の共通の処理（`NotificationService`）は通知一覧の読み込みで期限切れの処理を使う。期限切れの処理から通知の共通の処理を使うと依存が循環して起動しないので、譲渡の通知は通知の表（`NotificationRepository`）に直接保存する。

## Alternatives

- 運営が譲渡する・ORG_ADMIN にだけ譲渡できるようにする（#181 の 1・2）：オーナー本人だけが、ロールを問わず組織の担当者に譲渡する形にした。
- 会員 ID を入力して譲渡先を指定する、招待キーのようなものを渡して承認してもらう（#191 の 1・2）：今のアカウントの一覧から選び、店舗専用ページの通知で承認する形にした。
- 承認する段階を置かず、選んだ時点で交代する（#194 の案B）：作りは単純だが、譲渡先が同意しないままオーナーになるため採らない。
- 同時に複数の人へ申し出る（#194 の 4）：同時に承認されるとオーナーが2人になりうるため採らない。
- メールでも知らせる（#194 の 2・9 の当初の意見）：外部への配信は対象外のため、店舗専用ページの通知だけにした（2026-11-19 に直した食い違い）。
- 承認待ちを操作の記録だけで表す（#194 の 10）：記録の種類を足すだけでは承認を待っている期間を表せず、期限内だけ受け付ける・期限切れにする処理を作れないため、組織の表に2列を足した。承認待ちの新しい表も作らない。
- 通知に重要度の列を足す（#194 の 11 の意見）：種類の列を1つ足し、重要かどうかは種類から決める形にした（#194 の 17）。種類での絞り込みや種類ごとのアイコンは、列があれば後から足せるので今は作らない。
- 記録の種類の代わりに段階の列（仮：`transfer_phase`）を足す、譲渡を1つの種類（仮：`TRANSFER_OWNERSHIP`）で表す（#196 の 2）：既存の種類の列に値を足す形にした。
- 期限切れを「取り消し」で記録する（#196 の 1）：後で履歴を見たときに、オーナーが取り消したのか期限が過ぎたのか分からなくなるため採らない。
- 自動で無効の「操作した人」を譲渡先にする・空にする（#196 の 6）：申し出たオーナーにした。
- 交代した後の元のオーナーのロールを空にする（#195 の 6 の当初の意見）、新しいオーナーに「新しいオーナー」のロールを作る（#195 の 4）：元のオーナーは ORG_ADMIN、新しいオーナーは普通のオーナーにした。
- 譲渡のためにアカウントの一覧の画面を新しく作る（#195 の 3 の当初の意見）：今ある店舗専用ページの「アカウント」の一覧を使う。
- 交代から7日間の移行期間を設け、その間は元のオーナーもオーナーのまま残す（#195 の 5 の一時の決定、#197、#198）：オーナーが2人いる例外、7日後の切り替え、移行期間中の取り消しのための記録が要り、DB の設計が分かりにくくなるため、2026-11-19 にやめた（#190）。移行期間を表すために検討した次の形も、どれも採らない。
  - 組織の表に元のオーナーと移行期間の終わりの時刻の列を足す（`previous_owner_member_id`・`previous_owner_until` など）。
  - オーナーを入れる別の表を作り、新旧のオーナーを行で持つ（`organization_owners`）。オーナーを1つの列で見ているところ（認可の判定や画面）をすべて直す必要がある。
  - 元のオーナーを ORG_ADMIN にし、担当者の表に「オーナーと同じ権限を持つ期限」の列（`owner_privileges_until`）を足す。ORG_ADMIN なのにオーナーと同じ権限を持つ形が直感的でない。
  - 1回の譲渡を1行で持つ譲渡の表（`organization_owner_transfers`）で、元のオーナーが取り消せるようにする。新しいオーナーの元のロールと担当を残して逆向きに戻す処理が要り、作りと保守が重い。
  - オーナーも担当者の表のロール（`organization_members.role = 'OWNER'`）にまとめる作り直し。#102 のテーブル構成とオーナーの判定をすべて作り直すことになる。
- 申し出たオーナーが承認待ちの間に退会・停止されても申し出を残し、承認のときに元のオーナーを所属させない（#200 の決めること 5）：譲渡先が除名・停止・退会したとき（#205）と同じ形にそろえ、申し出を「自動で無効」にすると決めた。
- 終わった申し出の通知にもボタンを残し、押したらエラーを出す（#200 の決めること 6）：押しても通らないボタンを残さないため採らない。
- 譲渡の記録を新しい画面に出す（#200 の決めること 3）：除名・復帰と同じ「履歴」に、組織全体の記録として出す。
- 期限切れを定期処理で見つける：定期処理を作らない方針のため、次の操作で見つける（#194 の 15）。
- どの申し出の通知が今の申し出のものかを、通知と申し出の時刻を比べて見分ける、通知に申し出の ID を持たせる：時刻のずれで食い違うおそれがあり、DB の変更も要るため、いちばん新しい申し出の通知で見分ける（担当者は1つの組織にだけ所属し、組織の承認待ちは1件で、申し出のたびに通知を1件送るため、これで足りる）。
- 依存の循環を、遅れて読み込む指定やイベントで避ける：どの部品がどれに依存しているかが見えにくくなるため、通知の表に直接保存する。
- 担当者の退会でも組織の店舗をすべてロックする：担当者からオーナーになったときの 409 は要らなくなるが、ほとんどの担当者の退会で注文の確定を要らないロックで待たせるため採らない。

## Consequences

- 間違えて譲渡したときは、新しいオーナーにもう一度譲渡してもらうしか戻す方法がない。元のオーナーが自分で取り消すことはできない。
- 期限切れの申し出は、次に誰かが操作するまで承認待ちの列に値が残る。「自動で無効」の記録の日時は期限ではなく見つけた時刻になる（期限は通知の本文に書く）。
- 「自動で無効」の記録は、なぜ無効になったかを持たない。除名なら除名の記録が並んで残るが、停止・退会と期限切れは、通知の本文でしか区別できない。
- 承認待ちの間に譲渡先や申し出たオーナーが組織を離れると、期限を待たずに申し出が消える。退会した人も、その人あての「譲渡の結果」の通知は保存されるが、読むことはできない。
- オーナーの退会は組織のすべての店舗の行をロックするので、その間の注文の確定は退会の処理が終わるまで待つ。
- 申し出の通知は申し出の ID を持たない。今の申し出の通知を「いちばん新しい申し出の通知」で見分けるので、担当者が複数の組織に所属できるようにするときや、1回の申し出で通知を複数送るようにするときは、見分け方を変える必要がある。
- 移行期間はないので、`docs/` の「オーナーは1つの組織に1人」の説明（`organizations.owner_member_id` の一意キー、`owner_account_type` の CHECK）はそのまま正しい。
