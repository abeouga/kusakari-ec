# 商品・店舗の停止の前に、運営者が出店者へ警告できるようにする（issue #16）

> **2026-11-13 追記**：実装は [2026-11-13-moderation-warnings.md](2026-11-13-moderation-warnings.md) にある。下の「確かめていないこと」（停止中の商品のお会計）は、その実装で直した。

## Context

- 運営者が商品・店舗に対してできる操作は、停止と再開の2つだけである。
  - 商品の公開停止・再開（EC-A10）は `PUT /api/operator/products/{id}/moderation`。理由は必須で、出店者に通知する。
  - 店舗の利用停止・再開（EC-A11）は `PUT /api/operator/stores/{id}/enabled`。理由の入力欄はなく、出店者に通知しない。
- 軽い問題でもすぐに停止するしかなく、出店者は前もって知ることも直すこともできない。特に店舗の停止は影響が大きい。購入者の画面から全商品が消え、受取店舗に選べなくなり、出店者は商品・在庫・注文の操作がすべてできなくなる。それなのに、出店者には通知されない。
- 停止の理由と日時は DB に残っていない。商品は `products.suspended`、店舗は `stores.enabled` の真偽値だけで、商品の停止理由は通知の本文に残るだけである。
- 操作の履歴（監査ログ）のテーブルはない。店舗側アカウントの作り直しで使う DB の構成（v3、issue #126）でも、「運営の警告の記録」は #16 で決めるまで入れないことになっている。

## Decision

### 警告と停止の関係

- 運営者は、商品と店舗のどちらにも、理由を付けて「警告」できる。警告しても、商品の公開状態・店舗の利用状態は変わらない。購入者への表示も注文の受付も続く。
- 警告は、停止の前に行ってもよい段階である。必ず行う必要はない。停止は、警告をしていなくても実行できる。
- 期限は設けない。期限が来たら自動で停止する仕組みも作らない。停止するかどうかは、運営者が判断して手で行う。
- 警告を解除できるのは運営者だけである。出店者が「対応済み」と報告する機能は作らない。商品を編集しても、警告は自動では解除されない。
- 警告中の対象に、もう一度警告できる。

### 画面

- 運営者の「商品管理」「店舗管理」の画面に、「警告する」と「警告を解除」の操作を置く。警告するときは理由の入力を必須にする。
- 停止は、各画面の「デンジャーエリア」にだけ置く。停止では、商品・店舗とも理由の入力を必須にし、確認ダイアログを出す。今の店舗の停止は理由の入力欄がないので、ここが変わる。
- 再開はデンジャーエリアには置かない。通常の位置に置き、確認ダイアログだけを出す。
- 運営者の一覧で、警告中であることと、最後の警告の日時・理由が分かるようにする。対象ごとに、警告・停止・再開・警告解除の履歴を見られるようにする。
- 出店者の商品一覧と店舗の画面に、「警告中」のバッジと理由を出す。
- 購入者の画面には何も出さない。

### 通知（EC-S11）

- 警告・警告解除・停止・再開のすべてを、出店者へ通知する。通知には対象と理由を入れる。
- 店舗の停止・再開も通知するように、EC-A11 の「出店者に通知しない」を変える。
- 店舗あての通知は、今と同じく店舗の担当者全員に送る（`NotificationService.toStore`）。
- `notifications` に通知の種別を表す列は足さない。今のほかの通知と同じく、タイトルで区別する。

### データ

- 履歴は、商品と店舗で別のテーブルに持つ。`product_moderation_events` と `store_moderation_events` の2つで、列の形は同じにそろえる。
  - 列は、対象の ID（外部キー）、操作の種別（`WARN` / `CLEAR_WARNING` / `SUSPEND` / `RESUME`）、理由、操作した運営者の会員 ID（外部キー）、日時。
  - 理由は、警告と停止では必須、警告解除と再開では任意とする。
  - 行は書き換えず、削除もしない。
- 「今、警告中か」は、対象の履歴のうち最新の `WARN` と、最新の `CLEAR_WARNING` を比べて求める。`products`・`stores` には、警告用の列を足さない。
- 停止の状態は、今と同じく対象の列（v3 では `products.suspended`・`stores.suspended`）に持つ。停止・再開では、その列の更新と履歴の行の追加を、1つのトランザクションで行う。
- Java 側の操作種別の enum、DTO、画面の部品（理由入力のダイアログ・履歴の一覧・デンジャーエリア）は、商品と店舗で共通にする。
- 組織の停止（v3 の `organizations.suspended`）は、この決定の対象に入れない。

## Alternatives

- **警告を経ないと通常の停止ができないようにし、すぐ止めるのはデンジャーエリアからだけにする**：止める入口が2つになり、どちらを使うかの判断が運営者に増える。重大な問題ではすぐ止めたいので、警告は任意の前段階にした。
- **期限を設け、期限切れで自動停止する**：定期的に動く処理が新しく必要になる。運営者が見ていないところで、店舗の全商品が消えることにもなる。
- **期限の日付だけを出店者に見せる**：自動で止めないのに日付だけあると、期限を過ぎても何も起きないことになり、意味がはっきりしない。
- **出店者が「対応済み」と報告し、運営者が確かめて解除する**：出店者の画面と状態が1つ増える。まずは通知を見て直してもらい、運営者が確かめて解除する形で足りると判断した。
- **商品を編集したら警告を自動で解除する**：編集が問題の是正になっているとは限らない。店舗の警告にも当てはまらない。今の EC-A10 の「出店者が編集しても公開停止は解除されない」とも合わない。
- **最新の警告だけを対象の列に持ち、再警告で上書きする**：何回、何の理由で警告したかが残らない。停止の判断の材料にならない。
- **商品と店舗の履歴を1つのテーブルにし、`target_type` と `target_id` で対象を表す**：`target_id` に外部キーを張れない。存在しない対象や、種別と ID の食い違いを DB で拒否できず、v3 の「してはいけない組み合わせは DB の制約で拒否する」に合わない。`products.id`（文字列）と `stores.id`（数値）で型も違う。
- **1つのテーブルに `product_id` と `store_id` の両方を持ち、CHECK でどちらか一方だけにする**：外部キーは張れるが、片方の列が常に空になる。対象が増えるたびに、列と CHECK を足す必要がある。今回の画面は対象ごとの履歴だけで、全対象をまとめて見る必要もない。
- **`products`・`stores` に「警告中」の列を足す**：履歴と同じことを2か所に持つことになり、食い違う原因になる。
- **`notifications` に種別の列を足す**：今の通知の画面は一覧の表示だけで、種別で絞り込んでいない。足すと、今ある通知を作る処理もすべて直すことになる。

## Consequences

- 実装は v3 の DB（issue #107 のマイグレーション）の上に作るので、統合ブランチ `feature/shop-organization` で #107 の後に進める。
- v3 の設計の記録（`2026-11-11-shop-organization-db-v3.md`、PR #127）の「まだ決まっていないこと」にある「運営の警告の記録：入れない（#16）」は、この決定で決まる。PR #127 が入った後に、この決定を指すように直し、`schema.sql` と ER 図に2つのテーブルを足す。
- 停止の理由と日時が、商品・店舗とも履歴に残るようになる。v3 で DB を作り直すので、今の停止の記録は移さない。
- 店舗の停止の API は、理由を受け取るように変わる。
- ユースケースを、実装と同時に次のとおり直す。ユースケースの記述は今の実装に合わせているので、実装より先には直さない。
  - EC-A10：警告・警告解除の流れ、停止をデンジャーエリアに置くこと、確認ダイアログ
  - EC-A11：警告・警告解除の流れ、停止の理由を必須にすること、停止・再開を通知すること
  - EC-S11：警告・警告解除・店舗の停止と再開の通知
  - 必要なら、警告を新しいユースケースとして分ける
- 店舗が停止されても、出店者は通知を見られる必要がある。今の通知の API（`/api/notifications`）は会員ごとに返し、`requireSeller` を通らないので、停止中でも呼べる。画面から開けるかは、実装の E2E で確かめる。

### 確かめていないこと

- 停止中の商品がカートに残っているとき、購入できてしまうかどうか。決済の確認（`CheckoutService` の在庫の確認）は在庫の行の状態だけを見ていて、`products.suspended` を見ていないように読める。この issue とは別に確かめる。
