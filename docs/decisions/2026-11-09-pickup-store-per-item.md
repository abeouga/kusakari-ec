# 受取店舗を商品ごとに決める（issue #70）

## Context

カート上部の「店舗受け取り ○○」と「変更」ボタンで、カート全体に1つの受取店舗を選んでいた。選んだ店舗が、商品の在庫がある店舗と関係なく受取場所になっていた。issue #70 は、カートで受取店舗を指定・変更できないようにし、商品はその商品の在庫がある店舗（販売店舗）で受け取る形式にすることを求めている。

一方で、店舗側の業務（受け取り準備・受け渡し・キャンセル対応・店舗への通知・注文実績）は、注文の `orders.store_id` 1つを単位に動いている。商品一覧も、表示中の店舗（`carts.store_id`）の在庫で絞り込む前提で作られている（EC-B05）。

## Decision

- カートの「店舗受け取り」欄と「変更」ボタン、カートから店舗選択画面への導線を削除する。
- `cart_items.store_id` を追加し（V15）、明細ごとに受取店舗を記録する。新しい明細の受取店舗は商品の販売店舗とする。出店者の商品は出店者の店舗、所有者のない共通商品は表示中の店舗（その店舗が在庫を持って販売している）である。価格・在庫は受取店舗で検証する。明細を追加した後に表示中の店舗を変えても、その明細の受取店舗は変わらない。
- ヘッダーの「店舗を探す」（`PUT /api/cart/store`）は、商品を表示・追加する店舗の選択として残す。
- 注文確定は、受取店舗ごとに1件の注文を作り、各注文の明細をその店舗の在庫から減算する。注文の保存、在庫減算、明細保存は1トランザクションで行い、店舗・商品・在庫の順にそれぞれ並べてロックする。同じ `requestId` の再送は同じ注文群を返す（一意キーを `(cart_id, request_id, store_id)` に変更）。応答は `{ "orders": [...] }`。
- 注文確認は受取店舗ごとに店舗情報と商品をまとめて表示する。注文完了と注文履歴は注文ごと（＝受取店舗ごと）に店舗名を表示する。

## Alternatives

- 1件の注文に店舗の異なる明細を入れ、`order_items` に店舗を持たせる案は、受け取り準備・受け渡し・キャンセルが注文単位のため、ある店舗の操作が別店舗の商品の状態まで変えてしまう。採用しない。
- 商品一覧を全店舗の商品の一覧に変える案は、表示中の店舗を前提とするトップのカルーセル・商品一覧・買い物リストの設計（EC-B05）全体の変更になり、issue の範囲を超える。採用しない。
- 明細の受取店舗を注文時に決める案は、カートで見た価格・在庫と注文時の店舗が食い違うため採用しない。

## Consequences

- `cart_items.store_id` はNULLを許可する。V15で既存行はカートの店舗で埋める。V15より前のアプリが書いた行（NULL）は、カートの店舗を受取店舗として扱う。
- `POST /api/orders` の応答形式が変わる（単一の注文 → `orders` 配列）。呼び出し元はECの画面とE2Eだけで、Canvasは使っていない。
- Canvasが呼ぶ `/api/materials/quote` の要求・応答は変えない。Canvasは自身の `storeId` を送っており、カートの `storeId` に依存しない。
- 買い物リスト（庭の買い物リスト）は、商品ごとに販売店舗の在庫を表示し、カートへ移すとその店舗が受取店舗になる。
- E2E `e2e/business-pickup-store.spec.js` で、2店舗の商品を入れたカート、店舗ごとの注文確認、2件の注文、各店舗の在庫減算、`orders.store_id`、再読み込み後の注文履歴を実API・`kusakari_e2e` で確認する。
