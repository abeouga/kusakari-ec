# 店舗の閉鎖（#79）と、運営による組織の停止（#109）の実装

## Context

店舗の閉鎖（#79）と組織の停止（#109）は、2026-11-12 に流れと規則を決めていた（#79 の決定事項1〜12、#109 の 2026-11-12 のコメント、[残りの決定](2026-11-12-remaining-decisions.md) の 3-1〜3-5）。DB の列（`stores.closing_started_at`・`closing_started_by`・`closed_at`、`organizations.suspension_started_at`・`suspended`、`orders.cancelled_by_member_id`）と、買えない理由の判定（`CatalogService`）・カートから外す処理（#140）・返金（`RefundService`、#142）は先に入っていたが、閉鎖・停止を始める操作、閉鎖済み・停止への移行、まとめてキャンセル、90日後の連絡先の削除、画面がなかった。

実装にあたり、次のことを決める必要があった。

- 「未完了の注文がなくなったら自動で閉鎖済み・停止」を、いつ・どこで確かめるか
- 支払い待ち（`PENDING_PAYMENT`）の注文を、閉鎖・停止を止める注文に含めるか、まとめてキャンセルの対象にするか
- 閉鎖中の店舗の商品を、カートから外すか残すか（#79 の決定事項7の変更と、#140 の実装が食い違っている）
- 組織の停止の理由と履歴の持ち方
- 90日後の連絡先の削除を、アプリのどこで行うか（決定 3-1 で MySQL のイベントをやめた）
- 閉鎖済みの店舗の公開ページ（#79 の決定事項9「90日間は閉店しましたを表示」と、決定 3-2「閉鎖済みは404」が食い違っている）

## Decision

### 共通の判定（`OpenOrders`）

- 閉鎖・停止を止める注文は、状態が `PENDING_PAYMENT`・`ACCEPTED`・`READY` の注文とする。#79 の決定事項6（注文受付・受取準備完了・キャンセル申請の対応待ち）に、支払い待ちを足した。支払い待ちは30分以内に注文受付か取り消しになる（決済の決定 1-4）ので、それまで待つ。
- 運営のまとめてキャンセルの対象は `ACCEPTED`・`READY` だけにする。支払い待ちの注文は、同じお会計のほかの店舗の注文と決済（PaymentIntent）を共有しているので、ここでは取り消さない。
- まとめてキャンセルは、注文を ID の順にロックし、在庫を戻し、注文を `CANCELLED` にして `cancelled_by_member_id` に運営を、`cancellation_response` に運営の理由を入れる（`cancellation_status` は変えない）。カードで支払い済みの注文は `RefundService.refundCancelledOrder` で返金する（店頭払いは何もしない）。購入者には「この注文は出店者からキャンセルされました」、店舗には「運営が注文をキャンセルしました」を送る。
- 判定とまとめてキャンセルは、店舗の閉鎖と組織の停止で同じ処理を使う（#79 決定事項6・12）。

### 店舗の閉鎖（#79）

- API：オーナーは `POST/DELETE /api/seller/stores/{id}/closure`、運営は `POST/DELETE /api/operator/stores/{id}/closure`（同じ処理。操作した人の種別で `closing_started_by` を `OWNER` か `ADMIN` にする）。運営のまとめてキャンセルは `POST /api/operator/stores/{id}/order-cancellations`（`{ "reason": "..." }`、必須・500文字まで）。
- 閉鎖を始めると、店舗の行をロックして `closing_started_at`・`closing_started_by` を書く。お会計も店舗の行をロックしてから受付を確かめるので、閉鎖の後に注文はできない。店舗の担当者に「店舗の閉鎖を始めました」、未完了の注文がある購入者に「ご注文の店舗は閉鎖予定です」を送る。未完了の注文がなければ、その場で閉鎖済みになる。
- 閉鎖中は、オーナーが始めた閉鎖はオーナーと運営が、運営が始めた閉鎖は運営だけが取り消せる（オーナーは 403 `CLOSED_BY_OPERATOR`）。閉鎖済みは取り消せない（409 `STORE_CLOSED`）。閉鎖済みの店舗の情報の編集と公開の切り替えも 409 `STORE_CLOSED`。
- 閉鎖済みにするときは、`closed_at` を書き、店舗の担当者に知らせ、`store_members` のその店舗の行を消す（組織への所属は残す。#79 決定事項8）。
- 店舗の応答（`StoreService.Profile`）に `closingStartedBy`・`closedAt`・`openOrderCount`（閉鎖を止めている注文の件数。出店者と運営の店舗一覧だけ、公開ページは null）を足した。

### 組織の停止（#109）

- 3段階：通常（`ACTIVE`）→ 受付停止中（`NOT_ACCEPTING`）→ 停止（`SUSPENDED`）。列は今のまま（`suspension_started_at` と `suspended`）。
- API：`GET /api/operator/organizations`（組織ごとの状態・店舗数・未完了の注文の件数・履歴）、`POST .../{id}/stop-accepting`（理由は必須）、`POST .../{id}/resume`（受付停止の取り消しと停止からの再開。理由は任意）、`POST .../{id}/order-cancellations`（受付停止中だけ。理由は必須）。
- 受付停止にすると、配下のすべての店舗の新しい注文を止める。未完了の注文がなくなった時点で自動で停止にする（#109 の 2026-11-12 の決定）。運営がもう一度「停止」を押す操作は作らない。未完了の注文が残っている組織は、受付停止中のまま停止にならない。止めたいときは運営がまとめてキャンセルする。
- 取り消し・再開で通常に戻しても、停止の間にカートや庭から外れた商品は戻さない（#109）。
- 履歴は `organization_moderation_events`（V3 のマイグレーション）に残す。列の形は `store_moderation_events` とそろえ、種別は `STOP_ACCEPTING`（理由は必須）・`SUSPEND`（自動なので操作した人は空）・`RESUME`。
- お会計は、店舗の行のあと在庫の前に、組織の行を共有ロック（`FOR SHARE`）で読む。受付停止の直前に読んだ値で注文ができ、未完了の注文がないまま停止になることを防ぐ。ロックの順は「店舗 → 組織 → 在庫」と「組織 → 注文 → 在庫」で、輪にならない。

### 閉鎖済み・停止への移行の確かめ方（`ClosureSettlement`）

- 受け渡し（`COMPLETED`）とキャンセルの承認の後、コミットの後で別のトランザクションを開き、その店舗の閉鎖と組織の停止を確かめる。注文の行のロックを持ったまま店舗・組織の行をロックしない（まとめてキャンセルは店舗・組織 → 注文の順にロックするので、逆の順にするとデッドロックする）。
- 支払いの失敗・時間切れなど、ほかの経路で注文がなくなる場合は、1分ごとの定期処理（`kusakari.ec.closure-settlement-interval-ms`、既定 60000）で、閉鎖中の店舗と受付停止中の組織をすべて確かめる。

### 90日後の連絡先の削除

- アプリ内の定期処理（`ClosureSettlement.clearClosedContacts`、`kusakari.ec.store-contact-purge-interval-ms`、既定で1日1回）で、`closed_at` から90日たった店舗の `contact_name`・`contact_email` を空にする。行は消さない。MySQL のイベント（`docs/database-v3-check/store-closure-event.sql`）は作らない（決定 3-1）。
- 失敗はアプリのログに警告として出し、次の回にもう一度試す（イベントの失敗が MySQL のエラーログにしか出ない問題がなくなる）。

### 閉鎖中の店舗の商品と、公開ページ

- 閉鎖中（`STORE_CLOSING`）の商品は、カートから外さず「購入できません」を出す。閉鎖済み（`STORE_CLOSED`）になった時点から、カートを開いたときに外す。組織も同じで、受付停止中（`ORGANIZATION_NOT_ACCEPTING`）は外さず、停止（`ORGANIZATION_SUSPENDED`）から外す。
- 店舗の公開ページは、決定 3-2 のとおり、閉鎖予定（閉鎖中）は「閉店予定」と出し、閉鎖済みは404にする。#79 の決定事項9の「閉鎖から90日間、閉店しましたとお問い合わせ先を表示する」は作っていない。
- 購入者の注文履歴は、受け取る店舗が閉鎖中なら、受け取りの欄に「この店舗は閉鎖予定です。お早めにお受け取りください。」と出す。運営がキャンセルした注文は「この注文は出店者からキャンセルされました（運営から：理由）」と出す。注文の応答に `storeClosing`・`cancelledBy`（`OPERATOR`・`STORE`）を足した。

### 画面

- オーナーの店舗一覧に「閉鎖する」（確認つき）と、オーナーが始めた閉鎖の「閉鎖を取り消す」。状態に「閉鎖中（オーナーが開始・未完了の注文 N 件）」「閉鎖済み」を出す。
- 運営の店舗管理（`/operator/sellers`）を会員管理と分け、利用の停止・再開、閉鎖、閉鎖の取り消し、未完了の注文のまとめてキャンセル（理由つき・確認つき）を置いた。
- 運営の組織管理（`/operator/organizations`）を足した。組織の一覧と状態、受付停止・受付停止の取り消し・停止の解除・まとめてキャンセル（理由と確認つき）、履歴。

## Alternatives

- 閉鎖中の店舗の商品をカートから外す（#79 の決定事項7の 2026-11-12 の変更）：閉鎖中はオーナーが取り消して営業に戻せる。外した明細は戻さないので、取り消したときにカートが元に戻らない。Canvas もすでに `STORE_CLOSING` では配置を残す（決定 4-2）。組織の受付停止（外さない）とも揃えて、外すのは閉鎖済みからにした。
- 閉鎖済みの店舗を90日間「閉店しました」で表示する（#79 の決定事項9）：決定 3-2（閉鎖済みは404）が後で決めた形なので、それに従った。90日の表示を作るなら、公開ページの判定を変え、#119 の照会と合わせる必要がある。
- 受付停止とは別に、運営が「停止」を押す操作を作る：#109 の決定は「未完了の注文がなくなった時点で自動で停止」なので作らない。
- 未完了の注文がある組織の受付停止を拒否する：受付を止めないと注文が増え続けて停止が終わらない（#79 決定事項3・12）。受付停止は常にでき、停止への移行だけを待つ。
- 支払い待ちの注文もまとめてキャンセルする：決済がお会計単位で、ほかの店舗の注文と PaymentIntent を共有しているので、一部の注文だけを取り消すと支払い済みの扱いが崩れる。30分以内に結果が出るので待つ。
- 閉鎖済み・停止への移行を、注文の状態を変えたトランザクションの中で行う：注文 → 店舗・組織の順にロックすることになり、まとめてキャンセル（店舗・組織 → 注文）とデッドロックする。
- 定期処理だけで移行する：受け渡しの直後に状態が変わらず、オーナーや運営の画面の表示が最大1分遅れる。受け渡し・キャンセルの承認ではすぐ確かめ、定期処理はほかの経路の拾い漏れのためにした。
- 組織の履歴を `store_moderation_events` に入れる：店舗への外部キーがあり、組織を指せない。種別の CHECK も別なので、同じ形の別のテーブルにした（決定 3-3）。
- 連絡先の削除を MySQL のイベントで行う（#79 の元の決定）：決定 3-1 のとおり、既存の PC でアプリ用の DB ユーザーに EVENT 権限を付け直せないので採らない。

## Consequences

- マイグレーション `V3__organization_moderation_events.sql` を足した。V1・V2 は変えていない。テーブルは28個になる。
- オーナーの閉鎖は、受け取り待ちの注文がある間は閉鎖中のまま。受け取りに来ない注文の自動の処理はない（決定 1-8）ので、終わらないときは運営がまとめてキャンセルする。
- 閉鎖済みになった店舗は、担当者の店舗一覧から消える。オーナーと運営の一覧には「閉鎖済み」で残る。閉鎖済みの店舗の注文の実績の見せ方は #130 で扱う。
- 支払い待ちの注文が残っていると、閉鎖済み・停止への移行は最大で決済の時間切れ（30分）と定期処理（1分）のあとになる。
- 連絡先を消すまでの日数は90日で固定（設定値にしていない）。試験は `closed_at` を過去にずらし、定期処理の間隔を短くして確かめる。
- 運営の店舗管理の画面は会員管理と分かれた（以前は同じ部品で、店舗の住所とメールの欄を出していた）。
- 確かめていないこと：同時実行（閉鎖・受付停止とお会計を同時に送る）、本番の MySQL（RDS）での動き。
