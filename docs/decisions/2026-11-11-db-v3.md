# EC の DB 構成（v3）：組織・店舗・担当者、決済と返金、閉鎖と停止（#126、#104、#107）

## Context

店舗側アカウントの作り直し（#103）で、購入用のアカウントと店舗側のアカウントを分け、店舗側を「組織 → 店舗 → 店舗ごとの担当者」にした。あわせて、決済と返金（Stripe のテストモード）、販売手数料、店舗の閉鎖、組織の停止、組織のロール、招待キー、運営の警告の履歴を扱う。既存のデータは移行せず、DB を初期化して作り直す（#102 決定事項2）。

API は起動時に、エンティティとテーブルが合っているかを確かめる（`spring.jpa.hibernate.ddl-auto=validate`）。そのため、マイグレーションとアプリは同時に新しい構成へ切り替える必要があった。

ER 図・制約・公開の条件・注文と決済の流れは [../database-er.md](../database-er.md)、テーブル定義はマイグレーション（`backend/src/main/resources/db/migration/` の V1〜V3）にある。

## Decision

### マイグレーション

- `V1__schema.sql`（27テーブル）、`V2__sample_data.sql`（サンプルの組織1つ・店舗3つ・カテゴリー5つ・商品14件・在庫・素材コードの対応16件）、`V3__organization_moderation_events.sql`（組織の受付停止・停止・再開の履歴）の3本にする。旧構成（V1〜V15）からは移行しない。
- 旧構成の DB は Flyway の履歴が合わないので、そのままでは起動しない。`DB-reset.bat`（[手順](../database-reset.md)）で作り直す。
- サンプルの商品は、1商品1店舗に合わせて3つの店舗に置く。店舗1：オリーブ・ラベンダー・ローズマリー・モンステラ。店舗2：Canvas のモデルに対応する4件。店舗3：庭のデモ用の6件。
- サンプルの組織（ID 1）には、マイグレーションではオーナーを入れない。`DB-reset.bat` と `setup.bat` が最後に、テスト用アカウントの会員と種別をそろえ、オーナーを付ける（`scripts/set-test-accounts.ps1`、[テスト用アカウント](2026-11-15-test-accounts.md)）。

### 会員・組織・店舗

- 種別は会員の列1つ（`members.account_type`）で決める。`USER`（購入者）・`SHOP_OWNER_APPLICANT`（申請中の法人用アカウント）・`SHOP_OWNER`（オーナー）・`SHOP_STAFF`（子アカウント）・`ADMIN`（運営）の5種類（[会員の種別とロールの値](../member-roles.md)）。
- オーナーは組織に1人で、所属（`organization_members`）や担当（`store_members`）には入れない。
- 店舗の操作のロール（`MANAGER` / `STAFF` / 未割り当て）は店舗の担当（`store_members.role`）に、組織のロール（`ORG_ADMIN` / なし）は組織への所属（`organization_members.role`）に持つ。2つは受け持つ操作が重ならない。
- 会員テーブルは `members`、出店申請は `organization_applications` とする。申請の対象は店舗ではなく組織で、承認すると申請者が `SHOP_OWNER` になり、組織ができる。店舗はオーナーが審査なしで作り、作った直後は非公開。
- 出店申請は、1人につき「今の申請」と「前回の申請」の2行まで持つ（`is_latest` と `(applicant_member_id, is_latest)` の一意キー）。再申請は1つのトランザクションで「前々回の行を消す → 今の申請を前回にする → 新しい申請を作る」の順に行う。前回にできるのは、却下・取り下げ済みの申請だけ（CHECK）。料金プランは作らないので、申請に `plan` の列はない（#125）。
- 会員に、メール確認の日時（`email_verified_at`）と作成日時（`created_at`）を持つ。アカウントを自動で削除する処理は作らない。
- 店舗の公開は、オーナーの公開（`stores.published`）と運営の停止（`stores.suspended`）の2つの列に分ける。運営が停止を解除しても、オーナーがまだ公開していない店舗は公開されない。組織の停止も `suspended` の名前にそろえる。
- 店舗の緯度経度は空（位置なし）にできる。片方だけの入力は DB が拒否する。
- 店舗の閉鎖は `stores.closing_started_at`・`closing_started_by`（`OWNER` / `ADMIN`）・`closed_at` の3列で表す。閉鎖中を経ない閉鎖済みと、誰が始めたか分からない閉鎖は DB が拒否する。閉鎖済みになってから90日たった店舗の連絡先（担当者名・連絡用メール）は、アプリ内の定期処理（1日1回、`ClosureSettlement`）で消す。MySQL のイベントは使わない。店舗・商品・在庫の行は消さない。
- 組織の停止は「通常 → 受付停止中 → 停止」の3段階で、`organizations.suspension_started_at` と `suspended` から決まる。組織の行を1つ書き換えるだけで、配下のすべての店舗の新規注文の受付が止まる。受付停止を経ない停止は DB が拒否する。受付停止・停止・再開の履歴は `organization_moderation_events`（V3）に残す。
- 招待キーは `store_invitations.max_uses`（1 = 1回限り、空 = 期限内なら何回でも）を持ち、使った人を `store_invitation_uses` に1人1行で残す。キーのテーブルに組織の列は持たない（店舗からたどれる）。上限回数を超えないことは DB の制約では守れないので、アプリがキーの行をロックしてから使用の記録の件数を確かめる。
- ログイン情報の API（`GET /api/auth/me`）は、`accountType`・`organizationId`・`storeIds` を返す。

### 商品・カート・注文

- 商品は1つの店舗に属し（`products.store_id`、登録後は変えない）、在庫と公開状態は商品と1対1（`inventory` の主キーが `product_id`）。商品の削除は在庫の公開状態 `DELETED` で表し、`products.active` は持たない。商品番号は店舗の中だけで一意（`(store_id, sku)`）。
- カートは店舗を持たない。受取店舗は商品の店舗で、購入者は店舗を選ばない。お会計は受取店舗ごとに注文を1件作る。発送用の列は作らない。
- 受取連絡先と支払方法は `orders` に持ち、`order_details` は作らない。送料がないので、金額は `total_yen` だけ。
- 誰がキャンセルしたかを `orders.cancelled_by_member_id` に記録する。購入者のキャンセル申請の状態（`cancellation_status`）は申請の状態だけを表し、運営がまとめてキャンセルしても変わらない。
- 販売手数料は、注文したときの率と額を `orders.commission_rate_bp`（1万分率。800 = 8%）と `orders.commission_yen` に保存する。率は設定値 `kusakari.ec.commission-rate-bp`（既定 800）、額は合計に率を掛けて1円未満を切り捨てる。あとで率を変えても、過去の注文の手数料は変わらない（[手数料の決定](2026-11-13-commission-and-closed-store-sales.md)）。
- 運営の警告・警告解除・停止・再開の履歴は、商品と店舗で別のテーブル（`product_moderation_events`・`store_moderation_events`）に、同じ列の形で持つ。「今、警告中か」は列で持たず、最新の履歴から求める。理由のない警告・停止は DB が拒否する。
- してはいけない組み合わせは、アプリの確認に加えて DB の制約（複合外部キー・一意キー・CHECK）でも拒否する。トリガーは使わない。

### 決済と返金

- Stripe のテストモードだけを使い、実際のお金は動かさない（ルールは [残りの決定](2026-11-12-remaining-decisions.md) の 1-1〜1-17、実装は [カード決済の決定](2026-11-13-stripe-card-payment.md)）。
- `payments`：お会計1回につき1行。`(cart_id, request_id)` の一意キーで二重の請求を拒否する。
- `stripe_events`：処理済みの通知を、通知の ID を主キーにして記録する。同じ通知の2回目は主キーの重複で止まり、在庫・通知・返金を二重に処理しない。
- `refunds`：注文1件につき1行。`order_id` の一意キーで二重の返金を拒否する。金額はその注文の合計で、1つの決済に対する一部返金になる。
- 注文は同じお会計の決済だけを、返金はその注文が支払われた決済だけを指せる（どちらも複合外部キー）。
- カードの注文は支払い待ち（`PENDING_PAYMENT`）で作り、在庫はこの時点で確保する。店頭払いは決済を作らず、注文を受付済み（`ACCEPTED`）で作る。

### アプリの認可

- オーナーは自分の組織の全店舗、子アカウントはロールの付いた店舗、運営は全店舗を操作できる。
- 商品の登録・削除、店舗情報の編集、キャンセル申請への回答は、オーナーか `MANAGER`。商品の編集（価格を含む）・公開・非公開、在庫、注文の受け渡しは `STAFF` 以上（[残りの決定](2026-11-12-remaining-decisions.md) の 2-1）。商品の削除は、公開状態を変える API から行っても `MANAGER` 以上。
- 店舗側のアカウントと申請中のアカウントは、カート・注文・庭の買い物リストを使えない（403 `BUYER_REQUIRED`、同 2-6）。

## Alternatives

- 旧マイグレーション（V1〜V15）の後ろに V16 以降を足して移行する：既存のデータを移行しないと決めていて（#102）、15本の履歴を残す理由がない。
- マイグレーションだけを先に置き換える：起動時の `validate` で API が起動しなくなる。
- #104 のコメントの決定を、名前も列も変えずにマイグレーションにする：改定が重なっていて、どれが最新かを追えない。1つの構成にまとめ直した。
- 会員テーブルの名前 `auth_members` を残す：残す理由が「書き換えが増える」だけで、互換性が要らない。
- 出店申請を1人1行にして、再申請で同じ行を書き換える：前回の申請の内容と却下の理由が残らない。再申請のたびに行を増やす形は、行が増え続ける。
- 商品を組織のものにし、店舗ごとの在庫を持つ：受取店舗を購入者が選ぶ必要が出て、「商品の店舗で受け取る」（#70）と食い違う。
- `products.active` を残す：公開状態と二重になり、どちらが正しいか分からなくなる（#122）。
- カートに「閲覧中の店舗」を残す：受取店舗と混同される（#104 対応策9）。
- カートのテーブルをなくし、会員に直接明細を持たせる：注文と庭の買い物リストがカートの ID を使っていて、得るものが少ない。
- 店舗の公開を `enabled` 1つで持つ：運営が停止を解除したときに、オーナーが公開していない店舗まで公開される。
- 緯度0・経度0を「位置なし」の印にする：店舗の案内で距離が約14,000 km と計算される。
- `organizations.owner_account_type` の値を組織寄りの名前にする：複合外部キーのための固定値で、`members.account_type` の値と同じでなければ外部キーが成り立たない。
- 返金を注文の列（返金の ID・金額・状態）として持つ：二重の返金を一意キーで止められず、Stripe の管理画面からの返金や失敗した返金のやり直しを記録しにくい。
- 注文に「返金済み」の状態の列を足す：返金の行と同じ事実を2か所に持つことになる。
- 決済の ID だけを注文に持ち、複合外部キーにしない：注文が別のお会計の決済を指す誤りを DB が拒否できない。
- 支払いが成功してから注文を作る：支払い中にほかの人が同じ在庫を買えてしまう。
- 店舗の閉鎖を状態の列1つで持つ：閉鎖を始めた日時と閉鎖済みになった日時が別に要る（90日の判定に使う）。
- 組織の受付停止を店舗ごとの列で持つ：取り消しや再開で店舗の状態を戻す手間が要り、受付停止中に作った店舗が止まらない。
- 招待キーに使用回数の列だけを足す：何回でも使えるキーで誰が入ったかが残らない。
- 店舗の担当のロールに `AREA_MANAGER` などを足す：店舗ごとの行に組織全体の権限を持たせることになり、行ごとに食い違うとどれが効くか決まらない。
- 警告の履歴を1つのテーブルにして、対象の種別と ID の列で表す：対象に外部キーを張れない。
- 閉鎖した店舗の連絡先を MySQL のイベントで消す：アプリ用の DB ユーザーに EVENT 権限が要り、`event_scheduler` が `ON` のときだけ動き、失敗が MySQL のエラーログにしか出ない。アプリの定期処理なら失敗がアプリのログに残り、次の回にやり直せる（[残りの決定](2026-11-12-remaining-decisions.md) の 3-1）。

## Consequences

- DB を初期化するので、作り直す前の会員・店舗・商品・注文は失われる。EC と Canvas の片方だけを初期化すると、庭の持ち主（EC の会員 ID）と、買い物リストが持つ庭 ID が食い違うので、2つの初期化は続けて行う。
- 認証基盤（Cognito）のユーザーは消さない。初期化の後、初めてログインしたときに会員が作られる。
- お会計は、店舗（ID の順）→ 組織 → 商品 → 在庫（商品 ID の順）の順にロックする。商品の編集も「商品 → 在庫」の順にロックするので、輪にならない（`CheckoutService`）。
- Stripe の秘密鍵と、通知の署名の検証に使う秘密の値は環境変数で渡し、DB・Git・ログ・テストの成果物に入れない。
- `GET /api/stores/{id}` は、購入者・未ログインには公開中と閉鎖中の店舗だけを返し、非公開・停止・閉鎖済み・停止した組織の店舗は 404 にする。担当者・オーナー・運営は自分の扱える店舗を見られる。
- 次のことは決まっていないので、DB に持たない：出店規約に同意した記録（#15）、同じ品種の商品をジャンルでまとめて表示すること、発送（自宅配送。#120 は「発送は行わない」の決定案のまま）。
- 旧構成（V1〜V15）の表・列との対応、決める前の経緯、制約の試験の記録は、[kusakari-document の DB構成](https://github.com/abeouga/kusakari-document/tree/main/kusakari-ec/DB構成) にある。
