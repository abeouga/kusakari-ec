# 運営の警告と、商品・店舗の停止の履歴の実装（issue #16）

## Context

商品・店舗の停止の前に運営が出店者へ警告する段階は、2026-11-12 に流れと規則を決めた（[決定の記録](2026-11-12-moderation-warning.md)、#16 のコメント）。履歴のテーブル `product_moderation_events`・`store_moderation_events` は V1 のマイグレーションに入っていたが、アプリから使っておらず、運営の商品の停止も店舗の停止も履歴に残っていなかった。店舗の停止は理由を受けず、出店者に通知していなかった。

実装にあたり、決定の記録に書いていない次のことを決める必要があった。

- API の形（今の停止の API を残すか、操作の種別を受ける1つの API にするか）
- 同じ操作を2回送ったとき（すでに停止している商品の停止、警告していない対象の警告解除）の扱い
- 停止・再開で警告をどうするか。停止中の対象に警告できるか。閉鎖した店舗をどうするか
- 出店者の商品一覧に警告を出すための API（商品の応答は購入者・Canvas と共通）
- 通知のタイトル
- #16 のコメントで別にすると書いた「停止中の商品がカートに残ると購入できるかもしれない」件

## Decision

### データ

- マイグレーションは足さない。V1 の2つのテーブルをそのまま使う。Java では操作の種別を共通の enum（`ModerationAction`：`WARN`・`CLEAR_WARNING`・`SUSPEND`・`RESUME`）にし、2つのテーブルの Entity は同じ形にした。
- 「今、警告中か」は、警告と警告解除のうち最新の行が `WARN` かどうかで求める（決定のとおり。対象の列は足さない）。
- 理由は画面と API で500文字まで（今の商品の停止・組織の停止と同じ。DB は1000文字）。警告と停止は必須（400 `REASON_REQUIRED`）、警告解除と再開は任意。

### API

- 停止・再開は今の API を残し、履歴と通知を足した。商品は `PUT /api/operator/products/{id}/moderation`（`suspended`・`reason`）、店舗は `PUT /api/operator/stores/{id}/enabled`（`enabled`・`reason`）。店舗の停止は理由が必須になった。
- 警告・警告解除は、商品と店舗で同じ形の `PUT /api/operator/{products|stores}/{id}/warning`（`warned`・`reason`）にした。
- 履歴は `GET /api/operator/{products|stores}/{id}/moderation-events`（新しい順、操作した運営者の表示名つき）。
- 応答は、どの操作も操作の後の状態（`suspended`・`warning`）。
- 運営の商品一覧（`GET /api/operator/products`）と、店舗の応答（`StoreService.Profile`）に `warning` を足した。店舗の応答は購入者にも返すので、`warning` は出店者と運営にだけ入れ、購入者・未ログインには null にする（決定9「購入者の画面には何も出さない」）。
- 出店者の商品一覧には、`GET /api/seller/products/moderation?storeId=` を足した（警告中か運営が停止している商品と、警告の理由）。商品の応答（`ProductView`）は購入者の画面・Canvas と共通なので、項目を足さない。

### 操作の規則

- どの操作も、対象の行をロックしてから、履歴に1行足し、出店者（組織のオーナーと、ロールが割り振られた担当者。`NotificationService.toStore`）に通知する。
- 停止中の停止・停止していない対象の再開・警告していない対象の警告解除は、何もしない（履歴も通知も足さない）。今の商品の停止が同じ扱いで、二重送信で履歴と通知が重ならない。警告は、警告中でも毎回1行足す（決定4「重ねての警告」）。
- 停止・再開しても、警告は自動では解除しない（決定3「解除は運営だけ」）。停止中の対象にも警告できる。
- 閉鎖済みの店舗には、警告・停止・再開のどれもできない（409 `STORE_CLOSED`。閉鎖済みの店舗の編集と同じ）。閉鎖中の店舗にはできる。
- 通知のタイトル（`notifications` に種別の列は足さず、タイトルで区別する）：
  - 商品：「商品に運営から警告がありました」「商品への運営の警告が解除されました」「商品の公開を停止しました」「商品の公開停止を解除しました」（停止・解除は今のタイトルのまま）
  - 店舗：「店舗に運営から警告がありました」「店舗への運営の警告が解除されました」「店舗の利用が停止されました」「店舗の利用停止が解除されました」
  - 本文は「対象の名前 / 理由」（理由がなければ名前だけ）。

### 画面

- 運営の商品の審査（`/operator/products`）と店舗管理（`/operator/sellers`）に、共通の部品（`Moderation.jsx`）を置いた。警告中のバッジと理由、「警告する」「警告を解除」、停止中なら通常の位置に「再開」、履歴（開いたときに読む）、停止していなければ「デンジャーエリア」に「停止」。
- 停止・再開は確認ダイアログを経る（決定7）。警告と警告解除も、理由を入れるために同じダイアログを使う。理由が必須の操作で空のまま確定すると「理由を入力してください。」を出す。
- 店舗管理の「利用を停止／利用を再開」のボタンは、この部品に移した（停止はデンジャーエリア）。
- 出店者の店舗一覧（`/seller/stores`）の状態の欄と、店舗情報の編集（`/seller/profile`）に、警告中のバッジと理由を出す。商品管理（`/seller/products`）には、一覧の上に「運営からの警告・停止」の欄（商品名・理由）を、各行に「警告中」「運営により公開停止中」のバッジを出す。一覧は25件ごとに分かれるので、ほかのページの商品の警告も上の欄で分かるようにした。

### 停止中の商品のお会計（#16 のコメントの「別の issue にする」件）

- 直した。お会計は、店舗の行と組織の行の後、在庫の行の前に、商品の行を ID の順に共有ロック（`FOR SHARE`）で読み、運営が停止した商品があれば 409 `OUT_OF_STOCK`（カートの確認で止まるときと同じ）を返す。
- 理由：今までの確かめ（`CartService.view` の `purchasable`）はロックしない読み取りで、トランザクションの最初の読み取りの時点の値を見る。停止のコミットがその後なら、停止した商品の注文が1件通ることがあった。商品の停止は商品の行を排他ロックするので、共有ロックで読めば、停止の途中ならコミットを待ち、停止の後の値で判定する。
- ロックの順は「店舗 → 組織 → 商品 → 在庫」になる。商品の編集は「商品 → 在庫」、商品の停止は「商品」だけなので、輪にならない。
- 別の issue は立てない（この変更で直したため）。

### ユースケース

- 警告は、別のユースケースに切り出さず、EC-A10・EC-A11 の中の流れとして扱う（停止と同じ画面・同じ対象で、操作の前後の関係が強いため）。

## Alternatives

- **操作の種別を受ける1つの API（`POST .../moderation-events` に `action`）にする**：今の停止の API を使っている画面・試験・手順をすべて変えることになる。停止・再開の意味は変わらないので、今の API を残し、警告だけを足した。
- **同じ操作を2回送ったら 409 にする**：今の商品の停止は何もしない扱いで、試験もそれに合わせている。画面は操作の後に最新の状態を読み直すので、何もしない扱いで足りる。
- **停止したら警告を自動で解除する**：決定3（解除は運営だけ）と合わない。停止の後に再開しても、運営が確かめるまで警告は残るほうが、出店者にも分かりやすい。
- **商品の応答（`ProductView`）に警告を足す**：購入者の画面と Canvas の照会も同じ応答を使っているので、購入者に出さない決定（決定9）と合わない。
- **停止中の商品のお会計は記録だけにする**（remaining-issues の有力な案の一つ）：直し方が小さく（ロックしたうえでの読み取り1回）、ロックの順も輪にならないので直した。
- **お会計で商品の行を排他ロックする**：お会計どうしが同じ商品で待ち合うことになる。停止との関係だけを見ればよいので、共有ロックにした。
- **在庫の行のロックの後に商品の行を読む**：商品の編集（商品 → 在庫）と逆の順になり、デッドロックする。

## Consequences

- API の変更：店舗の停止（`PUT /api/operator/stores/{id}/enabled` の `enabled:false`）は理由が必須になった。商品の停止・再開と店舗の停止・再開の応答は、`{ "suspended", "warning" }` になった（以前は `{ "suspended" }`・`{ "enabled" }`。画面は読んでいなかった）。商品の再開の理由は空でよくなった（以前は空でない理由が必須）。`reason` の項目自体は、ほかの API と同じく、欠けると400 `INVALID_INPUT`。
- 業務 E2E のうち、店舗を停止する2件（`business-boundaries`・`business-purchase-restrictions`）は、停止の理由を送るように直した。
- 店舗が停止されても、出店者は通知（`/api/notifications`）を見られる。E2E で店舗の停止の通知が届くことを確かめた。
- ユースケースの記述（EC-A10・A11・S11）は、この EC のリポジトリにはなく、別のリポジトリ（`kusakari_document`）にある。この変更では直していない。
- 確かめていないこと：本番の MySQL（RDS）での動き。お会計と停止の同時実行は、E2E で停止と同じロックを持つトランザクションを DB に直接作って確かめた（運営の API そのものとの同時実行ではない）。
