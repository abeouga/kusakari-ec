# v3 の前に売っていた31商品の移し替えと、商品を追加した人の記録

## Context

DB 構成 v3（[記録](2026-11-11-db-v3.md)）で DB を作り直したとき、v3 の前に店舗1で売っていた31商品（2026-10-19 に書き出した `sample-data/products-20261019/`）は、初期データ（V2）に入らなかった。31商品は `scripts/import-product-sample.mjs` を手で流した PC にしかなく、PC ごとに商品が違っていた。今の初期データは店舗1の4商品（`olive`・`lavender`・`rosemary`・`monstera`）と、店舗2・3の10商品だけ。

v3 の前の DB を確かめると、31商品は sample-data と同じ ID・価格で、在庫だけがテストの注文で少し違っていた。残りの15商品のうち14商品は V2 に同じ ID で移してあり、「実演用・紫の草花」だけはどこにもない。

v3 の前は、商品に追加した会員（`products.owner_member_id`）を持っていた。v3 では商品は1つの店舗に属し、追加した人の列はない。店舗の担当者が複数いるので、どの商品を誰が登録したかを、店舗の商品管理と運営の画面で分かるようにしたい。

2026-11-20 に、ユーザーが下の案で決めた。

## Decision

### 31商品を Flyway のマイグレーションで入れる（V7）

- 31商品を、組織1（Kusakari サンプル組織）の店舗1（二子玉川ガーデン、`store_id=1`）の商品として入れる。ID・商品番号・価格・植物モデルの設定と構成は sample-data のまま、在庫は書き出したときの値、公開状態は `PUBLISHED`。素材コード（`product.{商品ID}`）の対応も入れる。画像は `frontend/public/images/` にあるものを使う。
- 店舗1にある4商品は削除済み（`inventory.publication_status='DELETED'`）にする。注文や庭から参照されるので、行は消さない。削除済みにするのはこの4商品だけで、各 PC で店舗の画面から店舗1に登録した商品は変えない（`import-product-sample.mjs` は店舗1のすべての商品を削除済みにしていた）。
- ほかの PC には、EC を起動したときの Flyway のマイグレーションで自動で入る。手で流すコマンドは要らない。
- `import-product-sample.mjs` をすでに流した PC でも失敗せず、商品が重ならないように、同じ ID の商品は sample-data の値で上書きし、素材コードの対応は入っていなければ足す。在庫も書き出したときの値に戻る。
- 「実演用・紫の草花」は移さない。
- 31商品の元の JSON（`sample-data/products-20261019/`）と、手で流すスクリプト（`import-product-sample.mjs`、`verify-product-sample.mjs`）は消す。マイグレーションが正本になり、JSON を残すと2つの写しが食い違うため。README にあった MySQL のセッションの時刻の決定は、[別の記録](2026-10-19-mysql-utc-session.md)に移した。商品の画像（`frontend/public/images/`）は残す。

### 商品を追加した人（`products.created_by_member_id`）

- `products` に、商品を追加した会員の列 `created_by_member_id`（`members(id)` への外部キー、空を許す）を足す。v3 の前の `owner_member_id` という名前は、v3 では組織のオーナーと紛らわしいので使わない。
- 店舗の画面で商品を登録したとき、ログインしている会員を記録する。編集では変えない。
- 初期データの商品（31商品と、V2 の店舗2・3の10商品と店舗1の4商品）は空のまま。運営の初期データとして扱う。テスト用アカウント（[記録](2026-11-15-test-accounts.md)）の会員はマイグレーションの後にスクリプトが PC ごとに違う ID で作るので、マイグレーションでは特定の会員を入れられない。
- 会員は消さない（退会は `members.enabled=false` と `withdrawn_at`、除名は `organization_members.expelled` の論理削除）。追加した人が退会・停止・除名されても記録は残し、画面には表示名をそのまま出す。担当者の操作の履歴（`organization_member_events`）と同じ扱い。
- 追加した人の表示名は、店舗の商品管理（その店舗の一覧を見られる担当者）と運営の商品の画面に出す。空のときは「初期データ」と出す。購入者向けの商品の API と画面には出さない。

## Alternatives

- sample-data を残し、手で流すスクリプトで入れ続ける：PC ごとに商品が違う状態が続き、DB を作り直すたびに流し直す必要がある。
- 起動時のアプリの処理で JSON を読んで入れる：一度だけ入れるという意味が Flyway の履歴に残らず、マイグレーションのチェックサムで中身の変更も検出できない。
- Java のマイグレーションで JSON を読む：JSON を書き換えるとマイグレーションの意味が変わってしまう（チェックサムに入らない）。SQL にした。
- 31商品の追加した人をテスト用の担当者（manager01 など）にする：会員がマイグレーションの後に PC ごとに違う ID で作られるので入れられない。
- 追加した人が退会・除名されたら名前に状態を添える：担当者の操作の履歴と扱いがずれるので、表示名をそのまま出すことにした。
- 購入者にも追加した人を出す：店舗の中の担当の分担は購入者に関係がないので出さない。

## Consequences

- V7 は31商品の植物モデルの構成を含むので、約6MB の SQL になる。
- 31商品を店舗の画面で編集・在庫変更していた PC では、V7 を当てたときに sample-data の値に戻る（`import-product-sample.mjs` を流し直したときと同じ）。
- 店舗1の4商品は削除済みになり、購入者の一覧と Canvas の商品一覧から消える。庭に置いてあれば、販売を終えた商品として出る。
- 追加した人がいない商品は、今ある商品（V7 より前に登録した商品を含む）すべて。V7 より前に店舗の画面で登録した商品は、追加した人を後から埋めない。
