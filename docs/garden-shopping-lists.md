# 庭の買い物リスト

## Context

2026-10-16の要件変更で、Canvasの庭別リストとECの購入用カートを分離する。

## Decision

EC `/cart` の「カート」「庭の買い物リスト」セグメントで切り替える。庭別一覧は `/cart#garden-shopping-lists` に表示し、`/cart/gardens/{gardenId}` で購入商品を選択する。初期未選択とし、全選択・個別選択・選択解除に対応する。リストの必要数はCanvasの配置数から決まり、ECカートへ追加後の数量は従来どおり編集できる。

ECサーバーがCanvasの集計APIを呼ぶ。接続先は既存の `KUSAKARI_CANVAS_API_URL` を使う。写真や3D構成は受け取らず、商品ID・材料コードからECの商品・価格・選択店舗の在庫を解決する。旧配置の候補が複数ある場合は購入商品を選択させる。

選択分をカートへ加算するAPIは `POST /api/cart/shopping-lists/{gardenId}/items`。庭とカートのrevision、行キーと商品IDだけを受け取り、数量はサーバーで再取得する。在庫不足・販売終了・数量上限・種類上限は商品単位で見送り、成功分を一つのトランザクションで追加する。同じ商品の数量は合算する。古いrevisionでは変更せず409を返す。

一部成功時はカートへ移動して結果と見送り理由を表示し、全件見送り時はリスト画面に留まる。庭を編集してもECカートの数量は変えない。買い物リストはカートへの追加後も保持される。

## Alternatives

Canvasによる直接カート更新と、リスト全件の自動追加は行わない。独立したリストテーブルは作らず、庭の配置を正本とする。

## Consequences

DB変更は不要で既存カートを保持する。Canvasが停止している場合はリストだけに取得エラー・再取得を表示し、ECの通常のカート・注文操作を維持する。所有者は現行のローカルデモ範囲を維持し、画面モックのアカウント情報を認証に利用しない。

## Verification

Canvasで `npm run test:shopping`。ECの既存購入・出品の回帰は `npm run test:shopping-regression`。専用MySQLと実APIを使い、庭別分離・即時反映・選択追加・部分成功・上限・競合・保存復旧を確認する。詳細なAPI契約と結果の保存先はCanvasの `docs/garden-shopping-lists.md` を参照する。
