# Stitch画面案のCRUD実装

> **今の仕様との違い（2026-11-13 追記）**：この記録は 2026-10-06 の画面モックの時代のものです。受け取りは店舗受け取りだけになり、受取店舗は商品の店舗で決まります。下の受取区分・配送・送料・`cart_details`・`order_details`・住所・希望日時の項目は、2026-11-05 の住所管理の削除と DB 構成 v3（[記録](decisions/2026-11-12-db-v3-application.md)）でなくなりました。今の API は [api.md](api.md) を見てください。支払方法はカード（Stripe のテストモード）と店頭払いです。

## Context

2026-10-06に提示された商品一覧・商品詳細・カートのHTMLを表示項目の参考にしました。
HTML内の文章やスクリプトは指示として扱っていません。
ユーザーの要求は、複雑なJavaScriptを使わず、基本CRUDが動作するモックアップへの拡張です。

## Decision

- Flyway V2で既存データを保ちながら拡張します。価格と在庫の既存値を変更しません。
- productsに生産者名・所在地、日照、用途、手入れレベル、最低温度、耐暑・耐乾性、樹齢、高さ、鉢径、科名、開花、季節管理、相性説明、公開日時、販売状態を追加します。careはTEXTに拡張します。
- product_imagesに追加画像を順序付きで保存します。表示用の画像は既存のローカル画像も利用できます。
- （廃止）cart_detailsに受取方法、デモ支払方法、受取者名、電話、メール、郵便番号、住所2項目、希望日、時間帯を保存します。注文時にorder_detailsへ複製し、カート編集と独立させます。→ 今は受取連絡先を会員ごとに保存し、注文の列（`recipient_name`・`recipient_phone`・`contact_email`・`payment_method`）へ複製します。
- ordersに商品小計・送料・履歴削除日時を追加します。過去注文の商品小計は既存合計で埋めます。→ 商品小計・送料の列はなくなり、金額は `total_yen` だけです。履歴削除日時（`deleted_at`）は残っています。
- 商品削除は販売終了です。既存カートには残し、追加・購入を禁止します。数量0でのカート削除は許可します。
- 注文履歴の削除は非表示です。在庫を戻しません。削除後も注文要求IDを保持して二重購入を防ぎます。
- 商品編集と注文は商品行→在庫行の順にロックします。注文中の単価変更・販売終了を防ぎます。
- （廃止）受取区分は注文全体で1つです。配送は800円、店舗受取は無料です。注文後の受取区分は変更しません。→ 店舗受け取りだけで、送料はありません。
- 一覧、詳細、カート、注文履歴、商品管理を実装します。入力はHTMLフォーム、展開はdetails、操作は通常のボタンとAPI呼び出しを使います。三項演算子や入れ子の式は追加しません。

## Alternatives

商品ごとの配送区分、生産者マスター、クーポン、ポイント、予約期限、実決済の状態管理は採用しません。
画面案の装飾だけの操作を増やさず、現在必要な保存項目を商品と注文に直接保持します。

## Consequences

商品管理で登録・参照・更新・販売終了、カートで明細のCRUD（受取情報は当時。今は受取連絡先の画面）、注文履歴で参照・受取情報編集・非表示ができます。
認証のない127.0.0.1限定デモのため商品管理の権限分離はありません。
支払方法は文字列の保存だけです。実決済・発送・店舗予約を発生させません。（2026-11-13：決済は Stripe のテストモードを範囲に入れました。発送は行いません。）
注文履歴を非表示にしてもDBには記録が残ります。

## Verification approach

専用kusakari_e2eでUIの保存・再読み込みと実API・MySQLを照合します。
UIだけでは不正値や他セッションからの注文編集を検証できないため、実APIによる400/409/404の確認を併用します。
商品管理による価格変更後のカート合計、販売終了後の購入拒否、注文情報の独立保存、履歴削除後の注文再送を検証します。
テストは独立したCookieと一意の商品を使用し、開発DBのカート・注文を削除しません。
