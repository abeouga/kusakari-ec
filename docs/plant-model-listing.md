# 植物特徴とCanvasのGLB部品構成

2026-10-17更新：第2版では24部品・10構成規則を使用し、特徴から構成した30商品を店舗1のローカルカタログへ追加しました。出品フォームは針葉樹・株立ち・横広がり・グラス・ロゼット・つる・ヤシにも対応します。旧版の商品・庭は以前の構成を保持します。以下の6部品の記述は初期版の記録です。

## Context

商品の園芸情報はECが管理する。出品者は完成済み3Dモデルを選ばず、植物の特徴を入力し、あらかじめ制作した共通GLB部品から構成を決める。

## Decision

- 出品フォームの「庭オブジェクト」で庭への配置を有効にすると、植物の形態、幅、全体形状、幹・枝、葉、花を入力できる。高さは「植物の特徴」の既存 `heightCm` を共用し、一度だけ入力する。高さの表記は土際から最高点まで（鉢を含まない）に統一する。既存の保存値は変換しない。販売カテゴリーと植物の形態は異なる分類なので別に保持する。
- プレビューはCanvasの `/model-preview` を埋め込む。特徴を変更した後はプレビューボタンで再確認する。
- 保存リクエストは `plantModelProfile` を送る。ECバックエンドがCanvasの `POST /api/model-assemblies/resolve` を呼び、返された部品構成を `modelComposition` として商品に保存する。クライアントに確定構成を指定させない。
- 商品APIとカート内の商品は、プロフィール・構成・`canvasMaterialCode` を返す。価格・在庫・カート・注文は引き続きECの正本を使う。
- 材料コード `product.<商品ID>` を当該商品だけに関連付け、既存の材料照合APIで配置数量から同じ商品を購入候補にできる。
- 特徴を変更しない在庫編集は保存済み構成を再利用する。旧クライアントが追加フィールドを省略した更新も構成を保持する。明示的なnullはモデル設定解除として扱う。
- 植物構成の更新が必要な保存でCanvasへ接続できない場合、商品更新をロールバックしてエラーを返す。
- JSON列はFlyway V4で追加する。既存商品の設定はnullで、従来の登録・編集リクエストも受け付ける。

## Setup

ECの `start.bat` とCanvasの `start.bat` で双方を起動する。

- ECサーバーからCanvas API：`KUSAKARI_CANVAS_API_URL`（既定 `http://127.0.0.1:8080`）
- 出品プレビュー：`VITE_KUSAKARI_CANVAS_URL`（既定 `http://127.0.0.1:5173/`）

部品の制作・接続点・構成契約はCanvasの `docs/modular-plant-models.md` に記載する。

## Alternatives

完成モデルのプルダウン選択は要件に合わない。表示時の形状生成やGLB生成は行わず、登録済み部品を保存済み変換で描画する。

## Consequences

新しい特徴に対応するにはCanvasの部品・規則を追加する。Canvasの庭は配置時の構成を持ち、商品の後日編集で既存庭の形状は変わらない。初期ライブラリは汎用部品6種類で、商品写真からの自動復元機能は含まない。

## Verification

ECの `npm run build:api` 後、Canvasで `npm run test:shopping` を実行する。専用MySQLを使い、各植物タイプ2パターンの出品プレビュー・登録・商品一覧と庭の買い物リストからのドラッグ・庭の保存復元・写真表示・旧固定GLBとの混在を検証する。成果物はCanvasの `artifacts/e2e/plant-model/` に保存する。
# 旧モデル応答の互換性（2026-10-18）

## Context

旧保存データのモデル構成profileにはbotanicalFormが存在しない。一方、商品側の型付きprofileとCanvasのGardenDocumentは未指定値をnullで返すため、同じモデルを配置・再読込した際の構造比較が不一致になる。

## Decision

商品APIのDTO変換で、旧モデル構成のprofileに限り未指定のbotanicalFormをnullとして返す。元のDB JSONには触らず、モデルのversion・部品・寸法・配置を維持する。JSONをその場で変更して購入トランザクションの変更検出に巻き込まないよう、応答用のprofileを分ける。

## Alternatives / Consequences

全商品再生成、既存JSONの一括更新、テスト期待値の緩和は採用しない。値を持つ植物別モデルはそのまま返す。旧6種の配置・再読込・カート転送を実API/MySQLで再検証し、元のseed JSONのハッシュも前後で比較する。

## 販売停止時の旧JSON保持（2026-10-18）

### Context / Decision

カタログ整理で旧14商品を販売停止した際、エンティティの全列更新により旧プロフィール7件に
未指定の `botanicalForm:null` が保存されることを実DB照合で検出した。
`ProductRepository.archiveById` は販売状態だけを更新し、プロフィールや構成を読み直して書き戻さない。
存在しないIDは404、既に販売停止した商品の再削除は成功とする。物理削除はしない。

### Alternatives / Consequences

検証で差を無視する方法や全モデルの再生成は採用しない。発生した7件の差は事前バックアップから当該列だけ復元した。
直近30商品と旧「木」の対応商品だけが通常カタログに残る。旧商品の既存の庭・注文・カート参照は維持される。

### Verification

Javaビルドと、Canvas側 `backend/verification/verify_catalog_archive.py` による
専用MySQL/実APIの8項目が成功。旧JSONを含む全商品列のうち販売状態だけが変わり、
再削除・販売一覧/材料照合からの除外・404・検証後の既存DB保持を確認した。
通常EC/Canvasの31商品表示と再読み込みもChromiumで確認した。
詳細と非公開の退避場所はCanvasの `docs/plant-library-v2.md` のカタログ整理節を参照。

## AI画像参照のID指定取得（2026-10-18）

### Context / Decision

Canvasの配置は商品IDを保持しているため、AI生成の参考商品を店舗や素材候補から再選択しない。
`POST /api/products/references` は最大200件の重複しない商品IDに対して、要求順で
ID・商品名・画像URL・販売状態・植物モデル有無だけを返す。3D構成JSONは読み出さない。
既存庭の参照を維持するため販売終了商品もID指定で読める。存在しないIDは404、重複は400。

### Alternatives / Consequences

一覧全件の大きな構成データ取得、商品名からの類似推測、価格・在庫の再選択は採用しない。
販売一覧・購入時の販売終了判定は変更しない。DBスキーマ変更はない。
利用者が旧「木」の例外を取り下げたため `canvas-oak` も販売停止し、現在の通常一覧は30商品。
保存済み庭・注文等を参照切れにしないため商品行や旧モデルファイルは物理削除していない。

### Verification

Javaビルドと、Canvasの `playwright.ai-products.config.ts` による専用MySQL/実API/Chromium検証で、
要求順・メタデータのみの応答・重複400・欠落404・販売終了商品の画像参照を確認した。
通常カタログと既存庭に必要な36商品の実画像取得も成功。通常DBの変更は木の販売状態1列のみ。
今回の有料画像生成は行っていない。


## スライダー入力とAI特徴設定（2026-10-19）

### Context

出品者による数値・選択肢の個別設定が多いため、数値の調整と特徴の仮設定を補助する。
高さは商品とモデルで共用し、任意の数値をスライダー初期値で埋めない。

### Decision

- 数値入力とスライダーを同期し、範囲・単位を表示する。葉密度と手入れレベルは3段階。
- `POST /api/products/plant-model-suggestions` は商品名・学名・カテゴリー・説明・任意の高さ、
  現在のprofile、任意の画像を受け、`profile / estimatedFields / warnings` を返す。
- ECサーバーからResponses APIの `gpt-6-luna` をStructured Outputsで呼び出す。
  商品説明内の命令は資料として扱い、既存のenum・数値制約とCanvasの実組立処理で検証する。
- 色コードはHTMLの色入力と同じ小文字の16進表記に統一する。
- 入力済み高さ・seedは維持する。未入力高さは整数cmで仮入力し、フォームで実寸未確認と表示する。
  保存操作で既存の商品情報として確定する。推定ラベル自体はDBへ保存しない。
- 自動反映・手動修正・直前への取り消しに対応。通信中は編集と保存を停止し、失敗時は入力を保持する。
- 選択ファイルを優先し、なければ指定済みメイン画像1枚を使用する。写真なしを選択可能。
  新規商品の既定の仮画像は送らない。選択ファイルと `/images/` 画像はData URL、外部画像はHTTPS URL。
  ファイルはPNG/JPEG/WebP・5MB以下。サーバーでも形式と容量を検証する。
- AI APIは商品・在庫・画像を永続化しない。商品画像の保存は従来のURL登録。
  モデルの確定は既存商品API、DBスキーマ変更なし。既存Canvasへの変更は不要。
- APIキーは `.env` の `KUSAKARI_EC_OPENAI_API_KEY`、モデル設定は
  `KUSAKARI_EC_PLANT_SUGGESTION_MODEL`（既定 `gpt-6-luna`）。キーをフロントへ渡さない。
  キー未設定・利用制限・認証/権限・通信失敗・無効な応答・組立不能をエラーコードで区別する。
- 1回の操作につきAI呼出しは1回、最大同時実行2件、読取タイムアウト90秒。AIの自動再試行なし。
- Canvasが寸法の不整合を返す場合だけ、AIが推定した葉・花・幹を段階的に小さくし、
  最大3回の追加組立検証を行う。高さ・幅・形態・seedは維持し、調整した場合は注意文を返す。
  型や形態の不整合・通信障害では補正しない。組立不能のままなら入力を保持して失敗を返す。
  この境界は既存Canvas生成器でしか検証できず、AIの推定には変動があるため、
  全体寸法に収まらない葉を持つ既知の設定でも実APIとJavaの補正処理を直接検証する。

### Alternatives / Consequences

全項目の自動入力は採用しない。商品説明・栽培情報・価格・在庫はユーザーの入力を維持する。
写真の寸法や細部は推定であり、正確な商品形状の復元を保証しない。
組立不能やAI失敗時に既定値で成功したように見せず、手動入力または再試行を案内する。

### Verification

`npm run test:product-input` は専用MySQLとEC/Canvasの実APIを使用し、
スライダー同期・空欄・小数・上下限・保存再読込・API入力検証・AI障害時の入力保持を検証する。
AI正常系は `KUSAKARI_EC_E2E_OPENAI_API_KEY` を明示設定した場合だけ実行（有料呼出し2回）。
通常のE2Eは開発用キーへフォールバックしない。成功レスポンスをモックしない。
成果物は `artifacts/e2e/product-*` と `plant-ai-*`、失敗traceは `artifacts/product-input-results/`。

## 商品入力ウィザード（2026-10-19）

### Context

商品情報・栽培情報・植物モデルの全項目を同時表示すると、通常の出品でも長いスクロールが必要だった。

### Decision

新規出品は「商品情報 → 庭オブジェクト → 確認」の3段階とし、最終操作だけで既存の商品APIへ保存する。
編集は商品情報・庭オブジェクトへ直接切り替え、一覧との横並びをやめる。
画像と基本項目はPCで横並び、サイズ・詳しい情報・モデル詳細は折りたたむ。
商品ドラフトとAIのprofile/高さをフォーム所有の状態とし、AIはDOMのFormDataではなく状態を参照する。
ステップはアンマウントせず、数値の入力途中や写真の選択を維持する。送信データは状態から生成し、
非表示にした項目も消さない。次へは該当段階を、保存は全体を検証し、エラー対象の折りたたみを開く。

### Alternatives / Consequences

単一画面の折りたたみだけでは入力順序が不明瞭なため、追加は手順式を採用した。
編集は価格だけの変更でも確認段階を強制しない。保存API、DB、AIの呼出し回数制限は変更しない。
当初は画像URL方式を維持したが、後述の画像アップロードへ変更した。
下書き永続化は対象外で、再読み込みでは未保存の商品入力が失われる。

### Verification

`npm run test:product-input` の実API/専用MySQL検証を新しい手順へ更新。
1440×900、390×900、320×900での3段階、折りたたみ内エラーへの移動、入力保持、3D省略、
出品後の再読込、タブ編集・価格変更後の再読込を検証する。既存のスライダー境界値、
CRUD、Luna実APIによる写真推定・取り消し・手動修正の検証も継続する。
画面は `artifacts/e2e/wizard-*.png`、保存結果は `wizard-persisted-*.json` に保存する。

## 商品画像（2026-10-19）

### Context / Decision

画像URLとAI用ファイルが分かれており、商品登録時に栽培情報まで入力する構成が負担になっていた。

商品画像のファイル選択を保存とAIで共通化し、URL入力を廃止した。PNG/JPEG/WebP、最大5枚、1枚5MBまで。POST /api/product-images はMIMEとシグネチャを検査してMySQLのproduct_mediaへ保存し、GET /api/product-images/{id}で配信する。既存の画像参照は引き続き読み込める。AIはメイン画像を読み込んでデータURL化し、写真送信の選択に従う。

### Alternatives / Consequences

外部ストレージは追加せず、既存のMySQLに画像を保存する。URL入力の維持は採用しない。

削除は商品の画像参照を外す操作であり、保存済み画像本体の物理削除は行わない。出品を中断したアップロードも残る。自動回収は未実装。商品下書きの復元は追加していない。

出品時の詳しい情報は生産者名・学名・科名とする。

### 出品者Tipsの撤去（2026-10-19）

Context: 利用者の依頼により、出品者Tipsを廃止する。
Decision: 編集画面、購入者表示、専用GET/PUT APIとDTO/サービス、専用CSSを削除する。専用文章項目（季節の育て方・空間との相性・開花案内）は商品APIの入出力からも除外する。
