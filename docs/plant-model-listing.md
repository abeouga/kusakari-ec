# 植物特徴とCanvasのGLB部品構成

## Context

商品の園芸情報はECが管理する。出品者は完成済みの3Dモデルを選ばず、植物の特徴を入力する。Canvasが、あらかじめ制作した共通のGLB部品から構成を決める。部品の制作・接続点・構成規則はCanvasの `docs/modular-plant-models.md` にある。

## Decision

### 商品入力の手順

- 新規出品は「商品情報 → 画像 → 庭オブジェクト → 確認」の4ステップで、確認画面の「出品する」で保存する。ステップ表記はボタンでないバー（現在のステップに `aria-current="step"`）で示す。編集は「商品情報・画像・庭オブジェクト」の3タブを直接切り替え、「変更を保存」で更新する。
- ステップはアンマウントせず、数値の入力途中や写真の選択を保つ。送信データはフォームの状態から作り、非表示の項目も消さない。「次へ」は該当のステップを、保存は全体を検証し、エラーのあるステップ・折りたたみを開いてその欄へフォーカスを移す。前のステップへ戻るボタンは「前の手順へ」。下書きは保存しないので、再読み込みで未保存の入力は失われる。
- 商品番号は入力欄を持たず、登録時にサーバーの `ProductSkuGenerator` が採番する。編集時は表示だけ。APIでも更新時は空か現在の値だけを受け付け、異なる値は409 `SKU_IMMUTABLE` で拒否する。
- カテゴリーは絞り込み付きのダイアログで選ぶ。商品の店舗（在庫を登録する店舗）は、画面内の地図モックと店舗一覧のダイアログで選ぶ。地図モックは店舗の緯度・経度（`stores.latitude/longitude`、任意）からピンを置き、外部の地図API・タイルは読み込まない。緯度・経度のない店舗と、(0, 0) の店舗は「位置情報なし」としてピンを置かず、一覧からだけ選べる。
- ダイアログはTab/Enter/Escで操作でき、閉じると開いたボタンへフォーカスを戻す。Escは最前面のダイアログだけを閉じる。
- 数値の項目（高さ・鉢径・樹齢・耐寒温度と庭オブジェクトの数値）は数値入力とスライダーを同期し、範囲と単位を表示する。葉の密度と手入れレベルは説明つきの3段階。価格・在庫は数値入力だけ。任意の数値をスライダーの初期値で埋めない。
- 詳しい情報は生産者名・学名・科名。サイズ・詳しい情報・モデルの詳細は初期状態で折りたたむ。

### 商品画像

- 「画像」ステップで追加・並べ替え・削除する。PNG/JPEG/WebP、最大5枚、1枚5MBまで。URLの入力欄はない。新規出品ではメイン画像が必須で、1枚目がメイン画像になる。
- `POST /api/product-images` がMIMEとファイルのシグネチャを検査してMySQLの `product_media` へ保存し、`GET /api/product-images/{id}` で配信する。
- 画像の削除は商品の画像参照を外す操作で、保存済みの画像本体は物理削除しない。出品を中断したアップロードも残り、自動の回収はない。

### 庭オブジェクト

- 庭オブジェクトのステップでは、植物の形態、幅、全体形状、幹・枝、葉、花を入力する。入力欄は「サイズ／形／枝・茎／葉／花」にまとめ、細かい調整は折りたたむ。自動／手動は2択の切り替え、花の色は名前つきの色見本で選ぶ。非表示のグループ（花を付けない、その植物タイプで使わない項目）の欄は、検証とプレビューの判定から外す。
- 植物の高さ（土際から最高点まで、鉢を含まない）は商品の `heightCm` を共用し、このステップだけで10〜1500cmの整数で入力する。商品ページの高さ表示もこの値を使う。範囲外のときはその欄に「植物の高さは10〜1500cmの整数にしてください。」を1件だけ出す。`ProductRequest.heightCm` も10〜1500（省略可）。販売カテゴリーと植物の形態は別の分類として持つ。
- 植物の新規出品は `plantModelProfile` を必ず保存する。必須の項目が未入力のまま「次へ」を押すと、エラーを出してその欄へフォーカスを移す。
- 植物以外のカテゴリーは `frontend/src/plantModel.js` の `nonPlantCategories`（今は「鉢・庭材」だけ）で判定する。これらの商品は庭ではCanvasに登録済みのモデル（レンガ・ベンチなど）を使うので、植物の特徴・AI・プレビューを出さず、「商品の高さ」（任意）だけを入力し、`plantModelProfile=null` で保存する。保存済みのprofileがある商品は、カテゴリーにかかわらず植物として扱い、profileを保つ。
- 庭オブジェクトのない既存商品（`plantModelProfile=null`）は、編集で特徴を変えるかAIで生成するまでnullのまま保存する。開いただけで既定のprofileに変えない。
- 植物モデルの数値欄は、空・範囲外・刻み違いの入力を欄に残してエラーを出し、profileには直前の正しい値を保つ。

### プレビュー

- Canvasの `/model-preview` を埋め込む。特徴を変えると400msのデバウンス後に自動で更新する（ボタンはない）。AIの反映後も同じ。スライダーをドラッグしているあいだは再読み込みしない。
- 入力が不正なあいだは直前のプレビューを残し、「入力を直すと更新します」を表示する。
- プレビューは二重バッファーで切り替える。新しいiframeを前のiframeの上で透明のまま読み込み、loadから700ms後に表示を切り替える。読み込み中のiframeはTab順とアクセシビリティツリーから外す。

### 保存とCanvasの構成

- 保存リクエストは `plantModelProfile` を送る。ECバックエンドがCanvasの `POST /api/model-assemblies/resolve` を呼び、返された部品構成を `modelComposition` として商品に保存する。クライアントに確定した構成を指定させない。
- 構成の更新が要る保存でCanvasへ接続できないときは、商品の更新をロールバックしてエラーを返す。
- 特徴を変えない編集（在庫の編集など）は保存済みの構成を使い回す。追加フィールドを省いた更新も構成を保つ。APIで明示的にnullを送るとモデル設定の解除になる（出品フォームには解除の操作はない）。
- 商品APIとカート内の商品は、profile・構成・`canvasMaterialCode` を返す。構成のある商品は材料コード `product.<商品ID>` をその商品だけに結び付け、材料照合APIで配置数量から同じ商品を購入候補にできる。価格・在庫・カート・注文はECの正本を使う。
- 旧モデル構成のprofileに `botanicalForm` がないときは、商品APIのDTO変換で `null` として返す。DBのJSONは書き換えない。

### AIによる特徴の推定

- 庭オブジェクトのプレビュー右下の「AIで生成」で推定する。`POST /api/products/plant-model-suggestions` は商品名・学名・カテゴリー・説明・任意の高さ、現在のprofile、任意の画像を受け、`profile / estimatedFields / warnings` を返す。
- ECサーバーから、Responses APIの `KUSAKARI_EC_PLANT_SUGGESTION_MODEL`（既定 `gpt-6-luna`）をStructured Outputsで呼ぶ。APIキーは `.env` の `KUSAKARI_EC_OPENAI_API_KEY` で、フロントへ渡さない。商品説明の中の命令は資料として扱い、enum・数値の制約とCanvasの実際の組み立てで検証する。キー未設定・利用制限・認証/権限・通信失敗・無効な応答・組み立て不能をエラーコードで区別する。
- メイン画像があれば常にAIへ送り、送らない選択肢はない（メイン画像がないときだけ写真なし）。選択したファイルと `/images/` の画像はData URL、外部の画像はHTTPS URLで送る。サーバーでもPNG/JPEG/WebP・5MB以下を検証する。
- 入力済みの高さとseedは保つ。未入力の高さは整数cmで仮に入れ、フォームで実寸未確認と表示する。推定のラベルはDBに保存しない。色コードはHTMLの色入力と同じ小文字の16進表記にそろえる。
- 1回の操作でAIの呼び出しは1回。同時実行は最大2件、読み取りのタイムアウトは90秒で、自動の再試行はしない。推定中はプレビューに処理中の表示を出してフォーム全体を操作できなくし、終わると押したボタンへフォーカスを戻す。失敗しても入力は保つ。「AI設定を元に戻す」で反映前に戻せる。
- Canvasが寸法の不整合を返したときだけ、AIが推定した葉・花・幹を段階的に小さくして、最大3回まで組み立て直す。高さ・幅・形態・seedは保ち、調整したときは注意文を返す。型や形態の不整合・通信障害では補正しない。
- AIのAPIは商品・在庫・画像を保存しない。モデルの確定は商品APIの保存で行う。

### AI画像生成の参考商品

- Canvasの配置は商品IDを持つので、AI画像生成の参考商品を店舗や素材の候補から選び直さない。`POST /api/products/references` は最大200件の重複しない商品IDについて、要求順に、ID・商品名・画像URL・販売状態・植物モデルの有無と、店舗・在庫・購入可否（購入できない理由）を返す。3D構成のJSONは読まない。
- 既存の庭の参照を保つため、販売を終えた商品もID指定で読める。存在しないIDは404、重複は400。

## Alternatives

- 完成モデルのプルダウン選択は要件に合わない。表示時の形状生成やGLB生成は行わず、登録済みの部品を保存済みの変換で描画する。
- 全項目の自動入力は採用しない。商品説明・栽培情報・価格・在庫は出品者の入力を保つ。
- 商品番号の変更を許して重複だけ検査する案は、「編集時は変更不可」と食い違うため採用しない。
- 外部の地図タイルを使う案は、外部通信と利用条件が増えるため採用しない。
- 植物以外かどうかを `categories` の列で持つ案は、DBとカテゴリーAPIの変更が要るため採用しない。
- 写真を送るかどうかの選択を残す案は採用しない。AIで生成しなければ写真は送られない。
- iframeを毎回置き換える案は、読み込み中に白い画面が見えるため採用しない。
- 外部ストレージは追加せず、MySQLに画像を保存する。

## Consequences

- 新しい特徴に対応するにはCanvasの部品・規則を追加する。Canvasの庭は配置時の構成を持ち、商品を後で編集しても既存の庭の形は変わらない。商品写真からの形状の自動復元はない。
- 写真の寸法や細部は推定で、正確な商品の形の再現は保証しない。組み立て不能やAIの失敗のときに既定値で成功したように見せず、手入力か再試行を案内する。
- メイン画像は外部AI（Responses API）へ必ず送られる。
- `categories` に植物以外のカテゴリーを足したときは `nonPlantCategories` も直す必要がある。直さないと、そのカテゴリーの新規出品で植物の特徴と高さが必須になる。
- 700msは目安の値で、Canvasの描画完了は検知していない。描画が遅いと、切り替え時に短いちらつきが残ることがある。

## Setup

ECの `start.bat` とCanvasの `start.bat` で双方を起動する。

- ECサーバーからCanvas API：`KUSAKARI_CANVAS_API_URL`（既定 `http://127.0.0.1:8080`）
- 出品プレビュー：`VITE_KUSAKARI_CANVAS_URL`（既定 `http://127.0.0.1:5173/`）

## 検証

`npm run test:product-input`（business 設定の `business-product-*` と `business-plant-ai`）と `business-plant-step` で、実API・専用MySQL・実Cognitoを使って確かめる。AIの正常系は `KUSAKARI_EC_E2E_OPENAI_API_KEY` を明示したときだけ実行し（有料の呼び出し）、開発用のキーには切り替えない。成功応答をモックしない。
