# EC の DB を初期化して作り直す（issue #106）

## Context

店舗側アカウントの作り直し（#103）では、既存のデータを移行せず、DB を初期化して新しいテーブル構成を作る（#102 決定事項2）。他の PC は `setup.bat` で環境を作っていて、PC によって MySQL の場所が違う。

- すでに MySQL が入っている PC（existing）：多くは 3306 番ポート。Canvas やほかのプロジェクトの DB と同じ MySQL を使っていることがある
- セットアップが専用の MySQL を作った PC（managed）：3307 番ポート。記録はユーザーのローカルデータフォルダーの `Kusakari\mysql` にある

`setup.bat` は「既存の DB を削除しない」方針で、DB を作り直す手段がなかった。対象を取り違えると、別のプロジェクトや開発者のデータを消してしまう。

## Decision

`DB-reset.bat` を追加する。その PC でこのプロジェクトが使っている MySQL を特定し、EC の DB だけを消して、その時点のマイグレーションで作り直す。Windows の管理者として実行する。

`scripts/reset-database.ps1` が管理者として起動し直し、`scripts/reset-database-core.ps1` が初期化を行う。

### 実行のしかた

1. `stop.bat` で、このフォルダーの Web と API を止める（止めていなくても、スクリプトがこのフォルダーの分だけ止める）
2. 新しいコードを取得した後なら、`npm run build:api` で API を作り直す。初期化の後の確認は、このフォルダーの API でテーブルを作るため
3. `DB-reset.bat -DryRun` を実行する。Windows の確認（ユーザー アカウント制御）が出るので「はい」を選ぶ。別のウィンドウが開き、対象が表示される。この時点では何も変更しない
4. `DB-reset.bat` を実行する。同じように Windows の確認の後、別のウィンドウに対象が表示されるので、合っていれば `RESET kusakari` と入力する
5. 「EC の DB の初期化が完了しました」と表示されたら、`start.bat` で起動する
6. Canvas を使っている PC では、続けて Canvas 側の DB も初期化する（abeouga/kusakari-canvas#63）

| 引数 | 動き |
| --- | --- |
| なし | 対象を表示し、確認の文字の入力を求める |
| `-DryRun` | 対象を表示するだけで終了する。何も変更しない |
| `-NoBackup` | 消す前のバックアップを取らない |
| `-ConfirmText "RESET kusakari"` | 確認の文字を引数で渡す。動作の確認用で、ふだんは使わない |

終了コードは、成功が 0、エラーが 1、確認の文字が違って中止したときが 2。Windows の確認で「いいえ」を選んだときは、何も変更せずに終了コード 1 で終わる。

管理者として起動し直したウィンドウは、結果を読めるように、最後に Enter キーの入力を待つ。すでに管理者として開いた PowerShell から実行したときは、そのまま同じ画面で進む。

### 対象の決め方

消す DB は `kusakari`（開発用）と `kusakari_e2e`（E2E 用）の2つに固定する。名前はスクリプトの中の定数で、入力や `.env` の値からは決めない。

接続先は `.env` から読み、次のすべてを確かめる。1つでも確かめられなければ、何も変更せずに止まる。

- `.env` の DB の URL が、`127.0.0.1` の `kusakari` と `kusakari_e2e` を指している（`setup.bat` と同じ確認）
- `.env` のポートで MySQL が応答している。専用の MySQL が停止しているときは、セットアップと同じ処理で起動する
- そのポートを待ち受けているプロセスが1つだけで、`mysqld.exe` である
- 接続した MySQL 自身が答えるポートが、`.env` のポートと同じである
- 専用の MySQL（managed）のときは、記録（`instance.json`）のポートと、データの場所が、接続先と一致する
- 既存の MySQL（existing）のときは、接続先が専用の MySQL のデータの場所ではない
- 対象の DB にテーブルがあるときは、Kusakari EC のマイグレーション履歴（`flyway_schema_history`）がある。なければ、別の用途の DB の可能性があるので止まる
- アプリ用の DB ユーザーに、2つの DB を作り直す権限（`CREATE` と `DROP`）がある
- 対象の DB に、ほかのプロセスが接続していない（ほかの作業フォルダーの API や E2E が動いていない）

### 消す前に表示するもの

MySQL の方式、ポート、プロセス ID、実行ファイル、データの場所、バージョン、接続するユーザー、消す DB ごとのテーブル数・適用済みのマイグレーションの件数・主なテーブルの行数。

### 実行すること

1. このフォルダーから起動した Web と API を止める
2. 2つの DB を、`.runtime\backups\db-reset-<日時>\` にバックアップする（`mysqldump`）。実行した人だけが読めるファイルにする
3. 2つの DB を削除して、空の DB を作る（照合順序はセットアップと同じ `utf8mb4_0900_ai_ci`）
4. セットアップと同じ確認を行う。DB ごとに API を起動して Flyway を実行し、マイグレーション履歴・商品4件以上・会員テーブル・ログイン用 API を確かめる

確認の処理は `scripts/database-verify.ps1` に移し、`setup.bat` と同じものを使う。新しいテーブル構成（#107）で確認の内容が変わるときは、この1か所を直す。

### 決めたこと（#106 の「決めること」）

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| E2E 用の DB も一緒に初期化するか | する。開発用と E2E 用を必ず一緒に作り直す | 2つの DB は同じマイグレーションで作るもので、セットアップも両方を確かめている。片方だけ古い構成が残ると、E2E が失敗する |
| 確認の方法 | 対象を表示した後に、決まった文字（`RESET kusakari`）の入力を求める。表示だけを行う `-DryRun` も用意する | 「はい／いいえ」より、押し間違いで消すことが起きにくい。大文字と小文字も区別する |
| Windows の管理者権限が必要か | 必要。起動したときに、Windows の確認（ユーザー アカウント制御）を求める。DB の操作はアプリ用の DB ユーザーで行い、MySQL の管理者（root）のアカウントは聞かない | ユーザー判断（2026-11-12）。#102 決定事項2 の「管理者権限で実行するスクリプト」に合わせ、Canvas の初期化（abeouga/kusakari-canvas#63）とそろえる。DB の操作そのものは、セットアップがアプリ用のユーザーに付けている権限（2つの DB への `CREATE` と `DROP`）で足りる。権限が2つの DB に限られているので、ほかの DB を消すことができない |
| Canvas の初期化と一度に実行できるようにするか | しない。EC と Canvas のスクリプトを続けて実行する | Canvas は別のリポジトリで、置き場所が PC によって違う。まとめて実行する手順は、他の PC の手順を整える #113 で扱う |

## Alternatives

- MySQL のデータフォルダーごと初期化する：同じ MySQL に Canvas やほかのプロジェクトの DB があると巻き込むため
- MySQL の管理者（root）で接続して作り直す：root のパスワードを聞く必要があり、root はどの DB でも消せるので、対象を取り違えたときの被害が大きい
- Windows の管理者権限を求めない：DB の削除と作成そのものには要らないが、ユーザー判断で、管理者として実行する形にした（最初の実装は管理者権限を求めない形で、2026-11-12 に変更した）
- 3306 と 3307 のうち応答している方を対象にする（`MySQL-reset.bat` の決め方）：両方が動いている PC で決まらない。`.env` に記録されている接続先を使う
- テーブルだけを削除して DB は残す：テーブルの一覧を取り違える余地がある。DB ごと作り直す方が、残るものがない
- バックアップを取らない：移行しないと決まっているが、消した後で必要になったときに戻す手段がなくなる。`-NoBackup` で省ける

## Consequences

- Windows の管理者権限を持たないユーザーは、このスクリプトを実行できない。表示だけの `-DryRun` も、管理者として実行する
- 起動した人と違うユーザーの管理者権限で実行すると、専用の MySQL の記録の場所が変わり、対象を取り違えるおそれがある。この場合は何も変更せずに止まる
- 消した DB のデータ（会員・店舗・商品・注文・カート）は、すべて失われる。バックアップは `.runtime\backups` に残るが、Git には入らない。会員の情報を含むので、共有しない
- EC だけを初期化すると、Canvas の庭の持ち主（EC の会員 ID）と、買い物リストが持つ庭 ID が、作り直した EC と食い違う。Canvas 側も続けて初期化する
- 認証基盤（Cognito）のユーザーは消さない。初期化の後、初めてログインしたときに会員が作られる
- DB を作り直した後でマイグレーションの確認に失敗すると、DB は空か、途中まで作られた状態で残る。原因を直してから `setup.bat` を実行すると、テーブルが作られる
- 閉鎖した店舗の連絡先を消すイベントは、#107 ではマイグレーションに入れなかった（`docs/database-v3-check/store-closure-event.sql`）。2026-11-12 の決定（3-1）で、イベントをやめてアプリ内の定期処理（1日1回）にした（#79）。セットアップが付ける権限は変えない
- 初期化の後の確認は、`backend/target` にある API の JAR でマイグレーションを適用する。古い JAR のままだと、古いマイグレーションが空の DB に適用されてしまう。新しい main を取得した後は、`npm run build:api`（または `setup.bat`）で API を作り直してから初期化する
- 2026-11-12、v3 への切り替えの後、以前にビルドしたフォルダーで初期化すると、確認が「Found more than one migration with version 1」で失敗した。Maven の `package` が、ソースから消した旧マイグレーション（V1〜V15）を `target` に残していたため。`scripts/api.mjs` の API のビルドに `clean` を付けて直した。直す前のフォルダーでは、`backend` で `mvnw clean package -DskipTests` を実行してから `setup.bat` を実行すると、空の DB にテーブルが作られる
- `scripts/setup.ps1` は、確認の処理を `scripts/database-verify.ps1` の関数の呼び出しに置き換えた。処理の中身は変えていない

## Verification scope

開発者がふだん使っている MySQL（3306）では試していない。使い捨ての MySQL 8.0.46 を別のポート（33999）に一時的なデータフォルダーで立て、セットアップと同じ権限のアプリ用ユーザーを作って確かめた。同じ MySQL に、Canvas の DB に見立てた `kusakari_canvas` と、別のプロジェクトに見立てた DB を置いた。18の場面は、初期化の本体（`scripts/reset-database-core.ps1`）を直接実行して確かめた。本体は、管理者権限のない状態でも DB の削除と作成ができた。

### 検証結果（2026-11-12）

18件すべて期待どおりだった。

| 場面 | 結果 |
| --- | --- |
| `-DryRun`（空の DB、データのある DB） | 対象とテーブル数・マイグレーションの件数・行数を表示し、データは変わらなかった |
| 初期化（空の DB） | 2つの DB にマイグレーション15件と商品4件以上ができ、セットアップと同じ確認が通った |
| 初期化（データのある DB） | 目印を付けたデータが消え、作り直された。消す前のバックアップが2つの DB 分でき、目印のデータを含んでいた |
| `-NoBackup` | バックアップを作らずに初期化できた |
| 同じ MySQL のほかの DB | 初期化の後も、Canvas に見立てた DB と別のプロジェクトに見立てた DB のデータが残っていた |
| 確認の文字が違う（小文字で入力） | 終了コード2で中止し、データが残った |
| `.env` のポートで何も応答しない | 何も消さずに止まった |
| `.env` のポートを MySQL 以外のプロセスが使っている | 何も消さずに止まった |
| 対象の DB にマイグレーション履歴がない | 何も消さずに止まった。もう片方の DB も消えなかった |
| ほかのプロセスが対象の DB に接続している | 何も消さずに止まった |
| 片方の DB を作り直す権限がない | どちらの DB も消さずに止まった |
| 専用の MySQL（managed）で、記録と接続先が一致する | 初期化でき、確認が通った |
| 専用の MySQL の記録と、ポートまたはデータの場所が違う | 何も消さずに止まった |
| `.env` は existing なのに、接続先が専用の MySQL | 何も消さずに止まった |
| `DB-reset.bat -DryRun`（管理者権限を求める形に変える前） | `.bat` から起動でき、終了コード0で終わった |

管理者権限を求める形に変えた後、次を確かめた。

- 管理者でないときに、管理者として起動し直す処理：起動の部分を置き換えて（Windows の確認を出さずに）、渡す引数（表示だけ・バックアップなし・確認の文字・起動した人のユーザー名）が正しく組み立てられること、起動が取り消されたときに「DB は変更していません」と表示して終了コード1になること、引用符を含む確認の文字を受け付けないことを確かめた
- 本体のファイル名を変えた後、確認の文字が違う場面・表示だけの場面・データのある DB の初期化（バックアップと、ほかの DB が残ることを含む）を、もう一度実行して通ることを確かめた

### 確かめていないこと

- Windows の確認（ユーザー アカウント制御）を実際に通して、管理者として起動し直した後の動き。確認の画面を操作できない環境で検証したため。管理者として起動した後に行う処理（起動した人との照合、本体の呼び出し、最後の Enter 待ち）は、まだ実際には動かしていない
- 3306 の既存の MySQL と、セットアップが作った 3307 の専用の MySQL そのもの。専用の MySQL は、記録の場所を一時的なフォルダーに向けて、同じ判定を通ることだけを確かめた
- 画面で確認の文字を入力する操作（確認の文字は引数で渡した）
- 専用の MySQL が停止しているときに、スクリプトが起動する動き（試験では起動した状態で実行した）
- 1つのポートを複数のプロセスが待ち受けている場合
- `setup.bat` の全体。変えたのは確認の処理の呼び出し方だけで、同じ処理が初期化スクリプトから通ることを確かめた
- MySQL 8.4 のサーバー（使い捨ての MySQL は 8.0.46。クライアントは 8.4.11 を使った）
- 他の PC での実行
