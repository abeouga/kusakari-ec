# EC の DB を初期化して作り直す（issue #106）

## Context

店舗側アカウントの作り直し（#103）では、既存のデータを移行せず、DB を初期化して新しいテーブル構成を作る（#102 決定事項2）。他の PC は `setup.bat` で環境を作っていて、PC によって MySQL の場所が違う。

- すでに MySQL が入っている PC（existing）：多くは 3306 番ポート。Canvas やほかのプロジェクトの DB と同じ MySQL を使っていることがある
- セットアップが専用の MySQL を作った PC（managed）：3307 番ポート。記録はユーザーのローカルデータフォルダーの `Kusakari\mysql` にある

`setup.bat` は「既存の DB を削除しない」方針で、DB を作り直す手段がなかった。対象を取り違えると、別のプロジェクトや開発者のデータを消してしまう。

## Decision

`DB-reset.bat` を追加する。`.env` の接続先にある EC の DB だけを消して、その時点のマイグレーションで作り直す。実行したら、そのまま最後まで進める。

`scripts/reset-database.ps1` が準備（Web と API を止める・依存・API のビルド）をして、`scripts/reset-database-core.ps1` が初期化を行う。

### 実行のしかた

1. `DB-reset.bat` を実行する
2. このフォルダーの Web と API を止め、`npm install` で依存を入れ、API を作り直す。ここで失敗したときは、DB に触れずに止まる
3. 作り直す DB と、そのテーブルの数・主な行数を表示し、そのまま作り直す
4. 「EC の DB の初期化が完了しました」と表示されたら、`start.bat` で起動する
5. Canvas を使っている PC では、続けて Canvas 側の `DB-reset.bat` も実行する

他の PC を新しい構成へ移すときの通しの手順は [他の PC の移行手順](migration-other-pc.md)、ほかの PC で実行するスクリプトの全体は [ほかの PC で実行するスクリプトと実行順](other-pc-scripts.md) にある。

| 引数 | 動き |
| --- | --- |
| なし | 準備をして、そのまま作り直す |
| `-DryRun` | 作り直す DB を表示するだけで終了する。Web と API を止めず、ビルドもしない。何も変更しない |
| `-NoBackup` | 消す前のバックアップを取らない |

終了コードは、成功が 0、エラーが 1。最後にキーの入力を待つ（`KUSAKARI_EC_NO_PAUSE=1` で待たない）。

### 対象の決め方

消す DB は `kusakari`（開発用）と `kusakari_e2e`（E2E 用）の2つに固定する。名前はスクリプトの中の定数で、入力や `.env` の値からは決めない。接続先（ポート・ユーザー・パスワード）は `.env` をそのまま使う。`.env` が専用の MySQL を指していて止まっているときは、起動してから作り直す。

### 実行すること

1. このフォルダーから起動した Web と API を止め、依存を入れ、API を作り直す
2. 2つの DB への、ほかのプロセスの接続を切る
3. 2つの DB を、`.runtime\backups\db-reset-<日時>\` にバックアップする（`mysqldump`）。実行した人だけが読めるファイルにする。失敗しても続ける
4. 2つの DB を削除して、空の DB を作る（照合順序はセットアップと同じ `utf8mb4_0900_ai_ci`）
5. セットアップと同じ確認を行う。DB ごとに API を起動して Flyway を実行し、マイグレーション履歴・商品4件以上・会員テーブル・ログイン用 API を確かめる
6. 開発用 DB（`kusakari`）に、テスト用アカウント9つの会員と種別、テスト組織2を入れる（`scripts/set-test-accounts.ps1`、#157）。セットアップも最後に同じことをする。失敗しても、作り直した DB はそのまま使える

確認の処理は `scripts/database-verify.ps1` に移し、`setup.bat` と同じものを使う。

### 決めたこと

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| E2E 用の DB も一緒に初期化するか | する。開発用と E2E 用を必ず一緒に作り直す | 2つの DB は同じマイグレーションで作るもので、セットアップも両方を確かめている。片方だけ古い構成が残ると、E2E が失敗する |
| 確認の方法 | 確認しない。対象を確かめるだけなら `-DryRun` を使う | 実行するだけで成功してほしい（ユーザー判断） |
| Windows の管理者権限が必要か | 必要としない。DB の操作はアプリ用の DB ユーザーで行い、MySQL の管理者（root）のアカウントは聞かない | セットアップがアプリ用のユーザーに付けている権限（2つの DB への `CREATE` と `DROP`）で足りる。権限が2つの DB に限られているので、ほかの DB を消すことができない |
| 消す DB の名前 | `kusakari` と `kusakari_e2e` に固定する | `.env` の書き間違いでほかの DB を消さないため |
| `setup.bat` と同時に実行したとき | 止める（同じフォルダーのロックファイル `.runtime\setup.lock`） | 2つが同時に DB を作り直すと壊れるため |
| Canvas の初期化と一度に実行できるようにするか | しない。EC と Canvas のスクリプトを続けて実行する | Canvas は別のリポジトリで、置き場所が PC によって違う |

## Alternatives

- MySQL のデータフォルダーごと初期化する：同じ MySQL に Canvas やほかのプロジェクトの DB があると巻き込むため
- MySQL の管理者（root）で接続して作り直す：root のパスワードを聞く必要があり、root はどの DB でも消せるので、対象を取り違えたときの被害が大きい
- 確認の文字・管理者への切り替え・対象の照合を残す（2026-11-12 から 2026-11-16 までの形）：使う人の操作が増え、自動で止められない Canvas や E2E があると止まって成功しないため、2026-11-16 にやめた
- 接続しているプロセスがあると止める：作り直す DB なので、接続は切って進めればよいため
- 3306 と 3307 のうち応答している方を対象にする（`MySQL-reset.bat` の決め方）：両方が動いている PC で決まらない。`.env` に記録されている接続先を使う
- テーブルだけを削除して DB は残す：テーブルの一覧を取り違える余地がある。DB ごと作り直す方が、残るものがない
- バックアップを取らない：移行しないと決まっているが、消した後で必要になったときに戻す手段がなくなる。`-NoBackup` で省ける

## Consequences

- 実行すると確認なしで消す。`.env` の接続先にある `kusakari` と `kusakari_e2e` は、別の用途に使っていても消える
- 別の作業フォルダーの API や E2E が対象の DB を使っていても、接続を切って作り直す。それらは、作り直した後の DB で動き続ける（エラーになることがある）
- バックアップに失敗しても止まらない。そのときは消した DB を戻す手段がない
- 消した DB のデータ（会員・店舗・商品・注文・カート）は、すべて失われる。バックアップは `.runtime\backups` に残るが、Git には入らない。会員の情報を含むので、共有しない
- EC だけを初期化すると、Canvas の庭の持ち主（EC の会員 ID）と、買い物リストが持つ庭 ID が、作り直した EC と食い違う。Canvas 側も続けて初期化する
- 認証基盤（Cognito）のユーザーは消さない。初期化の後、初めてログインしたときに会員が作られる
- DB を作り直した後でマイグレーションの確認に失敗すると、DB は空か、途中まで作られた状態で残る。原因を直してから `setup.bat` を実行すると、テーブルが作られる
- 初期化の後の確認は、`backend/target` にある API の JAR でマイグレーションを適用する。古い JAR だと古いマイグレーションが空の DB に適用されるので、`DB-reset.bat` が初期化の前に API を作り直す。API のビルド（`scripts/api.mjs`）は `clean` を付けて、ソースから消したマイグレーションを `target` に残さない
- 閉鎖した店舗の連絡先は MySQL のイベントではなくアプリの定期処理で消すので、セットアップはアプリ用のユーザーに EVENT 権限を付けない

検証の記録と、確認の入力や管理者への切り替えをやめた経緯（2026-11-16）は、[kusakari-document の DB構成](https://github.com/abeouga/kusakari-document/tree/main/kusakari-ec/DB構成) にある。
