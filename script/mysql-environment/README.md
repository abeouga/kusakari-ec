# 別PCのログイン用MySQL準備

## このMarkdownを読んだCodexへの指示

この手順は、利用者がこのMarkdownに従った環境準備を依頼したときに実行してください。

1. このファイルの2階層上をリポジトリのルートとし、ルートの `AGENTS.md` を読み、`git status --short --branch` で既存変更を確認してください。固定のユーザー名やこのPCの絶対パスを使わないでください。
2. Windowsであること、`backend/pom.xml`、`scripts/setup.ps1`、`config/cognito.development.json` が存在することを確認してください。利用者が実行中のアプリを使っている場合、DB準備でこのチェックアウトのAPI/Webが停止することを先に伝えてください。
3. `.env` の秘密値を表示せず、DB方式・ポート・MySQLの稼働状態を調べてください。通常は自動選択のまま実行してください。利用者が方式を指定した場合はその指定を優先します。既存サーバーが非対応で専用DBに切り替える場合、既存データが移らないことを説明してください。
4. リポジトリのルートを作業ディレクトリとして、次を実行してください。バッチは内部でWindows PowerShell 5.1を使用します。PowerShell 7で共通DBスクリプトを直接読み込まないでください。

   ```powershell
   $env:KUSAKARI_EC_NO_PAUSE = '1'
   & .\script\mysql-environment\setup-mysql.bat
   if ($LASTEXITCODE -ne 0) { throw 'MySQL環境の準備に失敗しました。成功として報告しないでください。' }
   ```

5. rootパスワードの入力が必要になった場合、利用者に端末の非表示入力で入力してもらってください。チャットや引数、Markdown、Gitへパスワードを書かないでください。対話入力を利用できない場合は、利用者へバッチの直接実行を案内し、未実行の範囲を明示してください。
6. 終了コード0と、開発/E2E両DBの「最新Flyway・会員テーブル・実API・ログイン用API」の成功表示を確認してください。失敗した場合は `.runtime/setup-*.log` とエラーログからDB接続、構造不一致、Cognito設定不足を区別してください。ログの共有前には秘密情報を除いてください。
7. 初回PCでWeb依存がなければルートの `setup.bat` も実行してください。既存環境なら `start.bat` で再起動してください。最後に実際のログインを確認してください。ログイン資格情報がなければDB/API準備完了と実ログイン未検証を区別して報告してください。
8. 実施したDB方式・ポート、初期化/更新/再実行の別、検証結果、残った問題を簡潔に報告してください。commit/push、既存DBの削除、rootパスワードのリセット、Flyway repair、Cognitoの無効化は行わないでください。他リポジトリのDBやプロセスも変更しないでください。

このフォルダーのバッチとPowerShellは入口です。実処理は同じリポジトリ内の `scripts/setup.ps1`、`scripts/database.ps1`、`scripts/database-contract.ps1` を使います。フォルダー単体では動きません。

## 操作

`kusakari-ec` のプロジェクト全体を別PCに配置し、このフォルダーの `setup-mysql.bat` を実行します。Windows 10/11 x64用です。以下はこのフォルダーを作業ディレクトリとした例です。

```bat
setup-mysql.bat
```

3306でMySQLが応答すれば既存サーバーを使用し、応答しなければ専用MySQLを3307に準備します。保存済みのDB方式は再利用します。既存サーバーのrootパスワードは最初に `password` を試し、異なる場合だけ非表示で入力します。既存サーバーのrootパスワードは変更しません。

既存サーバーがMySQL 5.7やMariaDBなどの場合は、専用MySQLを選択してください。

```bat
setup-mysql.bat -DatabaseMode managed
```

専用DBは既存MySQLのデータを移しません。既存DBを利用する場合は次を指定します。3306でサーバーが起動している必要があります。

```bat
setup-mysql.bat -DatabaseMode existing
```

成功後、アプリの依存を導入済みなら `start.bat` で起動します。初めてプロジェクトを配置したPCでは `setup.bat` を実行してWebと起動ツールも準備してから `start.bat` を実行します。

DB準備はAPIをビルドするため、このチェックアウトの起動中API/Webを停止します。自動再起動はしません。最新APIをビルド済みの場合だけ `setup-mysql.bat -SkipInstall` でビルドを省略できます。古いAPIでは最新マイグレーションの検証が失敗します。

## 合わせる設定と成功条件

- MySQL 8系、`utf8mb4_0900_ai_ci` 対応、接続先 `127.0.0.1`、APIのDBセッションはUTC。
- 開発DB `kusakari` と試験DB `kusakari_e2e`、アプリユーザー `kusakari`、ローカル用パスワード `password`。
- `localhost` / `127.0.0.1` のアプリユーザーと対象2DBへの権限を準備。
- 最新Flyway、Hibernateによる構造検証、会員テーブル、商品データ、実API起動、未ログイン応答、CSRF発行を両DBで検証。
- `.env` のDB接続先を保存。既存Cognito設定・APIキー・Canvas接続先などは保持し、直前の設定は `.runtime/env.previous` へ退避。
- 初回のみ不足しているCognito公開設定を `config/cognito.development.json` から補完。AWS管理用アクセスキーは不要。

MySQLの製品バージョンをインストール済みサーバー間で完全一致させる処理ではありません。専用モードでは発見済みのMySQL 8系を再利用し、なければ検証済み公式ZIPから導入します。互換性を検証してアプリの接続設定・権限・構造を揃えます。既存MySQLサービス設定、既存テーブルの照合順序を一括変更しません。すでに旧製品の専用データがある場合、そのデータディレクトリを自動アップグレードしません。

## 認証の範囲

パスワード認証はCognitoで行い、会員情報はMySQLに保存します。MySQLユーザーとログイン用メールアドレスは別物です。このスクリプトはCognitoユーザーを作成せず、他PCの会員・注文・庭データもコピーしません。新しいDBの会員は初回ログイン時に作られます。店舗への紐付けや既存会員状態の移行は別作業です。

成功表示はDBとログイン用APIの準備完了を意味します。実際のメールアドレス・パスワードでの認証成功やCognitoへの通信は別途起動後に確認します。認証失敗時にCognitoを無効化しません。

## 設計判断

Context: DB再設定がCognito設定を削除し、旧V1/V2限定の構造検査が現行の会員テーブルを拒否していました。

Decision: DB設定だけを置換し、ソースにある連続したFlyway履歴と対応テーブルを照合してからユーザーと権限を準備します。Flywayのチェックサム検証とHibernateの構造検証も実API起動で実施します。未知構造では自動削除やrepairを行わず停止します。

Alternatives: rootパスワードの強制変更、DB全消去、認証省略は採用しません。

Consequences: 再実行で会員・注文を削除しません。アプリユーザーのパスワードはローカル開発用に統一されます。公開環境には使用しません。適用済みマイグレーションは元に戻さず、失敗時は `.runtime/setup-*.log` とエラーログを確認して修正後に再実行します。これらのローカルファイルはGitに含めません。
