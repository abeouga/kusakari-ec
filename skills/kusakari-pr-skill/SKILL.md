# PR・Issueの本文を、テンプレートを守りつつ「判断に必要なこと」と「原文」で書く

## このスキルが解決する問題

PRやIssueの**構造はテンプレートで決まっている**。問題は**各見出しの中身**で、AIに書かせると次のようなことが起きる。

- 「概要」に関数名やファイルパスが並び、何が変わったのか読み取れない
- 「なぜ」が書かれず、「何をしたか」の作業ログになっている
- レビュアーに必要な情報と、次の作業者（AI）向けのメモが同じ段落に混ざっている
- 確認していないことが、確認済みのように書かれている
- **判断に必要な情報が、詳しいからという理由で折りたたみに押し込まれる。** 未決定事項の一部しか見出しの下に出ていない、決定の理由がない、完了条件が折りたたみの中の一覧を指している、など。読む人は結局折りたたみを開かないと判断できない

このスキルでは、テンプレートの見出しは一切変えず、本文を**2層**にする。2層は「詳しさ」ではなく「**読む人がそれを見て判断・行動するのに必要か**」で分ける。

- **各見出しの下**：読む人が判断・行動するのに必要なことを**すべて**、人間が読んで分かる言葉で書く。短くするために判断材料を削らない
- **本文の一番下の `<details>`（原文）**：全セクションについて、書くべきことを省略せずにすべて書いた全文。見出しの下の内容に加えて、ファイルパス・関数名・コマンド・経緯の細部・次の作業者への指示まで含む。**どのセクションの原文かを必ず明記する**

見出しの下は原文から作る。**原文にないことを見出しの下に書かない。** 見出しの下だけを読んで判断・レビュー・完了の確認ができ、原文だけを読んでも全セクションの内容がすべて分かる状態にする。

## 手順

1. **テンプレートを特定する**
   - PR：`.github/pull_request_template.md`、`.github/PULL_REQUEST_TEMPLATE/` 配下、ルートや `docs/` 配下の同名ファイル
   - Issue：`.github/ISSUE_TEMPLATE/` 配下。`.md` なら見出しをそのまま使う。`.yml`（Issueフォーム）なら各フィールドの `label` が見出しになる
   - テンプレートが複数あれば、内容に合うものを選ぶ。迷ったらユーザーに聞く
   - テンプレートが見つからない場合だけ、末尾の「テンプレートがない場合」を使う

2. **材料を集める**
   - PR：`git log <base>..HEAD` と `git diff <base>...HEAD --stat`、必要なら差分本体。最新コミットだけでなくブランチ全体を対象にする
   - Issue：ユーザーの説明、エラーログ、再現手順、関連コード、関連Issueやコメントでの議論
   - このセッションでの会話（なぜその実装にしたか、却下した案など）も材料にする

3. **先に全セクションの原文を書き、次に見出しの下を書く**（下の「書き方」）

4. **ユーザーに本文を見せて確認を取る**
   - 承認されたら `gh pr create --body-file <file>`、`gh pr edit --body-file <file>`、`gh issue create --body-file <file>` などで反映する
   - 本文はファイル経由で渡す。`--body "..."` は改行や記号が崩れやすい

## テンプレートの扱い

- 見出しの文言・順序・階層を変えない。見出しを追加・削除しない（一番下の原文の `<details>` は見出しではないので追加してよい）
- チェックリスト（`- [ ]`）は残し、実際に満たしたものだけ `[x]` にする。やっていないことにチェックを入れない
- テンプレート内のHTMLコメント（`<!-- 〜 -->`）は記入の指示として読み、その指示に従って書く。書き終えたらコメントは消してよい（リポジトリの慣習で残すなら残す）
- 該当しない見出しは削除せず、「該当なし」と一言書く（テンプレートの構造を保つため）

## 書き方

### 書く順番

1. テンプレートの全セクションについて、集めた材料をもとに**原文**を書く。省略・要約をせず、具体的な事実をすべて入れる
2. 原文をセクションごとに読み返し、下の「見出しの下に必ず書くもの」を**1つずつ拾い出す**。拾ったものは件数を減らさない
3. 拾ったものを、人間が読んで分かる言葉に書き直して各見出しの下に置く。原文はまとめて本文の一番下の `<details>` に置く

### 見出しの下に必ず書くもの

次に当てはまるものは、件数が多くても長くなっても、見出しの下に書く。原文にだけ置かない。

- **決定したこと（PRなら変えたこと）と、その理由。** 理由のない決定は書かない
- **採用しなかった案と、採用しなかった理由。** 1案1行でよい
- **まだ決まっていないこと・残っている作業の全件。** 「主なもの」だけを抜き出さない。数が多ければ、1項目1行に縮めて全件並べる
- **リスクと、元に戻せない影響。** 破壊的変更なら「何が失われるか」を具体的に書く（「破壊的変更」という言葉だけで済ませない）
- **設計の制約と、その制約で困る具体的な場面。** 「〜できない」だけでなく「そのため〜のときに〜が必要になる」まで書く
- **完了条件やチェックリストが参照しているもの。** 完了条件が「〜の項目がすべて決まり」と書くなら、その項目の一覧は見出しの下にある必要がある
- **進み具合を管理するチェックリスト。** 書く人が自分で作ったチェックリストも、見出しの下に置く（折りたたみの中だと進み具合が見えない）
- **内容の中心になる図。** DB設計ならER図、画面変更ならスクリーンショット。補足の図は原文だけでよい
- **確認したこと・していないこと。** 確認していないことは「未確認」と書く

### 原文にだけ書いてよいもの

次のものは、見出しの下に書かず原文にだけ書いてよい。見出しの下で必要なら、説明の後に括弧で1〜2個添える程度にする。

- ファイルパス、クラス名、関数名、テーブルの列名、制約名、型、バージョン
- 実行したコマンド、テストやログの詳細
- 経緯の細部（どのIssueのどのコメントで何が出たか、など）
- 判断の元になった具体的な数値や根拠の詳細（判断そのものと理由は見出しの下に書く）
- 次に作業するAIへの指示（触ってはいけない箇所、守るべき規約、実装上の注意）

### 見出しの下の書き方

- **原文にないことを書かない。** 原文にない事実・推測・評価を足さない。原文と食い違うことを書かない
- **見出しの下には `<details>` を置かない。** 原文は一番下にまとめる
- **「詳しくは原文を」と書かない。** 「全項目は原文にあります」のように読む人を原文へ誘導したくなったら、その情報は見出しの下に書くべきものである
- **最初の1文で、その見出しの問いに直接答える。** 「概要」なら何が変わるか、「背景」ならなぜ必要か、「確認方法」なら何をすれば確かめられるか
- **機能と目的から書く。** 関数名・ファイル名・ライブラリ名を先に並べない。必要なら、説明の後に添える
  - ✕「`useAuth` に `refreshToken` 処理を追加」
  - ○「ログイン状態が1時間で切れていた問題を直し、自動で更新されるようにしました（`useAuth` に処理を追加）」
- **「何をしたか」だけでなく「なぜ」と「その結果どうなるか」を書く。** 作業ログ（〜を修正、〜を追加、の羅列）にしない
- **前提知識のない人に通じる言葉で。** チーム内の略語やセッション中にだけ使った呼び名は使わない
- **短くするときは、言葉を削る。判断材料を削らない。** 1項目を1行に縮める、固有名を原文へ移す、のどちらかで短くする。項目の数を減らして短くしない
- 原文が1〜3行で、書き直しても短くならないセクション（例：「完了条件」「影響範囲」）は、原文と同じ文をそのまま書いてよい

### 原文（一番下の `<details>`）の中に入れるもの

原文は全セクションの全文なので、見出しの下に書いた内容も含めて、省略せずに書く。見出しの下の内容に加えて、「原文にだけ書いてよいもの」をすべて書く。

原文は人間向けに噛み砕かなくてよいが、ファイルパス・関数名・条件は省略せず具体的に書く。原文だけを読んでも、見出しの下なしで内容が分かるように、文として完結させる。

### 「。」で改行する

見出しの下と原文のどちらも、文章は**「。」の直後で改行する**。
1行に1文だけを置き、長い文を横に流さない。
「、」では改行しない。
「、」で改行すると、1つの文が途中で切れて読みにくくなる。
GitHubのPR・Issue本文では、1つの改行がそのまま改行として表示される。

- 段落の区切りは、これまでどおり空行にする
- 箇条書きの項目の中に「。」で終わる文が2つ以上あるときは、2文目以降を次の行に書き、項目の文頭にそろえて字下げする（字下げしないと別の項目や段落として崩れることがある）
- 次の中では改行しない：コードブロック、インラインコード、表のセル、見出し行、リンクの文字列、`<summary>` の文言
- 括弧の中の「。」では改行しない
- Issueを閉じる行（`Closes #12` など）は、文と混ぜずに1行ずつ書く。書き方は下の「Issueを閉じる書き方」に従う

### Issueを閉じる書き方

PRの本文で、マージしたときにIssueを閉じるには、**1つのIssueにつき1行、`Closes #番号` と書く**。
GitHubは、`Closes` の直後にある番号しかIssueとして関連付けない。

```markdown
Closes #108
Closes #109
Closes #110
```

- 番号を「、」「・」「,」でつないで、2つ目から `Closes` を省かない。
  `Closes #108、#109` と同じ行で続けても、`Closes #108、` の後に改行して `#109` と続けても、閉じるのは #108 だけになる（後者は PR #148 で実際に起きた）
- `Closes` の行の末尾に「。」や「、」を付けない
- 「どのIssueをなぜ閉じるか」の説明は、`Closes` の行とは別の文で書く
- `Closes` が効くのは、PRのマージ先がデフォルトブランチ（`main`）のときだけ。
  `feature/〜` などの統合ブランチに向けたPRでは、`Closes` を書いてもIssueは閉じない。
  その場合は「対応Issue」に `関連 #番号` と書き、統合ブランチを `main` にマージするPRで、閉じたいIssueを全件 `Closes #番号` で並べる
- PRを作った後、`gh pr view <番号> --json closingIssuesReferences` で、閉じたいIssueが全件関連付けられているか確かめる

### 2つの層をずらさない

- 同じものには、見出しの下と原文で同じ名前を使う（テーブル名・ロール名・項目名など）。まだ決まっていない名前は「仮」と書き、両方で同じ仮の名前を使う
- 完了条件は、見出しの下と原文で同じものを指すように書く
- 図・画像・チェックリストは、見出しの下に置いたものを原文に重ねて載せない（原文では「見出しの下の図のとおり」と書いてよい）。チェックリストが2か所にあると、片方だけ更新されてずれる
- 本文を後から更新するときは、見出しの下と原文の両方を直す

### 原文の置き方

- 本文の一番最後に、`---`（区切り線）を挟んで `<details>` を**1つだけ**置く
- `<summary>` の文言は `📄 原文` に統一する
- 中は**テンプレートと同じ順番で、全セクションを並べる**。短いセクションや「該当なし」のセクションも省かない
- 各セクションの原文の先頭に、**どのセクションの原文かを `#### 【見出し名】` の形で書く**。見出し名はテンプレートの文言をそのまま使う
- `</summary>` の直後と `</details>` の直前、各 `####` の前後に**空行を入れる**（ないとGitHub上でMarkdownが崩れる）

```markdown
## 概要

ログイン状態が1時間で切れていた問題を直し、操作中は自動で更新されるようにしました。

## 変更内容

期限が切れる少し前に、ログイン状態を自動で更新するようにしました。

- 採用しなかった案：期限切れ後に再ログイン画面へ戻す。
  入力中のデータが消えるため
- 未確認：複数タブを開いているときの動作

## 確認方法

ログインしたまま1時間以上操作し、ログイン画面に戻されないことを確認します。

---

<details>
<summary>📄 原文</summary>

#### 【概要】

ログインのアクセストークンは有効期限が1時間で、期限が切れると操作中でもAPIが401を返し、ログイン画面に戻されていた。
これを、期限の5分前にトークンを自動で更新する方式に変えた。

#### 【変更内容】

- `src/hooks/useAuth.ts`：`refreshToken()` を追加。
  トークンの有効期限の5分前（`AUTH_REFRESH_MARGIN`）に実行する
- 採用しなかった案：期限切れ後に再ログイン画面へ戻す。
  フォームに入力中のデータが消えるため採用しない
- 未確認：複数タブで同時に更新が走った場合の動作
- 注意：`AUTH_REFRESH_MARGIN` は他の画面でも参照しているので変更しない

#### 【確認方法】

ログインしたまま1時間以上操作し、ログイン画面に戻されないことを確認する。
E2Eは `e2e/auth-refresh.spec.ts` で、トークン期限を短くした設定で実行する。

</details>
```

## 設計・方針を決めるIssue

DB設計や仕様の検討など、議論して決めることが目的のIssueでは、決定事項・採用しなかった案・未決定事項そのものが本文の中心になる。次のように書く。

- 「改善内容」などの見出しの下に、**決定事項**（日付、決定と理由、採用しなかった案）と**未決定事項の全件**を、チェックリストで並べる。決まった項目は `[x]` にして、どう決まったかを1行添える
- 決定によって**新たに決める必要が出たこと**も、未決定事項に含める
- 設計の中心になる図（新しいER図など）は見出しの下に置く。比較用の古い図や叩き台は原文だけでよい
- 「完了条件」は、見出しの下にある未決定事項のチェックリストを指して書く
- 破壊的変更（データの初期化など）を決めた場合は、失われるデータと、影響を受ける別のシステムを見出しの下に書く

## 秘密情報

APIキー、トークン、社内URL、個人情報は、原文の中でも書かない。

## 書いた後の確認

提出前に、次を確認する。

- 見出しの下だけを読んで、このリポジトリを初めて見た人が、何が・なぜ変わるのか（決まったのか）分かるか
- 原文を開かなくても、レビュー・判断・完了の確認ができるか
- 「見出しの下に必ず書くもの」が、原文にだけ書かれていないか。特に、未決定事項・残作業が全件見出しの下に出ているか、決定に理由が付いているか
- 完了条件やチェックの対象が、見出しの下だけで確かめられるか
- 見出しの下に「原文にあります」のような誘導がないか
- 見出しの下に、原文にないことや原文と食い違うことが書かれていないか
- 見出しの下と原文で、同じものに同じ名前を使っているか
- 原文に全セクションがテンプレートの順番で揃っていて、それぞれ `#### 【見出し名】` が付いているか
- 原文だけを読んで、各セクションの内容が省略なく分かるか
- テンプレートの見出しが元のまま残っているか
- 確認していないことを、確認済みのように書いていないか
- 見出しの下と原文の文章が「。」の直後で改行され、「、」では改行されていないか
- 閉じたいIssueが、1件ずつ別の行の `Closes #番号` で書かれているか。マージ先が `main` 以外なら、`Closes` で閉じられないことを踏まえた書き方になっているか

## テンプレートがない場合

次の見出しで書き、上の「書き方」に従う。

```markdown
## 概要
## 変更内容
## 確認方法
## レビューしてほしい点
```
