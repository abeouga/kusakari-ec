# Kusakari のユースケースのシーケンス図

kusakari-document の `シーケンス図/kusakari-ec/`・`シーケンス図/kusakari-canvas/` に、ユースケースごとのシーケンス図を Mermaid で書くための決まり。お手本は EC-A01（会員を検索・確認する）の書き直しで、ユーザーが一つずつ指定した書き方をまとめたもの。

## 1. 始める前に

- **コードは固定したコミットで読む。** ユーザーは作業中に kusakari-ec・kusakari-canvas・kusakari-document のブランチを切り替えるので、デスクトップのチェックアウトの作業ツリーは信用しない。`git fetch` してから `git show <sha>:<path>` で読み、図の先頭に書く「対象のコード」の sha と同じものを使う。
- **ユースケース記述**は `アーカイブ/ユースケース/kusakari-ec/`（Canvas は `kusakari-canvas/`）にある。基本フロー・代替フロー・関連情報（どの共通代替フローを適用するか）を先に読む。
- **共通代替フロー**は `シーケンス図/kusakari-ec/00_全ユースケース共通の代替フロー.md`。\*a（通信に失敗した場合）と \*b（未ログインの場合）の中身はここを見る。
- 書き方の元の資料は `アーカイブ/シーケンス図/実装からシーケンス図を書く.html`。「矢印 1 本はコードの 1 か所に対応させる」はそのまま守る。ただし、そこにある「概要図と詳細図の 2 枚」はやめた（下の 2.）。
- 編集は、kusakari-document のデスクトップのチェックアウト（ユーザーの作業中のブランチ）ではなく、`git worktree add --detach <scratchpad>/... origin/main` で作った別フォルダーで行う。終わったら `git worktree remove` で片付ける。

## 2. ファイルの形

```markdown
# EC-A01 会員を検索・確認する

- ユースケース記述: [EC-A01_会員を検索・確認する](<../../アーカイブ/ユースケース/kusakari-ec/EC-A01_会員を検索・確認する.md>)
- 共通代替フロー: [00_全ユースケース共通の代替フロー](<00_全ユースケース共通の代替フロー.md>)
- 対象のコード: kusakari-ec の main（6bad7e3、2026-11-24 時点）

## シーケンス図
（参加者の書き方の 1〜2 行の説明と、Mermaid の図 1 枚）

## 共通代替フローを直接書いた図
（上の図の共通代替フローが起こる所に、*a・*b の中身を書き込んだ図）

## ユースケース記述との差
（箇条書き）

## 参照したコード
（GitHub の URL（コミットつき）と、そのファイルで見た関数名）
```

- **概要図は置かない。** 図は詳細な 1 枚だけにする。
- **「共通代替フローを直接書いた図」を下に置く。** 共通代替フローを ref で済ませずに、その画面で実際に起こる \*a・\*b を流れの中に書いた図。通信しない部分（画面の中だけの絞り込みなど）は共通代替フローが起こらないので、上の図と同じなら省いてよい。省いたことは図の前の 1 文に書く。
- ファイル名はユースケース記述と同じ名前にする。

## 3. 参加者

- **3 行で書く。** 1 行目は画面や役割の名前、2 行目はコンポーネント名・クラス名、3 行目は拡張子つきのファイル名を **かっこで囲んで** 書く。Mermaid は参加者を図の最上部と最下部の両方に出すので、どちらにもこの 3 行が出る。

  ```
  participant Page as 会員管理画面<br/>MembersPage<br/>(OperatorPages.jsx)
  participant Ctrl as 会員管理API<br/>MemberController<br/>(MemberController.java)
  ```

- ファイル名を削って「会員管理画面 (MembersPage)」のように縮めない。どのファイルを開けばよいか分からなくなる。
- **box で層を色分けする。** 境界が分からないと読みにくい。

  ```
  box rgba(47,111,219,0.10) ブラウザー React
  box rgba(27,127,92,0.12) EC API Spring Boot
  box rgba(180,120,20,0.12) 外部サービス
  ```

  MySQL は box の外に置く。Canvas の API は「Canvas API FastAPI」の box にする（色は Spring Boot と同じでよい）。
- 通るファイルは省きすぎない。EC の画面なら `Workspace.jsx` → 画面のコンポーネント → `useResource.js` → `api.js`、API なら Controller → Service → （AuthService）→ Repository → MySQL の流れを残す。

## 4. 矢印

- **`autonumber` を付ける。** 共通代替フローの適用先をこの番号で示す。
- **最初の矢印は利用者の操作にする。** 「運営者メニューの『会員管理』をクリック」のように、どの画面のどれを操作したかを書く。パスだけ（「/operator/members へ」）にしない。URL を直接打ったようにも読めてしまう。
- **同じ参加者の中だけで終わる実装の細部は、矢印にしない。** たとえば `PageLink` の `navigate()` で URL を書き換えるだけの処理は、次の矢印の文に含める（「URL を /operator/members に変え、MembersPage を表示」）。
- **矢印の文は「日本語で何をするか」＋「(メソッド名)」にする。** `list()`、`findAll()`、`storeIdsOf(m)` のようにメソッド名だけにしない。

  | 悪い例 | よい例 |
  | --- | --- |
  | `list()` | 会員の一覧を作るよう頼む (list) |
  | `requireAdmin()` | ログイン中の人が運営者かを確かめる (requireAdmin) |
  | `findAll()` | 全会員を読む (findAll) |
  | `storeIdsOf(m)` | その会員が操作できる店舗を調べる (storeIdsOf) |
  | `data`、`resource.data` | 会員の一覧 |

  HTTP の矢印は `GET /api/operator/members` のようにメソッドとパスを書く。画面の文言は「」で囲んで、コードの文字列どおりに書く。
- 戻りの矢印（`-->>`）も、何が返るかを日本語で書く。
- 長い文は `<br/>` で折り返す。
- ループは `loop 会員ごと`、分岐は `alt`／`else`、あってもなくてもよい処理は `opt` を使う。

## 5. Note は 2 か所だけ

- **`Note` は、最上部の共通代替フローと、代替フローや条件つきの処理の枠（`alt`・`break`・`opt` の中）の 2 か所だけで使う。** それ以外の説明は、矢印（自分への矢印を含む）の文に入れるか、「ユースケース記述との差」に書く。
- **最上部の共通代替フロー**は、フローごとに `<br/>` で改行し、適用先は **矢印の番号だけ** で書く。ある行にはパスを付け、別の行には付けない、という書き方をしない。
- **枠の中の Note には、その代替フローをどのユースケースから持ってきたかを書かない。** 「EC-B16 の 11a と同じ」「EC-B20 の図と同じ」のような出どころの説明は要らない。その図で何が起きて画面に何が出るかだけを書く。
- **枠の中の Note** は、`Note over (分かれた所の参加者),(画面)` の範囲に置き、「結果: 〜。<br/>画面: 〜。」の 2 行までにする。メソッド名や詳しい流れは「ユースケース記述との差」に書く。Note は `autonumber` の番号を使わないので、代替フローを Note にしても基本フローの番号は飛ばない。

  ```
  Note over User,Db: 共通代替フロー<br/>*b 未ログインの場合: 2 (URL を直接開いたときのログインの確認) と 5 に適用<br/>*a 通信に失敗した場合: 5 に適用
  ```

- 番号は矢印を足したり消したりするとずれる。図を直したら、この Note の番号を数え直す。

## 6. 代替フロー

1 枚の図に代替フローを矢印で全部描くと、基本フローが埋もれて読めなくなる。**矢印で描くのは、基本フローと、その図でしか起きない新しいやり取りだけ**にし、代替フローは「どこで分かれるか」だけを図で示して、分かれた後は Note の文にする。

| 代替フローの種類 | 書き方 |
| --- | --- |
| ユースケース記述にあり、ほかの参加者との新しいやり取りがある（新しい API、DB への書き込み、通知の保存など） | `alt` の中に矢印で描く。ただし条件つきの処理（`opt`）は下の行に従う |
| ユースケース記述にあり、画面の中だけで終わる（取り消す、閉じるなど） | 矢印 1〜2 本。補足は Note |
| ユースケース記述にあり、エラーで終わる（サーバーが 4xx を返し、画面が文を出す） | 分かれる所の矢印 1 本と Note 1 つ |
| ユースケース記述にない、実装だけの分岐（存在しない ID の 404 など） | Note 1 つだけ。詳しくは「ユースケース記述との差」 |
| 共通代替フロー（\*a、\*b） | 図には描かない。最上部の Note で番号を示す |
| 条件つきの処理（`opt`。停止のときだけ組織をロックする、申し出を無効にする、など） | 記述にあってもなくても、`opt` の中は頼む矢印 1 本と Note 1 つにする。中で何を読み書きするかは Note に書き、矢印で描かない。記述にないものは見出しに「(記述なし)」と書き、詳しくは「ユースケース記述との差」 |
| ほかのユースケースの図と同じ流れ（EC-A01 と同じ一覧の取得など） | 画面から API までの矢印を数本残し、矢印の文に「中身は EC-○○ の図の ○〜○ と同じ」と書く |

- **エラーで処理が終わる枝は `break` で囲む。** 枝の後に基本フローが続くので、`alt`・`else` で「正常の枝」を作るより入れ子が浅くなる。
- **エラーの後処理は描かない。** `readResponse → ApiError → reload → run が false → 画面を閉じる → エラーの文` のような、どのエラーでも同じ流れは、Note の「画面:」の 1 行と、図の前の説明文で済ませる。
- **大きさの目安。** 当てはめた後でも次を超えたら、さらに Note に寄せる。1 枚の矢印は 40 本程度まで、`alt`・`opt`・`break` の入れ子は 2 段まで、1 つの枝の矢印は 3 本まで（新しいやり取りの枝は除く）。

- **起こらない代替フローは描かない。** 例：EC-A01 の 2a（会員が 1 人もいない）は、ログイン中の運営者本人が一覧に入るので起こらない。図から外し、理由を「ユースケース記述との差」に書く。
- **分岐の処理がない代替フローは `alt` にしない。** 例：EC-A01 の 3a（入力欄が空になった）は、同じ `includes` の絞り込みで全員が残るだけ。基本フローの矢印の文に「(入力欄が空なら全員)」と含める。
- 代替フローの番号（4a、4a-2、\*a-1、\*b-2 など）は、`alt` の見出しや矢印の文の先頭に書く。戻り先（「基本フロー 3 へ戻る」）も矢印で書く。

## 7. 共通代替フローを直接書いた図の注意

- **コードがいつ動くかを確かめてから描く。** 例：`useAuth()` が `GET /api/auth/me` でログイン状態を読むのは、ページを開いたとき（URL を直接開いた、再読み込み）だけで、メニューのクリックでは読み直さない。入口を「URL を直接開いた」と「メニューから開いた」の `alt` に分け、\*b のログインの流れは前者の中に書く。
- EC の \*a は、届かない（`networkErrorMessage`）、Cognito に届かない（503 `AUTH_UNAVAILABLE`）、MySQL に届かない（503 `DATABASE_UNAVAILABLE`）を分けて書く。画面の文言と「再取得」（\*a-3）も書く。
- EC の \*b は、ログインしていない（`AuthPanel` を表示 → ログイン → `returnTo` で読み込み直す）と、使っている間に期限切れ（401 `LOGIN_REQUIRED` → `SessionNotice`）を分けて書く。
- 届かなかった要求は `-x` で描き、届いた後の失敗は、届いた矢印の後に戻りの矢印で描く。

## 8. 「ユースケース記述との差」に書くこと

- 図に描かなかった代替フローと、その理由。
- 記述に書かれていない決まり（大文字と小文字を区別する、前後の空白を取り除かない、など）。
- 記述にない処理（画面が使わない値をサーバーが返している、など）。
- 事前条件で外したため描かなかった分岐（運営者以外が開いたときの「権限がありません」と 403 など）。

## 9. 確かめること

- **描けるか**：kusakari-ec のリポジトリで `node .claude/skills/kusakari-sequence/scripts/validate-mermaid.mjs <ファイル>` を実行し、Mermaid 10.9.3 と 11.4.1 の両方で描けることを確かめる。Mermaid の本体（`mermaid-10.9.3.min.js` と `mermaid-11.4.1.min.js`）はリポジトリに入れていないので、置いたフォルダーを環境変数 `MERMAID_DIR` に指定する（指定がなければ `~/.claude/skills/kusakari-sequence/scripts/mermaid` を見る。新しく入れるときは、ダウンロードしてよいかユーザーに聞く）。Playwright は kusakari-ec の `node_modules` のものを使う（無いときは環境変数 `PLAYWRIGHT_INDEX` で指定する。新しく入れるときは、ダウンロードしてよいかユーザーに聞く）。
- **名前が合っているか**：図に書いたファイル・関数・API のパス・画面の文言が、対象のコミットにあることを `git show <sha>:<path> | grep` で確かめる。「参照したコード」の GitHub の URL のファイルが、そのコミットにあることも確かめる。
- **Note の置き場所**：`grep -n Note` で、Note が最上部の共通代替フローと、代替フローの枝（`alt`・`break` の中）だけにあることを確かめる。矢印の数と入れ子の深さが 6. の目安に収まっているかも数える。
- GitHub と Obsidian での見た目は確かめられないので、確かめていないと報告する。

## 10. 出し方と push

- ユーザーが「セッションに出力して」と言ったら、push せず、ファイルの全文を会話に ````markdown のコードブロックで出す。直した所だけを出すときは、変えていない節をはっきり書く。
- push は頼まれたときだけ。kusakari-document の main に直接 push してよいのは、ユーザーが main に push と言ったとき。
- コミットメッセージは、リポジトリの直近のコミットに合わせて日本語で書く。件名（何を変えたか）、本文（なぜ、何を、変えていないもの、確かめたこと・確かめていないこと）。`Co-Authored-By` などの AI の帰属の行は付けない（no-ai-text スキルに従う）。
- 1 つのユースケースを直したら、ほかのユースケースの図・00 の共通代替フロー・README の「概要図と詳細図」の説明が、まだ古い書き方のままであることを報告する。勝手に一緒に直さない。
