# Issue を短く、人が読める形で書く

Issue は、人が読んで「何をなぜやるか」を判断するための文書である。
AI が実装するための計画書にはしない。
実装に要る細かいこと（どのファイルをどう変えるか）は、作業するときにコードと docs/ から調べる。
書いておいても、作業するころには古くなっている。

## 見出し

- ふつうは「概要」の 1 つだけにする
- 決まっていないことがあるときだけ、「決めること」を足す
- ほかに要るときも、多くても 4 つまでにする
- テンプレートに欄が多く残っていても、空の欄や「該当なし」の欄は書かない

## 概要は 1 文で書き、要るときだけ注釈を付ける

**1 文目**：何ができるようになるかを「〜できるようにする」の形で 1 文に書く。
多くの Issue はこれで足りる。
PR の完了条件は、この 1 文から作る。

**注釈**：なぜ要るか・前提（前に決めたこと）・根拠へのリンクは、書くことがあるときだけ、1 文目の下に 1 行空けて `>` で 1〜2 文書く。
GitHub では灰色で出るので、本文と区別できる。

- 「どう進めるか」は、1 文目で分かれば書かない。
  迷うことは「決めること」に入れる
- 型を埋めるための文を書かない。
  このリポジトリの名前を主語にした文（drive-logger の Issue で「カブロガーに作る」など）は、言わなくても分かる
- 根拠の数字や前に決めたことは、Issue か docs/ へのリンクにして書き写さない

注釈も、読む人には 1 文目の続きとして読めるように書く。

- **前の文に出た言葉から始める。**
  初めて出る言葉を「〜は」で文の頭に置かない（「は」は読む人が知っていることに付く）
- **主語が変わるときは書く**
- **細部に落ちない。**
  返す形・名前・種類の値などは書かず、決まっていなければ「決めること」に入れる
- 前提を知らない人に通じない呼び名（その設計の中だけの言葉）は、言い換えるか説明してから使う

```markdown
### 概要
カブロガーの走行のデータを MCP で取り出し、Agorack のサイドバーに出せるようにする。

> Agorack は部品と MCP だけでつなぎ、答えの元になったデータを、どの部品からも同じ形で受け取ると決めている（agorack の決定 0003）。
```

✕ 型を埋めるために文を足した形（3 文目はリポジトリの名前を主語にしていて、言わなくても分かる）

```markdown
カブロガーの走行のデータを MCP で取り出し、Agorack のサイドバーに出せるようにする。
Agorack は部品と MCP だけでつなぎ、答えの元になったデータを、どの部品からも同じ形で受け取ると決めている（agorack の決定 0003）。
カブロガーにも、その形で走行を返す MCP サーバーを作る。
```

## 決めること

決まっていないことを、番号付きのチェックボックスで並べる。

```markdown
### 決めること
- [ ] 1. 返すもの（走行の一覧・1 本の走行の中身・異常のスコアの、どれから作るか）
- [x] 2. データをどこから読むか。
  決定：今のデータ API を通す
```

- 番号は `- [ ] 1.` の形で書き、一度振った番号は振り直さない。
  要らなくなった項目は消さず、`[x]` にして理由を 1 行添える
- 決まったら `[x]` にして、どう決まったかを 1 行添える
- すべて `[x]` になったら閉じてよい

## 書かないもの

- **完了条件**。
  PR に書く
- **実装計画**。
  関数名・パッケージ名・ファイルパス・テーブルや列の名前を並べない。
  名前そのものが話の中心のとき（API の形の名前など）だけ書く
- **やらないことの断り**。
  「〜は変えない」「〜はしない」「この Issue では扱わない」を書かない。
  範囲に入れるかどうか本当に迷うことは、「決めること」に入れるか、別の Issue にする
- **実装しながら確かめればよいこと**（処理時間、細かい例外の扱いなど）。
  PR で報告する
- **折りたたみ（`<details>`）の原文**。
  同じことを 2 回書かない
- **「決めること」を見れば分かる一言**（「決めることを決めてから作る」など）

## 文の書き方

- 前提知識のない人に通じる言葉で書く。
  セッションの中だけで使った呼び名を使わない
- 「。」の直後で改行し、1 行に 1 文を置く。
  「、」では改行しない。
  箇条書きの中で 2 文目を書くときは、次の行に字下げして続ける

## ラベルごとの書き方

ラベルによって合う書き方は変わる。
決まったものから、ここに足していく。

- （まだない）

## 親子の Issue

- 子 Issue は GitHub の sub-issue として親に登録する（`gh api repos/<owner>/<repo>/issues/<親>/sub_issues -F sub_issue_id=<子の ID>`。
  ID は `gh api repos/<owner>/<repo>/issues/<子> --jq .id` で取る）
- 親の本文に子 Issue の一覧を書かない。
  進み具合は sub-issue 欄で分かる
- 子 Issue にできるほど固まっていないことは、親の「決めること」に書く

## 既にある Issue に足す

同じ画面・同じ目的の変更が開いている Issue にあれば、新しく立てずにその本文を直す。
足したら、どの Issue に足したかをユーザーに伝える。

## 画像

ユーザーが画像を渡したら本文に添付する。
`gh` は画像を上げられないので、リポジトリの画像用のブランチ（drive-logger は `pr-evidence`、kusakari-ec は `pr-screenshots`。無ければ作る前にユーザーに聞く）に置き、コミットのハッシュで固定した raw URL で埋め込む。
個人情報や秘密が写っていれば、添付する前にユーザーに確かめる。

## 立てる前の確かめ

- 見出しが 4 つ以下で、空の欄を残していないか
- 概要の 1 文目が「〜できるようにする」になっているか
- 注釈は要るときだけで、`>` で 1〜2 文か。型を埋めるための文を足していないか
- 注釈を声に出して読み、1 文目から続けて読めるか（初めて出る言葉で文を始めていないか、細部に落ちていないか）
- 完了条件・断りの文・名前の羅列・折りたたみが無いか
- 本文はファイルに書き、`gh issue create --body-file <file>` で立てる（`--body "..."` は改行や記号が崩れやすい）
