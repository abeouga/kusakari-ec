# PR を、見る人が判断できる短い文で書く

PR は、見る人がマージしてよいかを判断するための文書である。
Issue には「何ができるようになるか・なぜ・どう進めるか」だけがあり、完了条件は無い。
完了条件は、実際の変更を見ながら PR で書く。

## 手順

1. テンプレート（`.github/pull_request_template.md` など）を探し、見出しをそのまま使う
2. 材料を集める：ブランチ全体の `git log <base>..HEAD` と `git diff <base>...HEAD --stat`、対応する Issue の概要と決めること、このセッションでの判断
3. 完了条件を、Issue の概要の最初の文（「〜できるようにする」）から作る
4. 本文をファイルに書き、`gh pr create --body-file <file>` で作る

## 完了条件

- Issue の概要の最初の文を満たしたと言える条件を、番号付きのチェックボックスで並べる（`- [ ] 1.`）
- 確かめられたものだけ `[x]` にする。
  確かめていないものは `[ ]` のまま残し、なぜまだかを 1 行添える
- 「テストが通る」のような、どの PR にも当てはまる項目は書かない（テンプレートの動作確認にある）

## 各見出しの書き方

- 「変更内容」は、何が変わったかを最初に 1 文で書く。
  なぜ変えたかは、書くことがあるときだけ、その下に 1 行空けて `>` の注釈で 1〜2 文書く（GitHub では灰色で出る）
- 最初の文で、その見出しの問いに答える
- 何が変わったか・その結果どうなるかを、人の言葉で書く。
  関数名やファイル名は、見る人が差分を探すのに要るときだけ、文の後に括弧で 1〜2 個添える
- 確かめたことと、確かめていないことを分けて書く。
  確かめていないことを、確かめたように書かない
- 残っている作業（本番への反映など）は「未対応事項」に書く
- 「〜は変えていない」の断りは、見る人が心配しそうなこと（判定の点数、約束の形など）に限って 1 文で書く
- 該当しない見出しは「なし」と一言にする
- 折りたたみ（`<details>`）の原文を作らない。
  同じことを 2 回書かない
- 「。」の直後で改行し、1 行に 1 文を置く。
  「、」では改行しない

## Issue を閉じる書き方

- 1 つの Issue につき 1 行、`Closes #番号` と書く。
  `Closes #108、#109` と並べると #108 しか閉じない
- `Closes` の行の末尾に「。」や「、」を付けない
- マージ先が `main` 以外なら `Closes` は効かない。
  `関連 #番号` と書き、`main` に入れる PR で閉じる
- 作った後、`gh pr view <番号> --json closingIssuesReferences` で関連付けを確かめる

## 画像

画面に効く変更は、変更後の画像を本文に貼る。
`gh` は画像を上げられないので、リポジトリの画像用のブランチ（drive-logger は `pr-evidence`、kusakari-ec は `pr-screenshots`。無ければ作る前にユーザーに聞く）に置き、コミットのハッシュで固定した raw URL で埋め込む。

## マージ

squash でマージするときは、件名と本文を自分で渡す（`gh pr merge <番号> --squash --delete-branch --subject "..." --body "..."`）。
件名と本文の書き方は `no-ai-text` スキルの「コミットメッセージ」に従う。
